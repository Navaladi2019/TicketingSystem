    What a user can now do

    A tenant admin publishes a version of a ticket type that gives a field a default, for example "priority defaults to 3". In the background, every existing ticket that has no priority gets 3 stored. Each changed ticket gets one audit entry. Its version moves, so an open edit form sees a 412 once, but its "last updated" time does not change. No workflow is started by the rewrite.

    • A publish that also marks the field x-nava-unique is refused (422 invalid_definition): two tickets would share the value.
    • Making an existing field required is now allowed when the new version gives it a default (NeedsBackfill). Without a default it is still breaking.
    • A second publish of the same type while the job runs replaces it; the newer job does the work.
    • Types that already had a default before S29 get one job each from the rollout migration, except types that combine a default with x-nava-unique.

    Not yet (TICK-1192): filtering on priority 3 before the job ends, the job's progress on the type's page, and the list of tickets that could not be rewritten. Until then a filter finds only tickets whose value is stored, as before S29.

    How it works

    • Publish: metadata engine, steps 3a and 6a.
    • The job: schema backfill workflow and its tables.
    • The record write: OpMaterialize.
    • Temporal: schema.backfill is start-only and relay-only (Temporal authorization).

    Row What it proves State
    1 The three tables under RLS for nava_app and nava_worker: no tenant B row, no B insert, nava_app inserts only its own fresh pending job, nothing with no tenant, no value column; B's active job never blocks A's admission runs
    2 getEntityType, the failures route and a publish on B's key are the unknown key's 404 for A waits on TICK-1192
    3 With open windows in both tenants, the D12 shapes never return or count a B record, and the ACL holds in the UNION ALL arm waits on TICK-1192
    4 OpMaterialize in A's transaction naming B's record or B as actor writes nothing; a patch, another source, a principal or another actor is refused runs
    5 The real workflow t:A rewrites A's records and none of B's, with the same key and B's own job; mismatched ids fill nothing; no value in history runs
    6 The relay marks a payload carrying tenant_id dead with no Temporal call, and always starts under the row's tenant runs
    authz No worker command can start or continue-as-new schema.backfill; only nava-relay starts it; the queue is not a side door runs
