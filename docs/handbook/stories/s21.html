    S21: Filter a large ticket type on a flagged field in milliseconds

    Story TICK-739, plan PLAN-007 (TICK-736), design ADR-006, with erratum E1 (the barrier waits past xmax; READ COMMITTED writers only) and amendment A1 (the 350 ms bands). **In progress: built on the story branch TICK-739/filterable-fields, not on main, and not yet accepted.** Every build task is merged into the story branch. Still open: the acceptance kit (TICK-749, PR #794), the branch's catch-up with main (TICK-1023), and the ≥ 40% ACL plan investigation (TICK-1022).

    What a user can now do

    A tenant admin marks a top-level field of a ticket type as filterable by adding "x-nava-filterable": true to the property in a published version. The platform indexes the existing records in the background. Once the field is ready, an agent filters a 400k-record list on it in tens of milliseconds instead of about a second:

    • filter[priority]=1 and filter[site][in]=s1,s7 (equality, up to 100 values) on text, number, date-time and boolean fields;
    • filter[priority][gte]=2&filter[due_at][lt]=2026-12-01 (ranges on number and date-time fields). On an array field, one element must satisfy every bound.

    While the field is indexing, a filter on it answers 422 field_not_ready with the whole percentage done, index_progress, and nothing else. Records created or edited during or after indexing are found.

    Rules a caller sees

    Situation Answer
    The field is masked for the caller 400 masked_field (checked first)
    The field is not flagged 400 field_not_filterable, except the three seed fields that keep the old JSONB scan until S22: incident.priority, request.priority, change.risk
    The field is flagged and indexing 422 field_not_ready, index_progress
    The value does not fit the field's type, or a range on text or bool 422 validation_failed
    Publish puts the flag below the top level 422 filterable_field_not_top_level
    Publish changes the value type of a flagged field 422 filterable_field_type_change
    Publish drops a flag or a flagged field 422 filterable_field_removal_unavailable (removal is S22)
    Publish flags more than 5 fields on a type, or 50 in the tenant 422 index_quota_exceeded
    Publish flags a field whose index is being removed 409 field_index_busy
    Publish uses x-nava-searchable 422 searchable_not_available (free-text search is RFC-016)

    The list filter reads the side table only through a correlated EXISTS (SELECT 1 FROM rfv_<t> v WHERE v.tenant_id = r.tenant_id AND v.record_id = r.id AND v.field_id = $n AND v.value <op> $m) inside the one list statement that carries the row ACL, so the ACL and the tenant predicate apply to every hit and to total. TestListFilterPushdownIsAnIndexCond checks the plan uses rfv_<t>_value as an index condition for each operator under forced RLS. Indexed lists record nava.records.list.indexed.duration, labelled by selectivity band and ACL presence only.

    Attack paths

    Registered isolation paths (internal/tenancy/isolation/fieldindex_attack_paths.go), run by TestRegisteredPaths in the CI integration job with ISOLATION=1. Each row was shown red against a broken variant of the defence it proves (review). **All six rows run; none is pending.**

    Row Case Attack Defence proven Task
    1 CI-2 Tenant A filters on values only tenant B has, while B's fields move through every registry state Hits, total, status, error code and index_progress equal those of a value no tenant has TICK-748
    2 CI-8 An agent filters on a value only in a record the ACL hides, or on a masked field Same bytes as a value nobody has, for every operator; a masked field is the same 400 masked_field in every state TICK-748
    3 CI-2 Tenant A publishes a flagged definition against tenant B's type, with a forged X-Tenant-Id; the backfill's seven statements run as tenant A with tenant B's field id Registry and outbox rows for the caller's own tenant only; the statements read, write and flip nothing (0 rows or FK 23503) TICK-748
    3b CI-2 FieldIndexBackfill is started from tenant A's outbox row whose payload names tenant B (tenant_id or field_id) The tenant is bound from the row (the relay header), never the payload; the real coordinator and backfill write nothing TICK-975
    4 CI-2 Every runtime role, as raw SQL: UPDATE a side table, write another tenant's side or registry row Refused; registry column grants are exactly ADR-006 D14 TICK-748
    5 CI-2 Read counts out of field_not_ready The body carries the registry's percentage only, identical for every value, caller and record count TICK-748

    Row 3 originally covered the database layer only, with its workflow half (3b) registered as pending on TICK-745. TICK-975 added 3b, which drives the real coordinator and backfill, so both now run. The relay also refuses a payload tenant_id that differs from the row's before any Temporal call.

    Performance

    Scored on the reference machine on 2026-11-19 (TICK-992, story head 9ec4e1f5), against ADR-006 D13 as amended by ADR-006-A1 (≤ 150 ms list p95; ≤ 350 ms for the 0.5–2% band with or without a narrowing ACL, and for the ≥ 40% band with one):

    • Lists, 40 cells: 2 miss against the A1 limits, both 0.25% in (160.9 / 152.8 ms, 29–35 ms of server time, on a host whose idle control read up to 1.3× the fully idle figure). Three cells pass by 10% or less, so they are provisional: 2% ACL text eq 317.6 ms, 40% ACL text in 327.6 ms, and 0.25% ACL bool eq 143.5 ms. TICK-1002 rescores the provisional cells on a fully idle host.
    • Insert with 5 flagged fields: 83% of baseline tps (budget ≥ 40%).
    • Live writes during a 400k backfill: −7.4% p95 (budget ≤ +25%); the backfill takes 8–10 minutes.

    TICK-1022 is open: on one fresh stack the ≥ 40% ACL list p95 read 578–983 ms, and 119 ms on the next. The diagnosis in PR #796 ties the count plan to the side table's visibility map after the backfill. The numbers are on the benchmarks page and in field-index-measured.md.

    How to try it

    The acceptance kit (Bruno folder S21 filterable fields, TICK-749) is not merged yet. When it is, it seeds 400k incidents in tenant A, publishes x-nava-filterable on priority (number) and due_at (date-time) as the tenant A admin, polls the list as the tenant A agent until the field is ready, then filters. This section will name the kit's steps and its recorded run.

    Not in this story

    • Removing a flag, the operator quota raise to 10, flagging the seed fields and retiring the JSONB scan: S22 (TICK-740).

    • Free-text search (x-nava-searchable, RFC-016) and sort on data fields.
