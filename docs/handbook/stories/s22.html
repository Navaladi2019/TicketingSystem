    What a user can now do

    • Unflag a field. A tenant admin publishes a version without "x-nava-filterable": true on a property. The publish is accepted (201). A filter on the field answers 400 field_not_filterable straight away, and the field's index is removed in the background. Flagging it again while the removal runs answers 409 field_index_busy; afterwards it is accepted and re-indexed. Before S22 this publish was refused.
    • Get a higher limit. An operator raises a tenant's per-type limit of filterable fields from 5 to at most 10, with a reason. The change is audited. A tenant cannot raise its own limit.
    • One filter path. The seed types incident, request and change flag the fields they filter on (priority, priority, risk), and the old JSONB filter scan and DataFilterTimeout are gone: every data-field filter goes through the field index, and its count runs under CountBudget.

    Rules a caller sees

    Situation Answer
    Publish that drops the flag 201; the field is removing
    Filter on a field that is removing or not flagged 400 field_not_filterable
    Flag a field that is still removing 409 field_index_busy
    Publish that deletes a flagged property 422 schema_breaking_change
    Publish over the type's limit (5, or the raised limit) 422 index_quota_exceeded
    PUT /api/v1/operator/tenants/{tenant}/limits with a tenant token 403
    Same, unknown tenant / value outside 5 to 10 or no reason / not strict JSON 404 / 400 / 422 invalid_tenant_limits
    Same, the value already in force 200, nothing written, no second audit entry

    How it works

    • Removal. In the publish transaction the registry row flips to removing and one field_index.remove outbox row is written. The relay hands it to the tenant's field-index coordinator, which runs field_index.remove.run as a child after any backfill ahead of it: barrier, batched deletes of 1,000 side rows, then the registry row is deleted only if no side row is left. See Field-index backfill: removal.
    • Limit. tenant_limits holds the raised value; publish reads it through tenantlimits.PerType. Only nava_onboard writes the table, in the target tenant's transaction. See Tenancy.
    • Seed publisher. entity_definition_versions.published_by_system ('onboarding' only) lets onboarding publish a v2 seed with no principal. nava_app may not write that column (TICK-1172). See Entity types.
