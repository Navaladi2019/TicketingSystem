    Handbook / security / 2. Tenant resolution

    2. Tenant resolution

    Boundary

    The tenant of a request comes only from the validated token, through the binding of its issuer and organization. Nothing the client controls (path, query, body, header, W3C baggage) can name or change it. A token that maps to no tenant, to two tenants, to a tenant that is not active, or to a principal whose federated identity is not bound to that tenant gets 401.

    Enforcement point

    internal/platform/auth wraps every /api/v1 operation. It reads the bearer token, calls identity.IdentityResolver.Resolve, and puts the returned identity.Principal in the request context. Handlers read it with identity.FromContext and pass its TenantID to tenancy.InTenantTx.

    keycloak.Adapter.Resolve (ADR-001 A.1 steps 2 to 5):

    1. The token must name exactly one organization.
    2. tenant_identity_binding (issuer, org_id) gives the tenant; the pair is UNIQUE, so one organization never resolves to two tenants.
    3. The bound tenant's tenants.state must be active, read inside InTenantTx(tenant).
    4. The token's idp claim, if present, must be an IdP alias bound to that tenant.
    5. The principal (tenant, sub) must exist, be enabled, and have its federated links known and all bound to the tenant.

    Any refusal is 401 tenant_unresolved with a fixed reason; a store failure is 500, so a database outage never makes clients drop good tokens. The log carries the reason, never the token or a claim value; tenant_id is a log field and a span attribute after auth, never a metric attribute.

    Proving tests

    Attack Test
    Zero or two organizations, unbound idp, foreign federated link, NULL links, no principal row TestResolveRefusals; against PostgreSQL TestT17RefusalsAgainstPostgres
    Binding to a tenant that is not active TestResolveTenantNotActive, TestT17aRefusesNonActiveTenant
    Forged tenant in query, header, body or baggage CI-2 HTTP paths in TestRegisteredPaths; TestMeIgnoresForgedTenant, TestGetMeIgnoresSuppliedTenant, TestForgedBaggageIsNotInTheContext
    Same sub in two tenants TestGetMeSameSubjectInTwoTenants
    A second binding of one (issuer, org) TestT09DuplicateBindingRejected; CI-5.12
    A token scope naming another tenant's organization; a broker taking over another tenant's user TestOrganizationScopeCannotNameAnotherTenant, TestBrokerCannotTakeOverUserOfAnotherTenant; CI-5.01, .02, .06 to .11, .13 in TestCI5
    Logs, spans, metrics TestRefusalLogsNoToken, TestServerSpanCarriesTenantOnlyAfterAuth, TestMetricHasNoTenantAttribute

    Fixture that turns it red

    Every HTTP path in the isolation suite first requires a baseline GET /api/v1/me to answer 200 for tenant A, so no path can pass on a 401; a path passes only on a 200 whose body names tenant A and never tenant B. The CI-5 mutation checks are recorded in identity-ci5.md: binding tenant B to idp-tenant-b makes CI-5.09 fail, and giving the CI-5.10 seed principal no link makes that path fail.

    Accepted risks

    ID Sev Risk Status Owner Revisit trigger / proposed fix Source
    AR-035 🟠 Medium Email-domain ownership is first-claim-wins (T21). Onboarding refuses public email-provider domains but does not verify DNS ownership: the allow-listed operator who names the domains attests the tenant owns them (the AC's "explicit operator approval"). A mistaken or malicious operator can claim a domain before its real owner; the unique key then makes the owner's own onboarding fail with domain_claimed. The public-domain list (internal/onboard/public.go) is best-effort: it is hard-coded, misses regional variants (yahoo.fr, gmx.de, ...) and subdomains of listed providers. IdP URLs are checked once, at onboarding, so DNS rebinding can still point a validated host at an internal address when Keycloak resolves it later. Accepted Security & Multi-Tenancy Reviewer Self-service signup, or any non-operator caller: require DNS TXT verification of each domain, replace the list with a vendored, maintained free-mail list, refuse subdomains of listed providers, and re-check or pin the resolved address when Keycloak fetches an IdP URL. TICK-81 (T21), TICK-194 (T18a) security review, onboarding.md
    AR-037 🟡 Low An IdP bound to another tenant can create the username for an address in tenant A's domain before A's invited admin's first broker login. A's admin is then refused (federated_identity_account_exists). Nothing links and no /t/<A>/ placement happens (TICK-252 condition 2c). Accepted Security & Multi-Tenancy Reviewer Revisit at the first tenant whose IdP is not domain-exclusive, or the first support case of an invited admin hitting this. Fix: a domain-to-tenant guard at first login, via an rfc. Workaround: the operator deletes the squatting user. TICK-252 CTO decision (2026-10-27); spike N2; Security ruling 2026-10-26
