        5. Temporal: workflow id, worker guard, Authorizer

        Boundary

        All tenants share one Temporal namespace, one worker fleet and one task queue. A workflow running for tenant A must not start, signal, cancel or continue into a workflow of tenant B, and a platform process holding one Temporal certificate must not call an API outside its row of the allow-list or reach the server's internal ports. Record data must not be written into Temporal history.

        Enforcement point

        Three layers, lowest first:

        1. Certificate and network. mTLS with the installation CA; the gateway forwards only the frontend port; internode traffic uses its own CA, so a platform certificate cannot join the cluster.
        2. Authorizer (temporal-server/authz, a custom server build pinned by ADR-001-A1). Each certificate CN is an identity with a fixed row of allowed API methods and workload types (the D9 allow-list, golden-tested). For a worker's task completion it decodes the task token, takes the tenant from the workflow id prefix t:<tenant>:, and refuses any command that targets another tenant's workflow id, continues-as-new without the matching nava-tenant header, or is not on the command list. Each deny is logged with alert=true and counted in nava_authz_denied.
        3. Worker guard (internal/workerguard, in the worker process). The SDK interceptors check the nava-tenant header on start, signal, child, continue-as-new and memo calls, and withhold any result, failure or payload that carries record data before it reaches history (CI-7).

        The workflow id is built from the tenant of the JWT on the platform side, never from a client value (R-CORE); that rule is enforced in nava-core code and tests, not by the Authorizer (AR-004).

        Fixture that turns it red

        A mutation was run by hand while writing CI-6: with the child target switched to the attacker's own tenant, the cross-tenant child test fails (the call is allowed and no alert is logged), so the deny depends on the tenant, not only on the command type. Each worker-command test also requires that no WorkflowTaskCompleted appears in the attacker's history, so a deny that still wrote history fails.

        Accepted risks

        AR-001 (a stolen nava-worker certificate reaches every tenant) and AR-002 (histories are not encrypted in M1) are the accepted residuals of sharing one Temporal cluster across tenants.

        ID Sev Risk Status Owner Revisit trigger / proposed fix Source
        AR-001 (R8) 🔴 High† A stolen nava-worker certificate polls every tenant's tasks and histories and can set any app.tenant_id, so it reads and writes any tenant under RLS. A stolen nava-relay or nava-core certificate can start or signal for any tenant. Accepted Security reviewer Any new holder of a Temporal certificate, or per-tenant workers required ADR-001 §5
        AR-002 (R1) 🟠 Medium† Temporal histories are cross-tenant data and are not encrypted in M1. Accepted Solution Architect First regulated-data tenant, or TICK-41 decided; then a per-tenant encrypting codec ADR-001 §5

        AR-013 (R7) 🟡 Low† A custom Temporal server build to own (the Authorizer module). Accepted Technical Lead Every Temporal upgrade, or any Go vuln DB advisory against the pinned server (A1) ADR-001 §5, ADR-001-A1
        AR-016 (RS2) 🟡 Low† D6-K dynamic-config checks, including A2's new row, run only at startup. Accepted Security & Multi-Tenancy Reviewer Any runtime write path to dynamic config ADR-001-A1, ADR-001-A2
        AR-019 (RS7) 🟡 Low One nava-worker pod can unload a sibling's SDK-shaped sticky queue (stickyQueueName checks shape, not owner). Source calls it harmless. Accepted Security & Multi-Tenancy Reviewer Per-pod or per-tenant worker certificates; sticky queues gain a tenant meaning ADR-001-A2, plan-adr-001-a2
        AR-025 🟡 Low The worker keeps GetWorkflowExecutionHistory (SDK history paging), which takes any workflow id and no task token, and the task-token APIs (RespondActivityTaskCompleted and the others), which the Authorizer does not inspect. A nava-worker certificate holder that knows another tenant's workflow id, run id and scheduled event id could read that history or hand-build a task token. Needs a compromised worker process (same trust class as AR-001), not tenant workflow code. Accepted Security & Multi-Tenancy Reviewer Activity code ever given a raw Temporal client; per-tenant worker certificates TICK-65 issue (T27b review TICK-84, T27c review TICK-110), worker-guards.md
        AR-040 ⚪ Info The Authorizer does not tie the relay's nava-tenant header to the tenant in the workflow id; it only requires a t: prefix. Safe today: the relay derives both from outbox.tenant_id, and the worker guard rejects a mismatch. Accepted Security & Multi-Tenancy Reviewer Any relay change that sets the header and the workflow id from separate values: add a D9a header check in the Authorizer TICK-85 (T30b, PR #96) security review, recorded on TICK-191
        AR-042 🟡 Low A workflow panic's value and stack are recorded in WorkflowTaskFailed. The worker guard cannot recover it without turning a task retry into a workflow failure, so a panic value built from record data would reach the history. Review rule instead: workflow code never panics with a value built from data. No feature workflow exists yet. Accepted Security & Multi-Tenancy Reviewer Checked in every review of internal/workflow/ under the "Workflow panics" row of review-standard-core.md (P3-26, TICK-362); revisit if a review finds a panic built from data TICK-245 Security triage, row 7a; temporal-ci6.md
        AR-043 ⚪ Info A failure the worker guard withholds is retyped nava.Opaque, so a RetryPolicy.NonRetryableErrorTypes entry naming its original type no longer matches. The non-retryable flag itself is kept, which is the documented way to stop retries. Accepted Principal Software Engineer A retry policy that lists error types: use the non-retryable flag, or add the type to the guard's allowed list after review TICK-245; worker-guards.md
        AR-S11a-01 🟡 Low The workflow interpreter learns each step from a workerguard.Directive activity result, so a history shows the order of directives (which branch a condition took: one derived bit per step) and TimerStarted shows each wait length. Neither is a tenant literal: every Directive value is a UUID, a fixed Kind constant or a wait taken from the published definition, never from a record field, and the guard refuses anything else (worker-guards.md, directiveOK). Accepted Security & Multi-Tenancy Reviewer A step kind whose branch or wait is chosen from a record field value, rather than only from the definition, or history encryption (R1) is taken up TICK-360, TICK-363 grooming; TICK-362; plan-records-path.md D-3-12, D-3-15
        AR-TICK-386-01 🟡 Low The worker guard binds a workerguard.Directive by name, not by handler: directiveAllowed accepts one only from a regular activity named nava.interpreter.NextStep called from a workflow named nava.interpreter (TICK-386). Any binary with the guard and namespace credentials can register both names on its own task queue, and its NextStep could then record a Directive. It is not exploitable today, because only cmd/nava-worker links internal/workflow/interp. It does not cross tenants: the activity tenant check runs first, and directiveOK limits the record to canonical UUIDs, a fixed kind and a bounded wait, so at worst a rogue workflow steers its own steps. Accepted Security & Multi-Tenancy Reviewer A second binary links internal/workflow/interp, or any new worker polls nava-tq. Proposed fix: bind at registration time, so workerguard refuses to register DirectiveWorkflow or DirectiveActivity unless the handler is interp.Workflow or (*interp.Activities).NextStep. Add a cmd/* test of every binary's registered names. PR #332 security review, directive.go (directiveAllowed)
