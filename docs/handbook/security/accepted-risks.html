        Accepted-risk register

        Every risk the project has knowingly accepted. This page is rendered at build time from docs/security/accepted-risks.md, which stays authoritative: the rows below are copied as written, and only their relative links are rebased so they open from the handbook. Each layer page in this section lists the rows that apply to it.

        Severity

        Flag Meaning
        🔴 High A tenant-isolation break if one precondition fails (for example, one stolen credential)
        🟠 Medium Data exposure or a weakened control, but needs more than one failure, or the control is in doubt
        🟡 Low Availability, cost or operability; no tenant data at risk
        ⚪ Info Process cost or a known limitation

        A severity marked † was assessed when this register was built (2026-10-24), because the source gives none. An unmarked severity is the source's own rating.

        Status: Accepted (signed off as is), Fix proposed (a cheap fix is written down; prefer fixing over keeping it), Control disputed (the recorded mitigation does not hold as written; re-decide).

        AR-027 🟡 Low A leased head is not backing off, so its available successors on the same target can fill the tenant's 200-row scan window. The other targets then wait while the deep target drains one row per settled dispatch (one poll at best), until fewer than 200 of its rows are older than theirs: about depth − 199 settled dispatches for a target depth rows deep. That drain also follows a normal settle of the head, not only a crash, and each relay crash during the drain adds one more lease. Accepted Technical Lead T33's flood test shows it (TestT33LeasedHeadOnDeepTarget pins both bounds) TICK-74, TICK-248, decision-log 2026-10-25 T30a, outbox-relay.md
