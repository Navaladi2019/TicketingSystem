    Handbook / security / 4. Database: RLS, owner and roles

    4. Database: RLS, owner and roles

    Boundary

    PostgreSQL is the floor under every caller: a handler, a worker activity, the relay, purge, onboarding or a hand-written query. Whatever the Go code above forgets, a role connected with tenant A's setting, or with no setting, reaches 0 rows of tenant B, or an error. No runtime role can switch the floor off.

    Enforcement point

    ADR-001 invariants I1 (tenant wall in the database) and I3 (least-privilege roles):

    • Every tenant table has tenant_id, ENABLE and FORCE ROW LEVEL SECURITY, and a policy on NULLIF(current_setting('app.tenant_id', true), '')::uuid. FORCE makes the policies apply to the table owner as well.

    • Owner vs app. nava_migrator owns the schema and is granted to no one; runtime roles (nava_app, nava_worker, nava_relay, nava_purge, nava_onboard, nava_groupsync, nava_erasure, nava_audit_reader and the others) own nothing, cannot run DDL, and none has SUPERUSER or BYPASSRLS.

    • Per-service roles. db/grants.yaml lists each role's table and column grants; migrate grants exactly those and revokes anything else.

    • A policy that does not test app.tenant_id must be on the ADR-001 Annex A.3 allow-list (catalog.AllowList(), internal/db/catalog/policy.go), and has a fixed FOR, TO and predicate. Today it has 11 policies; these are the only places a role can reach rows across tenants:

      • outbox_relay_select: SELECT by nava_relay, USING (true).
      • outbox_relay_update: UPDATE by nava_relay, USING pending rows (dispatched_at IS NULL AND dead_at IS NULL), WITH CHECK (true).
      • binding_lookup: SELECT by nava_app and nava_groupsync, USING (true).
      • binding_onboard: INSERT by nava_onboard, WITH CHECK the tenant is provisioning.
      • idempotency_purge and idempotency_purge_select: DELETE and SELECT by nava_purge, USING the key is expired (expires_at < now()).
      • outbox_purge and outbox_purge_select: DELETE and SELECT by nava_purge, USING dispatched more than 7 days ago or dead more than 30 days ago.
      • workflow_ref_purge and workflow_ref_purge_select: DELETE and SELECT by nava_purge, USING closed more than 30 days ago.
      • audit_chain_head_purge_select: SELECT by nava_purge, USING the R17 predicate (shared with the chain:reseed gate).

      So nava_purge selects and deletes expired rows of every tenant. PinnedTenantPolicies() adds a state test to the tenant predicate for the onboarding and group-sync policies (for example the tenant is provisioning, or its group is tombstoned).

    • Unique keys and foreign keys include tenant_id, so a row of tenant A can never reference a row of tenant B.

    • pgbouncer.get_auth(text) is the one SECURITY DEFINER exception: the infrastructure function in db/grants.yaml, granted only to pgbouncer_auth, which returns no row for a superuser, BYPASSRLS or REPLICATION role. main has no views. The proof is CI-1 (ci1SecurityDefiner), which fails on any other SECURITY DEFINER function.

    The policy text of every table is on Row-level security, and every role's grants are on Roles and grants.

    Claim Test

    Fixture that turns it red

    TestFixturesMakeTheSuiteFail applies each fixture and requires a PASS line to turn FAIL: NO FORCE on records (caught on the owner line), RLS disabled on outbox, a fail-open policy, and a session-wide SET through PgBouncer. TestCI9FixturesMakePathsFail widens one system role's grant or policy at a time (a records column granted to the relay, a data column granted to purge, a purge policy that stops testing expiry, an onboarding policy without its state test) and requires its path to fail.

    Accepted risks

    AR-001 and AR-002 are the two High and Medium residuals of ADR-001 that touch this layer: a stolen nava-worker certificate can set any app.tenant_id, so RLS cannot stop it, and Temporal histories in the shared cluster are not encrypted.

    ID Sev Risk Status Owner Revisit trigger / proposed fix Source
    AR-001 (R8) 🔴 High† A stolen nava-worker certificate polls every tenant's tasks and histories and can set any app.tenant_id, so it reads and writes any tenant under RLS. A stolen nava-relay or nava-core certificate can start or signal for any tenant. Accepted Security reviewer Any new holder of a Temporal certificate, or per-tenant workers required ADR-001 §5
    AR-002 (R1) 🟠 Medium† Temporal histories are cross-tenant data and are not encrypted in M1. Accepted Solution Architect First regulated-data tenant, or TICK-41 decided; then a per-tenant encrypting codec ADR-001 §5
    AR-003 (R2) 🟠 Medium† The migrator is all-powerful over its tables; the backup role and backup set hold every byte, including Keycloak and Temporal if they share the cluster. Accepted Technical Lead Any request to run DDL from a runtime process, or a logical-dump requirement ADR-001 §5
    AR-029 (RS8) ⚪ Info nava_onboard, bound to tenant A, can read A’s active row (id, state, onboarding_request_hash, created_at); the signed A.3 text said provisioning only. No other row or tenant; the tenant predicate is CI-pinned. Accepted Security & Multi-Tenancy Reviewer A column is added to nava_onboard's tenants SELECT list; onboarding stops running inside InTenantTx(tenant); T21 lets the caller influence app.tenant_id (condition: server-derived only). A new tenants column is no longer a trigger: the SELECT grant is a column list, so the column stays unreadable until granted (TICK-180) ADR-001-E3 (accepted residual), RFC-004 §5
    AR-031 🟡 Low The hand-grant gate (TICK-233) fails only a run on a fresh database. A first production deploy is fresh, so a hand GRANT in a migration fails that deploy's migrator run after the grant step has revoked it; a re-run then sees an already-migrated database and passes. Fails safe: the privilege never survives, and CI (always fresh) catches the migration first. Accepted Technical Lead Production first-deploy tooling changes (for example, a deploy that does not migrate from empty or does not stop on a failed migrator run) TICK-233, security review of PR #139 and the Technical Lead's acceptance (2026-10-26)
    AR-032 🟡 Low The CI-4 grant comparison covers databases, schemas, tables, columns, sequences, functions and default privileges, not types or foreign-data wrappers. A hand grant on a type or FDW is neither revoked nor reported. Neither object reaches tenant rows. Accepted Technical Lead db/grants.yaml starts covering types or FDWs, or a migration adds an FDW TICK-233, security review of PR #139 and the Technical Lead's acceptance (2026-10-26)
    AR-041 🟠 Medium outbox_payload_check and outbox.ValidatePayload bound accidental record data (a producer bug that writes a title, an email or free text), not a deliberate encoder. Since P3-42 (TICK-711) every production kind (nava.interpreter, nava.interpreter.signal, audit.seal) has a per-kind key allow-list in Go, at Enqueue and at the relay (outbox.ValidateKindPayload), so its key words and number of keys are fixed. UUID content (122 writer-chosen bits per value) remains writer-chosen, and a kind with no allow-list (the demos, test kinds) keeps the key pattern only, so code that holds nava_app or nava_worker and bypasses Enqueue can still encode data into a Temporal history. A signal name other than nava.interpreter.signal can also still reach an interpreter run through EnqueueAtVersion: there is no signal-name allow-list and no workflow_cause row. It is inert today: the interpreter listens on no other signal, and workerguard.ResolveCause fails closed with ErrCauseNotFound for a delivery with no cause row (Security review of P3-42, Low). Revisit when any new interpreter signal channel is added. No endpoint writes outbox rows today, and a tenant token cannot reach this path. Accepted Security & Multi-Tenancy Reviewer A new production outbox kind: add its keys to kindPayloadKeys (internal/outbox/outbox.go) in the same change. Any new interpreter signal channel: add a signal-name allow-list to EnqueueAtVersion first outbox-payload-check.md, TICK-240
