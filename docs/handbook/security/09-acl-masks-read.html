    9. ACL and field masks on the read side

    Boundary

    A user of the right tenant whom the record ACL does not admit, or who may not read a masked field, learns nothing about that record or field through any read surface: get, list (filter, sort, total, cursor), history, the access explainer, or an error response. A record they cannot see answers exactly like a record that does not exist.

    Enforcement point

    internal/authz is the one authorization layer (ADR-001 I5), evaluated inside the query and in the caller's tenant transaction:

    • Rows. CompileRead turns the tenant's published policy into the WHERE of the record query, with the share EXISTS matched on tenant_id and the (kind, id) pair. canRead maps a hidden record to the missing-record 404, before If-Match, so there is no 403 or 412 oracle.
    • Fields. authz.Shape drops masked fields from every response body, including history before and after (changed is computed after shaping).
    • Queries. checkPlan (authz.CheckQueryFields) refuses a filter or sort on a masked field with a 400 before any SQL runs, so neither the result, the total nor the timing depends on the hidden value.
    • Explainer. Requires the tenant admin first, runs in the caller's tenant, and lists only masked fields the admin can read.
    • Subjects. authz.NotInTenant refuses another tenant's group or user in a policy or mask, with the same 422 as an unknown id.

    How the ACL is compiled and how masks apply are on Core: ACL and Core: field masks.

    Proving tests

    The S10 attack rows (P3-37) are registered isolation paths under CI-8, run by TestRegisteredPaths through the real handler as nava_app via PgBouncer; each row and its red mutation is in s10-acl-attacks.md.

    Fixture that turns it red

    Each S10 row was shown red by a named mutation: checkPlan returning nil gives 200 on a masked filter; canRead answering 403 fails the oracle check; no shaping puts cost into history after; the explainer's Readable filter dropped names a field the admin cannot read. Row 7 (share forgery) needs both the tenant predicate dropped and RLS off on record_shares to go red, which shows the two layers are independent.

    Accepted risks

    Errors and logs are part of the read side: AR-006 (a recovered panic value is logged as is) and AR-010 (error.type export shape) apply here.

    ID Sev Risk Status Owner Revisit trigger / proposed fix Source
    AR-006 🟠 Medium† A recovered panic value is logged as is; a panic message built from input can log client data. Accepted (untracked) Technical Lead† Give it a TODO row, or redact the panic value in recovery observability-notes §2.7
    AR-010 🟡 Low boundedToken accepts a bare UUID or single word, so a library writing a bare id as error.type would export it. None does today. Accepted Technical Lead† A library on the path writes ids into error.type; then restrict to known type and code shapes tenant-transactions.html §4, filter.go:83
    AR-TICK-653-01 (numbers issued before a mask) 🟡 Low A number format with a {field:…} token prints the field's code into every number. If that field is masked later, numbers already issued keep showing it in audit rows, outbox events, sent emails and external references; they cannot be recalled. New numbers stop carrying it because a mask on a referenced field must be published together with a format that drops it. Accepted (ADR-005, 2026-11-10; Security round 1 on RFC-014) Security & Multi-Tenancy Reviewer A tenant asks to recall issued numbers, or a regulated tenant masks a field already used in numbers ADR-005 §3.4, §8
    AR-TICK-653-02 (per-scope volume) 🟡 Low A per-scope counter (for example per branch and month) reveals the number of records in that scope to anyone who can read one record in it. Within the tenant only; the per-type counter already does the same per type. Accepted (ADR-005, 2026-11-10) Security & Multi-Tenancy Reviewer A tenant treats per-scope volume as confidential ADR-005 §8
