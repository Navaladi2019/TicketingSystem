    Handbook / security / 1. Token validation

    1. Token validation

    Boundary

    Only a Keycloak access token for the platform's API, signed by a key of a trusted issuer's own JWKS, gets past the edge. An ID token, a refresh token, a token of another realm, or a token signed with a key the attacker controls is refused before any tenant is looked up.

    Enforcement point

    keycloak.Adapter in internal/identity/keycloak/keycloak.go is the only package that imports a JWT or JWKS library (depguard and navalint, CI-11). It applies, in order:

    • iss must be on the configured allow-list (NAVA_OIDC_ISSUERS), checked before any HTTP request, so a token cannot make the service fetch from a host it names.
    • The signing key comes only from the JWKS that the issuer's own discovery document names. That jwks_uri must be on the issuer's scheme and host, under its path, and neither fetch follows a redirect.
    • alg must be RS256 and kid must be set; the key itself must be an RSA signing key for RS256 (no none, no HS256 signed with the public key).
    • exp is required; exp and nbf allow 30 s of clock skew.
    • typ must be Bearer and azp set, so an ID token is refused.
    • One audience per resolver: nava-api for tenants, nava-operator-api for operators. An operator must also be on Config.Operators, so a role mapping alone never makes anyone an operator.
    • An unknown kid forces at most one JWKS fetch per issuer per 30 s, shared by concurrent callers, so a rotated key works without a restart and an unauthenticated caller cannot drive key fetches.

    A refusal is 401 invalid_token; the error and the log carry no token or claim value.

    Attack Test

    ID token TestIDTokenRejected; CI-5.05 in TestCI5

    The live catalogue is CI-5 (TestCI5, make identity-attacks), described in identity-ci5.md.

    Fixture that turns it red

    TestKC2612FixtureOrgPickerTamperSucceeds runs CI-5.06's organization-picker tamper against the pinned negative-fixture Keycloak (26.1.2) and **requires the tamper to succeed** there, so a passing CI-5.06 on the current Keycloak means the attack is refused, not that the case cannot see it. Every row of TestVerifyMatrix that must be refused is paired with a valid control that must be accepted.

    Accepted risks

    ID Sev Risk Status Owner Revisit trigger / proposed fix Source
    AR-030 🟠 Medium The Keycloak runtime account (nava-platform, manage-users) can map the realm role nava-operator to any user. Since TICK-195 that alone grants nothing: ResolveOperator also requires (iss, sub) on the platform-config operator allow-list (TestPlatformServiceAccountCanAssignOperator), and the live check TestOperatorRoleMembersAllowListed fails on any unlisted member. Residual: a stolen runtime secret can still take over an allow-listed operator through manage-users (password and credential reset). Not reachable from a tenant token: the DirectoryAdmin adapter has no role-mapping or credential route (TestAdapterNeverMapsRoles). Accepted Security & Multi-Tenancy Reviewer Move operators to a realm the runtime account cannot reach. Revisit at the first non-local deployment, or at once if the runtime account gains a role or any runtime code path gains a role-mapping or credential call. TICK-73 (T18, PR #101) security review; allow-list TICK-195
    AR-045 🟡 Low Users created through the admin API (InviteUser) and brokered users get default-roles-nava, which includes account/manage-account. The account REST API is closed today only because the account-console client has no client scopes. If they are restored (a realm edit or a Keycloak upgrade), a user can change their own email to any address without verification, one in another tenant's domain included. Their tenant, roles and groups do not change (TestSelfServiceCannotChangeTenantRoleOrGroupAttributes, checked against an open API by hand on Keycloak 26.8.1), but a squatted address makes that tenant's InviteUser for it fail as ErrInviteRefused, which the API reports as a success. Accepted Security & Multi-Tenancy Reviewer account-console gains client scopes, manage-account is relied on, or self-service signup is added. Fix: make the user-profile email attribute admin-edit only (or turn on email verification), and drop manage-account from default-roles-nava. TICK-82 (T26, PR #153), deprovisioning-identity-boundary.md
