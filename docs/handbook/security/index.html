        Security and tenant isolation

        Threat model

        The attacker holds a valid token for one tenant (tenant A), and wants a row, a field, an id or a workflow of another tenant (tenant B). Variants of the same attacker hold tenant A's admin rights, tenant A's external IdP, or one stolen platform credential (a database login or a Temporal certificate). Every page in this section answers the same question for one layer: **which request would get tenant A something of tenant B's, and what stops it?**

        The pages follow a request from the edge to storage and then to what leaves the system. Each one states the boundary, the enforcement point in the code on main, the tests that prove it, the fixture or mutation that shows each test can fail, and the accepted risks that apply to that layer.

        How isolation is proven

        The isolation suite (internal/tenancy/isolation, make isolation, ADR-001 Annex B CI-2) seeds tenants A and B and runs every role against every tenant table, plus registered SQL, HTTP, DB, API and stack paths, as tenant A against tenant B's data. Its fixtures each break one control and must turn a PASS line into a FAIL, so a suite that cannot fail is caught. The full description is isolation-suite.md.
