    7. Identity boundary and deprovisioning

    Boundary

    A user removed from a group, or disabled, loses that access **within 10 minutes**, even while holding an unexpired token. Nobody can raise their own tenant, role or group through Keycloak self-service, a service account, token exchange or the operator role. Group sync and invitations act only inside one tenant.

    Enforcement point

    • Groups and enabled come from the database, not the token. The API reads the principal's groups and its enabled flag from the synced rows on every request (pgstore.principalSQL). Once one nava-groupsync cycle has applied a change, an unexpired token already sees it.
    • The bound (D-P9). nava-groupsync runs at most every 5 minutes (config.MaxGroupsyncInterval), and the realm's access-token lifespan is at most 300 s.
    • Group sync is per tenant. Each cycle applies one tenant's snapshot inside that tenant's transaction as nava_groupsync; a hostile snapshot that names another tenant's rows changes nothing there.
    • Keycloak. The account console and profile cannot change any attribute that feeds a tenant, role or group claim; token exchange is disabled; service accounts carry no organization; nava-operator cannot be self-assigned, and an operator must also be on the adapter's allow-list (token).
    • Operator and tenant tokens do not cross. A tenant admin's token is refused on /api/v1/operator/*; an operator token (audience nava-operator-api only) gets 401 on a tenant endpoint.

    Proving tests

    The eight T26 cases (TICK-82), one named test or registered path each:

    # Case Test
    1 A group removal takes effect within 10 minutes path T26-1 in TestRegisteredPaths (real groupsync.Syncer between two calls with one token)
    2 A disabled user's token stops working within 10 minutes path T26-2 in TestRegisteredPaths
    3 Self-service cannot change a tenant, role or group attribute TestSelfServiceCannotChangeTenantRoleOrGroupAttributes
    4 A service-account token cannot act in any tenant TestServiceAccountTokenCannotActInAnyTenant
    5 Token exchange stays disabled TestTokenExchangeStaysDisabled
    6 A tenant admin token is refused on operator routes path T26-6 in TestRegisteredPaths
    7 A user cannot self-assign nava-operator TestUserCannotSelfAssignOperatorRole
    8 An operator token on a tenant endpoint gets 401 path T26-8 in TestRegisteredPaths

    Cases 3, 4, 5 and 7 need the real Keycloak and run in make stack-test-identity; the isolation report lists them as STACK.

    Group sync and invitations across tenants: TestHostileSnapshotNeverTouchesAnotherTenant, TestTombstoneIsolatedPerTenant, TestTenantACannotReachTenantBGroups, TestDisableUserInAnotherTenantsSubtreeIsRefused, TestInviteCannotEnrolAnotherTenantsUser, TestInviteCannotSquatAnotherTenantsEmail, TestGetMeTombstonedAndDisabledPrincipals.

    Fixture that turns it red

    TestStackPathsExist fails when a stack case's named test is renamed or deleted, so the four Keycloak-only cases cannot silently drop out of the report. Cases 1 and 2 call the real handler with the same token before and after the sync cycle, and require the first call to show the group (or to succeed), so a case that never had the access cannot pass.

    Accepted risks

    ID Sev Risk Status Owner Revisit trigger / proposed fix Source
    AR-022 (R3) ⚪ Info† No tenant self-administration of Keycloak in M1; the platform API does it. Accepted CTO / the human owner Epic 26 scoping ADR-001 §5
    AR-030 🟠 Medium The Keycloak runtime account (nava-platform, manage-users) can map the realm role nava-operator to any user. Since TICK-195 that alone grants nothing: ResolveOperator also requires (iss, sub) on the platform-config operator allow-list (TestPlatformServiceAccountCanAssignOperator), and the live check TestOperatorRoleMembersAllowListed fails on any unlisted member. Residual: a stolen runtime secret can still take over an allow-listed operator through manage-users (password and credential reset). Not reachable from a tenant token: the DirectoryAdmin adapter has no role-mapping or credential route (TestAdapterNeverMapsRoles). Accepted Security & Multi-Tenancy Reviewer Move operators to a realm the runtime account cannot reach. Revisit at the first non-local deployment, or at once if the runtime account gains a role or any runtime code path gains a role-mapping or credential call. TICK-73 (T18, PR #101) security review; allow-list TICK-195
    AR-036 🟡 Low There is no way to abandon a provisioning tenant (T21). A tenant whose onboarding fails or is never retried keeps its Keycloak organization and IdP, and once bound its tenant_identity_binding and tenant_email_domain rows, so its email domains stay claimed against the real owner (see AR-035). The same holds for a tenant whose retry is refused with onboarding_conflict because its stored binding names a different org (TICK-242): it stays provisioning and only the abandon operation releases it. Nothing is exposed to another tenant; the cost is stuck domains and orphaned Keycloak objects that only a manual cleanup removes. Accepted Technical Lead An abandon operation for the operator (delete the Keycloak organization and IdP, release the rows), or the first stuck domain in practice TICK-81 (T21), Security review of PR #130, onboarding.md
    AR-038 🟡 Low The nava-groupsync service account holds view-organizations, which reads every Keycloak organization realm-wide (name, alias, domains) and every organization's members. Keycloak 26.8.1 offers nothing narrower: view-realm does not open the member-organization read, and query-organizations answers 200 with an empty list. The tenant boundary for this account is enforced in code (subtree from the tenant argument; org ids and IdP aliases from tenant_identity_binding under RLS), as it already is for its realm-wide view-users. No write on organizations, no IdP, role or flow read. Accepted Security & Multi-Tenancy Reviewer Revisit when Keycloak offers organization-scoped admin permissions (FGAP v2 for organizations), when a second caller of an /organizations path on this account is proposed, if a proxy is put in front of Keycloak on the groupsync path, or if the nava-groupsync secret is ever exposed. Guards: TestGroupsyncAccountFloor; TestKeycloakRejectsNonCanonicalOrgPaths; the admin.do organization-route allow-list on the account (the runtime account may send only GET /organizations/members/{id}/organizations, checked on the real path before the token fetch) and its unit test TestRuntimeAccountOrganizationRoutes; the secret is never the dev literal outside compose. TICK-252 Security ruling (2026-10-26, Keycloak 26.8.1 role probe); round 1 re-check (2026-10-27)
    AR-045 🟡 Low Users created through the admin API (InviteUser) and brokered users get default-roles-nava, which includes account/manage-account. The account REST API is closed today only because the account-console client has no client scopes. If they are restored (a realm edit or a Keycloak upgrade), a user can change their own email to any address without verification, one in another tenant's domain included. Their tenant, roles and groups do not change (TestSelfServiceCannotChangeTenantRoleOrGroupAttributes, checked against an open API by hand on Keycloak 26.8.1), but a squatted address makes that tenant's InviteUser for it fail as ErrInviteRefused, which the API reports as a success. Accepted Security & Multi-Tenancy Reviewer account-console gains client scopes, manage-account is relied on, or self-service signup is added. Fix: make the user-profile email attribute admin-edit only (or turn on email verification), and drop manage-account from default-roles-nava. TICK-82 (T26, PR #153), deprovisioning-identity-boundary.md
    AR-S8-01 🟡 Low Removing a user from a tenant's onboarded admin group takes effect at the next group-sync cycle (cmd/nava-groupsync, groupsync.DefaultInterval = 5 minutes), not on the next request: the resolver re-reads group_members on every request and authz.RequireTenantAdmin(Tx) checks those groups against tenant_admin_group, so the lag is at most one sync interval (5 minutes) plus the cycle's run time. Until then a removed admin keeps admin rights. The admin check keys on the stored group id (tenant_admin_group), never on a path, so a rename grants nothing. Accepted Security & Multi-Tenancy Reviewer A product need for immediate revocation, the sync interval growing past a few minutes, or sync stops running: add an on-demand sync for the admin group, or check membership against the directory on admin routes. P3-04 (TICK-342), plan-records-path.md D-3-3, grooming TICK-363
    AR-TICK-529-04 (R-E5-4) 🟡 Low When a tenant's admins (or auditors) group is revived in Keycloak, its pointer is gone, so the tenant has no admin until the pointer is re-recorded. Fails closed. Accepted (ADR-004-E5, 2026-11-04) Security reviewer A tenant reports a lockout after a Keycloak restore ADR-004-E5 Accepted risks
