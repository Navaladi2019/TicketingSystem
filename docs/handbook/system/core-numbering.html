    Core: record numbering (gaps and gapless)

    Purpose

    Every record gets a human number, <prefix><7 digits> (INC0000001), unique and increasing per tenant and entity type. Numbers come from one record_counters upsert on (tenant_id, entity_definition_id, scope_key); there is no sequence (ADR-001 I8). Every type uses the default format (numbering.Default(): {prefix}{seq:7}, scope key '') until S18 links formats to types. The format compiler is already in internal/records/numbering (see the compiler note). A type's numbering_mode picks where the upsert runs:

    • gaps (default, ADR-005 L2s): in a transaction of its own on the allocator pool, committed before the record is inserted. The counter row is locked for one round trip. A create that fails after its number leaves a **gap by design**.
    • gapless (ADR-005 L1): last in the create's own write batch, so a rollback gives the number back, at the cost of holding the counter lock until the create commits.

    The decision and its rules are in the normative ADR-005 and the numbering section of record-write-pipeline.md.

    Entry point

    • write.create in internal/records/pipeline/pipeline.go reads Compiled.NumberingMode() and calls write.allocate (alloc.go) for a gaps type.
    • PoolRunner.Allocate -> tenancy.AllocTx -> store.QueueAllocate (internal/records/store/numbering.go).
    • gapless: store.QueueInsertNumbered in write.writeCreate (batch.go).
    • Mode change: entitytypes.Store.SetNumberingMode.
    • Format: write.format returns numbering.Default(); its ScopeKey() is the upsert's third key.
    • First-create race: store.CounterRace, retried once in PoolRunner.Allocate and, for gapless, after a savepoint in the batch (ADR-005-E1).
    • Pool wiring: cmd/nava-core/allocator.go (NAVA_ALLOCATOR_DATABASE_URL).

    Errors

    Error HTTP
    a second 23505 on the counter after the one retry, gaps 500 internal_error, nothing committed but possibly the number (a gap)
    a second 23505 on the counter after the one retry, gapless 500 internal_error, the create rolls back and gives the number back: no gap (batch.go:257)
    ErrRetryable (allocation past its timeout) 503 retry_later, nothing committed but possibly the number (a gap)
    allocation not this create's (tenant, type, scope, epoch) 500 internal_error (a bug, never expected)
    entitytypes.ErrInvalidNumberingMode refused before anything is written

    Notes

    • Metrics: nava_numbering_alloc_acquire_seconds, nava_numbering_alloc_seconds, nava_numbering_alloc_timeouts, and nava_numbering_first_create_retries (first-create races retried, with a mode attribute: gaps or gapless; no tenant or type attribute).
    • Story: S17.
    • Measured create latency under both modes: benchmarks page.
