        Handbook / database / Tenancy

        Tenancy

        tenants is the root of every other table. It is the one table whose tenant key is id, not tenant_id, so its policies test id against app.tenant_id. Every other table points at it, directly or through a composite key. Every composite key starts with tenant_id, so a foreign key cannot point at another tenant's row.

        A tenant starts as provisioning and becomes active. Onboarding (nava_onboard) inserts the row and moves it to active. Its pinned policies (see RLS) let it write the tenant only while the tenant is provisioning, and only for the tenant in app.tenant_id. onboarding_request_hash makes a repeated onboarding request idempotent.

        Tables

        tenants

        Kind: table. Row-level security: enabled true, forced true. Primary key: id.

        Audit: exempt from the audit log: Tenant lifecycle, written by onboarding. R2 has no tenant subject type; the epic that audits onboarding registers one (I8).

        Column Type Null Default
        id uuid no -
        state text no -
        onboarding_request_hash bytea yes -
        created_at timestamp with time zone no now()
        Index Method Columns Include Predicate Design note
        tenants_pkey (unique) btree id - - identity

        Policies with exactly the tenant predicate on id (RLS): tenants_onboard_select (SELECT, nava_onboard), tenants_tenant (SELECT, nava_app).

        Policy Kind Type Command Roles Using Check
        tenants_activate pinned permissive UPDATE nava_onboard ((id = (NULLIF(current_setting('app.tenant_id'::text, true), ''::text))::uuid) AND (state = 'provisioning'::text)) ((id = (NULLIF(current_setting('app.tenant_id'::text, true), ''::text))::uuid) AND (state = 'active'::text))
        tenants_onboard_insert pinned permissive INSERT nava_onboard - ((id = (NULLIF(current_setting('app.tenant_id'::text, true), ''::text))::uuid) AND (state = 'provisioning'::text))

        Grants (db/grants.yaml, roles and grants): nava_app SELECT (id, state); nava_onboard SELECT (id, state, onboarding_request_hash, created_at); nava_onboard INSERT (id, state, onboarding_request_hash); nava_onboard UPDATE (state).
