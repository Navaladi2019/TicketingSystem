                    Handbook / database / Roles and grants

                    Roles and grants

                    db/grants.yaml is the only place a privilege is granted. Two jobs read it: db-roles, as the bootstrap superuser, creates each role with exactly the attributes listed (always NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS) and revokes any membership; migrate, as nava_migrator, grants what each role lists and revokes, and logs, anything else on an object it owns, PUBLIC included. The database itself starts with REVOKE ALL ... FROM PUBLIC (00001_global_revokes.sql).

                    A grant decides which columns a role may touch. Row-level security decides which rows: every table is under FORCE ROW LEVEL SECURITY, so a grant here reaches only the rows its policies allow.

                    Column lists matter. UPDATE never includes a key or a column that is set once at insert, so a record's number or a group's identity provider id cannot be rewritten. Only nava_audit_reader may read audit_log.diff and diff_salt (ADR-004-A1).

                    Infrastructure exceptions

                    Name Object Security definer Granted to Reason
                    pgbouncer_get_auth pgbouncer.get_auth(text) true pgbouncer_auth PgBouncer's auth_query reads pg_shadow, which only a superuser can. The function returns a row only for roles with pgbouncer_login: true, and never for a superuser, BYPASSRLS or REPLICATION role.

                    Audited and exempt tables

                    Every tenant table is either audited, with a commit-check trigger that makes a write fail unless it wrote its audit entry in the same transaction, or exempt with a reason (db/audited-tables.yaml, ADR-004 R12). The gate fails on a table that is neither.
