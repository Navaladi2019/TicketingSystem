    Handbook / database / Numbering

    Numbering

    record_counters holds one row per (tenant_id, entity_definition_id, scope_key): the next record number of that type in that scope. Today every row has the default scope '', so there is still one counter per type. A record takes its number with one upsert, INSERT ... ON CONFLICT (tenant_id, entity_definition_id, scope_key) DO UPDATE SET next, so next is the only column a role may update; the insert arm sets scope_key and period_end.

    The type's numbering_mode (ADR-005) decides when the number is taken. A gaps type takes it in its own short transaction before the create, so a failed create leaves a gap. A gapless type takes it inside the create transaction, so a rollback gives the number back. The table is exempt from the audit log, because the record insert that takes the number is audited.

    Scope key and period end (S17, release R1)

    Four migrations, all online (runbook: record-counters-scope-key.md):

    • M1 adds scope_key text NOT NULL DEFAULT '' and period_end timestamptz NULL, plus record_counters_scope_key_len (at most 128 characters), added NOT VALID and validated by the next migration. Existing rows read ''.
    • M2 builds record_counters_scoped_key, a unique index on (tenant_id, entity_definition_id, scope_key) that the upsert names as its arbiter, and record_counters_period_end, a partial index on period_end IS NOT NULL that the purge job will read. Both are built CONCURRENTLY; the partial index stays empty until S18 publishes period formats.
    • The primary key is still (tenant_id, entity_definition_id). Until M3 (S18, release R2) both unique indexes exist, so the pre-S17 build still runs and a rollout with mixed binaries works for existing counters.
    • A type's first create can lose a race for its counter row with 23505 on the index the upsert does not name (ADR-005-E1). R1 retries once. The pre-S17 build has no retry (accepted risk AR-S17-01).
    • M3 is the point of no return. After it the pre-S17 build can never be deployed again, and there is no rollback past it. Rolling back the S17 schema before M3 is goose down-to 20261112192959, only once no R1 replica serves.

    record_counters

    Kind: table. Row-level security: enabled true, forced true. Primary key: tenant_id, entity_definition_id.

    Audit: exempt from the audit log: Record-number counter (D-3-9); the record insert that takes the number is audited.

    Column Type Null Default
    tenant_id uuid no -
    entity_definition_id uuid no -
    next bigint no -
    scope_key text no ''::text
    period_end timestamp with time zone yes -
    Foreign key Columns References On delete
    record_counters_entity_definition_fkey tenant_id, entity_definition_id entity_definitions (entity-definitions) (tenant_id, id) NO ACTION
    Index Method Columns Include Predicate Design note
    record_counters_period_end btree period_end - period_end IS NOT NULL record-counters-scope-key
    record_counters_pkey (unique) btree tenant_id, entity_definition_id - - platform-tables, record-counters-scope-key
    record_counters_scoped_key (unique) btree tenant_id, entity_definition_id, scope_key - - record-counters-scope-key

    Policies with exactly the tenant predicate on tenant_id (RLS): record_counters_insert (INSERT, nava_app, nava_worker), record_counters_select (SELECT, nava_app, nava_worker), record_counters_update (UPDATE, nava_app, nava_worker).

    Grants (db/grants.yaml, roles and grants): nava_app SELECT; nava_app INSERT; nava_app UPDATE (next); nava_worker SELECT; nava_worker INSERT; nava_worker UPDATE (next).
