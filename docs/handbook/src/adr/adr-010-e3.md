## Problem

The onboard default `incident` rule (`assignment_group_id in caller: my_groups`) always rendered `= ANY($n::uuid[])`, even for a caller in one group. On PG 16 an `= ANY` on a non-first index column makes the `records_list_group` scan unordered, so the band (ii) page read 20,137 rows and sorted: 61.3 ms instead of 0.99 ms, and the ≥ 40% ACL cell missed 350 ms p95 (TICK-1049). CI-6, as amended by E1, forbade the text change.

## Decision

| # | One line |
|---|---|
| E3-1 | Rewrite (c) is allowed: `caller: my_groups` for a caller with exactly one group renders `= $n::uuid` with a `uuid.UUID` argument, everywhere that condition renders. |
| E3-2 | Narrow scope: zero groups stays fail-closed, two or more stay `= ANY`, literal lists stay `= ANY`, `record_shares` unchanged. |
| E3-3 | The golden normalizes (c) only for that column, caller and argument, records which rewrite applies to which case, and is not regenerated. |
| E3-4 | Same visible rows and order; tested by unit, real-PostgreSQL equivalence, and two pair-level I5 coverage keys. |
| E3-5 | The plan test asserts no Sort between the group scan and the branch `Limit`, and fewer than 10% of the group's rows read. |
| E3-6 | Nothing else in ADR-010 or E1 changes. |

## Residuals

`AR-TICK-1085-01` in [accepted risks](../security/accepted-risks.md): callers in two or more groups keep `= ANY` and the read-and-sort plan. Expected to exceed the 20.6 ms page budget above about 6,800 matching rows; TICK-1084 measures it. Latency only.
