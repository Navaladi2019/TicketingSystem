## Problem

A1 says `make vulncheck-temporal-server` is a required `ci.yml` step. Since 10 November it ran in `govulncheck.yml`: every second day, by hand, and on pull requests that changed `go.mod` or `go.sum` of either module. The `root` scan was not a required check of `main`. The `temporal-server` scan shared its name with the required `ci.yml` job that tests the Authorizer. E4 assumed GitHub counts the green one. The shared name was removed by PR #900 (2026-11-25), and TICK-1146 showed a later run does replace a red check (PR #902), so neither scan reliably blocked until FU2.

## What is built

- Every pull request runs `vulncheck-detect`; there is no `paths` filter.
- The module scans (`vulncheck-root`, `vulncheck-temporal-server`) run only when detect asks for them: a module's `go.mod` or `go.sum` scans that module; `govulncheck.yml`, its copy, the two scripts, `tools/ci/cisteps/`, `tools/ci/checkpins/`, a `FROM golang:` line or a `go.work` scans both; anything else scans neither.
- The gate (`if: always()`) reports `vulncheck` on pull requests into `main`, and `vulncheck-other` on any other base.
- Detect and the gate run the scripts as they are on `main`, not the pull request's copy.
- `vulncheck` is a required check of `main` since 2026-11-27 (TICK-1154). Test V-4 showed a red scan `BLOCKED` (TICK-1155).
- The schedule and a manual run scan both modules. A red scheduled run opens or updates its own `govulncheck is red: <short sha>` issue (TICK-1152); issue #259 is closed.
- `make check-ci-steps` compares the whole workflow with `tools/ci/cisteps/govulncheck.copy.yml`. `make check-pins` fails when a module's `toolchain` differs from a `FROM golang:` of that module, or when a `go.work` is tracked (`TestScannedToolchainIsTheShippedToolchain`, V-5). See [Go toolchain and setup](../operations/go-toolchain.md).

The full pipeline description is in `docs/quality/ci-pipeline.md`.

## Decision

| # | One line |
|---|---|
| E4-1 | Decision 3 is reworded to what is built. Zero findings, no exception: unchanged. |
| E4-2 | A library update that clears a finding is an ordinary bug fix after a green `ci:full` run, unless it moves a Temporal pin, changes an Authorizer golden file or uses `replace`, `exclude` or a fork (triad), or moves a trust-path library (Security review). The scanned Go must equal the shipped Go. |
| E4-3 | Until FU2, the agents' rule stopped a merge: each job `success`, `skipped` or missing is red. FU2 is done (2026-11-27): the required check `vulncheck` now blocks. |
| E4-4 | A new job `vulncheck` always reports and becomes required. It carries that name only on pull requests into `main`. Contract: `docs/adr/ADR-001/E4/vulncheck-contract.md`. |
| E4-5 | No two workflows report the same check name (done by TICK-1145, PR #900). |
| E4-6 | The two-day schedule stays (the owner's decision). |

## Options that lost

Not required, as today; required with the `paths` filter kept; a scan on every pull request; a conditional job in `ci.yml`; scanning both modules on any library change; a list of required names; a copy of the `jobs:` block only; no pull request scan; no erratum.

## Accepted risks

AR-TICK-1140-01: a new flaw can stay unseen on `main` up to about 50 hours. AR-TICK-1140-02: a red scan could be merged; closed by FU2 (2026-11-27), kept for the audit trail. AR-TICK-1140-03: a pull request can edit the gate that judges it.
