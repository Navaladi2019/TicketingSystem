## Problem

A1 says `make vulncheck-temporal-server` is a required `ci.yml` step. Since 10 November it runs in `govulncheck.yml`: every second day, by hand, and on pull requests that change `go.mod` or `go.sum` of either module. The `root` scan is not a required check of `main`. The `temporal-server` scan shares its name with a required `ci.yml` job, so GitHub marks both as required, and which one decides when they differ is not known.

## Decision

| # | One line |
|---|---|
| E4-1 | Decision 3 is reworded to what is built. Zero findings, no exception: unchanged. |
| E4-2 | Until the follow-ups land, the agents' rule that every job is green is what stops a merge on a red scan. |
| E4-3 | The pull request scan becomes a required check through a job `vulncheck` that always runs and reports. It scans only the module whose library list changed. |
| E4-4 | No required check name is used by two workflows; `make check-ci-steps` enforces it. The scan jobs are renamed. |
| E4-5 | The two-day schedule stays (the owner's decision). |

## Options that lost

Not required, as today; required with the `paths` filter kept; a scan on every pull request; a conditional job in `ci.yml`; scanning both modules on any library change; no pull request scan; no erratum.

## Accepted risks

RS1 (AR-TICK-1140-01): a new flaw can stay unseen on `main` up to about 50 hours. RS2 (AR-TICK-1140-02): until the follow-ups FU1 and FU2, a red scan can be merged. RS3: a base-branch change starts no new check. RS4: a pull request can edit the workflow that judges it.
