## Problem

[ADR-005](adr-005.md) §3.5 says what happens under `overflow: refuse`. A create whose counter no longer fits the `{seq:N}` width fails with 409 `number_space_exhausted`, and that refusal must be audited. But ADR-004 R2 is a closed list of actions, and none of them fits a refused create.

## Decision

- R2 gains the action `number_space_exhausted`. There is no new subject type, no new envelope column and no new index.
- **R2b:** each refused create writes exactly one entry.
  - Domain `record`; subject `entity_definition` / D, the type the create targeted.
  - Both versions are NULL.
  - The refused command's actor, source and request id.
  - `diff` is one `add` of `/number_space` with four keys: `{epoch, scope_key, width, counter}`.
  - The entry never carries the attempted record data, the field values or the idempotency key.
- **Placement (CTO ruling, spike S1):**
  - The entry is written in a transaction of its own, on the caller's (API) pool, after the refused create's transaction has ended.
  - It is never written on the allocator pool, and never while a create transaction is open.
  - The append runs on `context.WithoutCancel`, bounded by the request's deadline, so a client that disconnects does not drop the entry.
- If the append fails, the request returns the refusal joined with the audit error. A refusal is never reported as a success.
- Two migrations widen the action CHECK:
  - **A** re-adds it `NOT VALID`, a catalogue change of about 2 ms.
  - **B** runs `VALIDATE` under `ShareUpdateExclusiveLock`.
- **Budget rule** ([budgets](../../../../docs/budgets.md)): only allocations run on the allocator pool. The one known exception is `rejectTooDeep`'s `cascade_too_deep` row (RS-E9-3).

## Why this placement

Spike S1 put the row on the 4-connection allocator pool and retried refused creates. In 1 of 7 reps, another tenant's allocation p95 reached 114 ms, 32× its baseline. With the row on the API pool after the rollback, that tenant stayed at its baseline in 5 of 5 reps.

## Residuals

- **RS-E9-1:** a client that keeps retrying writes one row per attempt.
- **RS-E9-2:** a field masked later still shows its code in earlier rows. This is covered by the widened AR-TICK-653-01.
- **RS-E9-3:** `rejectTooDeep` still uses the allocator pool.
