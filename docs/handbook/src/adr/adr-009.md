## In plain words

When a tenant admin publishes a version of a record type that gives a field a default value, a background job writes that value into every existing record that lacks it. Until the job ends, searches already count the default as a match. A field that must be unique can no longer have a default.

Today an old record shows the default when you open it but does not appear when you filter on that value, and nothing ever fixes old records that nobody edits. After this ADR, right after publishing "priority defaults to 3", a filter on priority 3 finds the old records too; the record type's page shows the job's progress; when the job ends every record has priority 3 stored and one audit entry for the change, and its "last updated" time has not moved.

Deviations recorded during the build (PLAN-010 decisions, not ADR changes):

- **C3 payload (D-10-10).** The outbox payload is `{entity_definition_id}` only, because `outbox_payload_check` admits UUID values. The version is in `target_seq` and the dedupe key; the causation audit id is on the job row. The workflow input is the relay's `Delivery`; the job is parsed from the workflow id.
- **Publish writes the job (D-10-11).** `nava_app` gets INSERT on `schema_backfills` only, under a pinned policy that admits a fresh `pending` row of its own tenant. ADR-009's grants line contradicts D1 here and needs an erratum.
- **D13 error code.** The refusal is `422 invalid_definition`, the code this endpoint already uses for compile refusals. `invalid_schema` does not exist.
- **Job audit entries.** "Started" and "finished" are domain `config`, action `update`, subject the entity definition, following the numbering-mode precedent, not new audit actions.

## Decision

*Paraphrases: "Decision".* The job reuses the platform's one checked write path (I4) for every record, so validation, version bump and audit all still happen. It is tenant-scoped by its workflow id, not by an argument, and runs as `nava_worker` with no new role and no `BYPASSRLS`.

| # | One line |
|---|---|
| D1 | A publish that adds any top-level default inserts, in the same transaction, a `schema_backfills` job row and a `schema.backfill` outbox row. |
| D2 | The relay starts the workflow as `t:<tenant_id>:schema.backfill:<def>:<version>`; activities take the tenant from the workflow id. Start-only, relay-only, no new DB role or RLS allow-list entry. |
| D3 | Each record goes through `pipeline.Write(OpMaterialize)` with an empty patch; if applying defaults changes nothing, there is no write. |
| D4 | One audit entry per rewritten record, plus one at the job's start and one at its finish. |
| D5 | `version` +1 (the ETag changes), `schema_version` moves to current, `updated_at` is kept. |
| D6 | `OpMaterialize` starts no `on_updated` workflows, signals nothing and writes no outbox rows. |
| D7 | A queue table, `schema_backfill_pending`, filled after the ADR-006 D9 barrier; one short transaction per record, no row lock, no savepoints; failures go to `schema_backfill_failures` (id and code only). One job per tenant at a time, at most 4 tenants per worker pool. |
| D8 | No lock on `entity_definitions`; a newer publish supersedes a running job, which drops its queue and ends. |
| D9 | A record that cannot be rewritten never blocks the type; it still matches filters through the failures table. |
| D10 | `GET /entity-types/{key}` gains a `backfill` object (state and counts); a new admin-only `GET …/backfill/failures`. |
| D11 | Every surface that returns a record body shows the effective value: current defaults applied, then field masks. Audit diffs show stored bytes. |
| D12 | While the window is open, filters on a defaulted field also match records that lack the field: an `OR` shape while the queue is filling or more than 1,000 remain, a `UNION ALL` over the queue and failures at 1,000 or fewer. The ACL is in every branch. |
| D13 | Compile refuses `default` together with `x-nava-unique` (built as `422 invalid_definition`). |
| D14 | Making an existing property required is `needs_backfill`, not Breaking, when the next version gives it a default. |
| D15 | A one-time rollout migration queues a job per tenant and type that already has a default, and skips types that already combine a default with `x-nava-unique`. |

**Measured cost** (spikes): about 7.3 ms and 4 KB of WAL per rewritten record; live-write p95 rose 1.7% at 20k records, against 28% for the rejected batch-lock design. The 100k run is the CI-12 test in S29.

## Options that lost

| Option | Why |
|---|---|
| Batches of 100 under `FOR UPDATE SKIP LOCKED` (RFC rev 0) | +416% live p95 and 73 conflicts at 100k; livelock on a database error; savepoints overflow the subtransaction cache. |
| `FOR SHARE` on `entity_definitions` | Refused for `nava_worker` (`42501`); needs a new grant and delayed a publish by 3–8 s. |
| Never backfill; compute effective values in every query | A permanent cost no index can help, and defaults copied into plpgsql. |
| Bulk `UPDATE` from a migrator job | Bypasses I4 (validation, version, audit) and puts an operator credential on a tenant action. |
| Lazy only, stored-only filters; or refuse filters while the job runs | The first is the bug; the second is unusable on large types. |

## Competitive Gate

**PASS.** Axis X2 (change and upgrade cost): adding a defaulted field to a type that already has records becomes one publish, with no admin follow-up and no platform staff. It avoids pain point CP-SF-02 (tenant-written batch code to backfill). Invariants I1–I9 are unchanged.
