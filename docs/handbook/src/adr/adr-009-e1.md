## Problem

D13 said that publishing a field with both `default` and `x-nava-unique` answers 422 `invalid_schema`. That code was never registered. The error catalogue (`api/errors.yaml`, `internal/platform/problem/problem.go`) has one code for a rejected entity definition: `invalid_definition`. The S29 acceptance kit (TICK-754) failed criterion 4 only on that string.

## Decision

| # | One line |
|---|---|
| E1-1 | D13 reads: 422 `invalid_definition`, `errors[].pointer` = `/definition/schema/properties/<name>/default`, `rule` `invalid`. |
| E1-2 | The same answer on `publishEntityTypeVersion` and `createEntityType` (both compile through `metadata.CompileNew`). RFC-021 D13 and CI-9 are read the same way. |
| E1-3 | S29 criterion 4 and the kit (`S29-5.bru`) say `invalid_definition` and assert the pointer. |
| E1-4 | `invalid_schema` is not added to the catalogue. |

## Options that lost

Register `invalid_schema` and change the code; keep `invalid_schema` as an alias of `invalid_definition`.

## Accepted risks

None. The response carries a pointer and a rule, never a field value. I1–I9 are unchanged.
