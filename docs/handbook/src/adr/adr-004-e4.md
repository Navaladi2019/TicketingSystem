*Paraphrases: "Decision", "Verdict table".*

## Problem

On one commit, the same CI job read 129.5 µs and 190.9 µs on two GitHub-hosted runners against a 175 µs ceiling, with the same-run ratios unchanged. Absolute ceilings measured on shared hosts produced red builds that were not regressions.

## Decision

The `commit-check-budget` job keeps measuring both rows as E3 defines them. Only the verdict rule changes.

- Absolute ceilings (per call and per import probe) become review thresholds: going over emits a warning annotation and the job stays green.
- The job fails on any of: a missing or non-positive measurement, a same-run ratio out of range, or a clause arm that is not flat across sizes.
- Every run logs its numbers and the host CPU model, and writes both rows to the step summary. Baselines in `docs/budgets.md` record the CPU model.
- The old "re-run" verdict is removed; that case is now a warning.

## Accepted risks

E4-R1: a regression that slows the clause and the same-run reference equally keeps the ratios in range and passes. The cue to look was later reworded by [ADR-004-E6](adr-004-e6.md).
