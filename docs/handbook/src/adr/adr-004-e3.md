## Problem

The commit-check trigger probes `audit_log` once per subject at COMMIT. Under PostgreSQL's default plan caching, a pooled backend switches to a cached generic plan that is a sequential scan on a young partition and keeps it. A later import of thousands of subjects then costs quadratic time at COMMIT (2.9 s at 4,000 subjects), and the single-subject path decays too.

## Decision

- The commit-check function carries `SET plan_cache_mode = force_custom_plan`, so every probe is planned with its own values and no plan outlives the call. A session setting cannot override it.
- The probe reads only plpgsql locals, never `NEW.<col>`, so bound values appear as constants in the plan.
- CI-A3 checks the function's catalogue settings for the new option.
- The performance tests check the plan that actually runs at COMMIT, not a prepared generic plan.
- The budget row of 100 µs per call is replaced by two rows measured against 38 partitions: single subject must stay flat across sizes (max/min under 1.5) and import per probe has its own ceiling. Same-run ratio limits guard against runner noise.
- Rollout is one normal migration, before any table attaches the trigger.

Scope is one function, one migration and one catalogue check; no schema, grant, policy, role or database setting changes.
