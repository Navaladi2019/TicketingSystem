*Summary. The normative text is the linked `.md`.*

## Problem

R's count (`LIMIT 1001`, no order) could be a Seq Scan of all of `records` when one tenant holds about half the table or more. PostgreSQL priced only the part it expected to read before 1,001 matches. At m = 0 it read the whole table, including other tenants' rows. Page plus count then reached 162 to 178 ms of SQL.

## Decision

| # | One line |
|---|---|
| A4-1 | `records_list_updated` is rebuilt online with `INCLUDE (org_unit_id)`, under the same name. |
| A4-2, A4-3 | The count's text and the page are unchanged; there is no Go change. |
| A4-4 | Fallback: if a pin shows no Index Only Scan, the R arm gets `ORDER BY r.updated_at DESC, r.id DESC`, only in counts with at most one R arm. |
| A4-5, A4-6 | Plan pins: an IOS whose `Index Cond` starts at `tenant_id`, with rows read ≤ the tenant's rows of the type. A 1.3× node-run-cost guard. Mutant `r_count_no_covering`. A CI world that is red today. |
| A4-7 | A2-R4 reworded for generic plans. |
| A4-9 | New register row AR-TICK-1143-01 (Low). |

## Evidence

- **Warm count:** today 86–170 ms; ordered 61–80 ms; **index 17–28 ms**.
- **Cold count:** today 1.1–1.7 s; ordered 9.0–10.2 s; **index 18–25 ms** (Technical Architect).
- **Cost:** the index +23 %; WAL +1.0 to 1.5 % (Postgres & Data Modeling Specialist).

## Residuals

- **A4-R1:** AR-TICK-1143-01. See [accepted risks](../security/accepted-risks.md).
- **A4-R2:** a filter the index does not hold reads the table rows, as today.
- **A4-R3:** the first cold region list before A2-4 is in `main`.
- **A4-R4:** the size and write cost, and the build time at production size.
- **A4-R5:** an R arm that carries another branch's negation is not an IOS.
- **A3-R2:** rewritten.
