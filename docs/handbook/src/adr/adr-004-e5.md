*Paraphrases: "Context", "Decision" D1 to D11.*

## Problem

`records.assignment_group_id` was `ON DELETE SET NULL` from `groups`. When group sync deleted a group, PostgreSQL itself rewrote the records as the table owner, bypassing the write pipeline: no version bump, no audit entry, no outbox event. The commit-check trigger refused that write at COMMIT, so group sync, deprovisioning included, stalled whenever a record named the deleted group.

## Decision

- **Tombstone groups.** `groups` gains `deleted_at`. Sync never deletes a group row; a returning group is revived on the same platform id. The sync role loses DELETE on `groups`.
- **R29.** Every foreign key referencing an audited table must use NO ACTION or RESTRICT; CI checks it from the catalogue. `records_assignment_group_fkey` becomes `RESTRICT`.
- **Readers.** Sync's own diff read and the policy subquery see tombstoned rows; user-facing readers (such as `/me` group paths) filter them out.
- **Admin and auditor pointers** are deleted in the same transaction when their group is tombstoned, with matching narrow DELETE grants and policies.
- **Pipeline.** A write that changes `assignment_group_id` to a tombstoned group is refused with 422 `assignment_group_removed`; an unchanged value passes. Records keep the reference and read models mark it `removed: true`.
- **Database guard.** A generated `live` column and composite foreign key make the database refuse members in a tombstoned group, for every role.
- **No secrets in records.** R6 applies to record payloads: a value at an `x-nava-secret` or `writeOnly` path is refused with 422 `audit_secret_in_diff`. There is no "store and mask" mode. Publishing a record definition that requires a marked property is refused.
- **Migration order:** expand first, contract only after the new binaries run everywhere.
