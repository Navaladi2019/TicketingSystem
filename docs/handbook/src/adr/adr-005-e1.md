## Problem

ADR-005 said that between M2 (the 3-column unique index is built) and M3 (it becomes the primary key) old and new binaries coexist. That holds for **existing counter rows only**. `INSERT ... ON CONFLICT (cols)` absorbs a conflict only on the index its target names. While the table has two unique indexes, two first upserts for the same tenant and type can race: the loser waits for the winner, then fails with `23505` on the index it did not name. Measured with 8 workers: 15,533 failures of 160,000 for the pre-S17 build and 19,829 for R1. Nothing is duplicated; the caller sees a refused create.

## Decision

- **R1 retries once** on `23505` for `record_counters_pkey` or `record_counters_scoped_key`. A `gaps` type retries in a fresh allocation transaction. A `gapless` type opens its batch with a savepoint, rolls back to it and re-sends the whole batch. The retry is sound at READ COMMITTED only; no role or database default may raise the isolation level for `nava_app`.
- The retry and the savepoint are removed with M3 (S18).
- A concurrent first-create test pins it; the runbook says to run M3 soon after R1 is fully rolled out.

## Rejected

Creating counter rows in advance (against D-3-9), shortening the window alone, and retrying until success.

## Accepted risk

AR-S17-01 (Low): while the pre-S17 build still serves, its first create of a type can fail with `23505`. Closed by M3.
