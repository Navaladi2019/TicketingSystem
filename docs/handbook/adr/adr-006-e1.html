    Summary. The normative text is the linked docs/adr/ADR-006-E1-d9-barrier-waits-past-xmax.md.

    In progress: not on main yet

    ADR-006-E1: the D9 barrier also waits on running xids at or above xmax

    Status: ACCEPTED, rev 2, 2026-11-19 (Solution Architect verdict, TICK-977). Two Technical Architect critiques found the correction sound. Their non-blocking points were taken in rev 1 and rev 2. Nothing was contested, so no CTO tie-break was needed. The E1-3 test merged in PR #743 before the verdict. Erratum to ADR-006 D9. Normative text: the E1 record; explainer: E1-explained.html. Spike: e1-newest-xid. The page is in-progress because ADR-006's implementation is not on main yet. The fix is implemented in PR #738 (TICK-745), on the story branch.

    Paraphrases: "What was wrong", "Correction", E1-1 to E1-5.

    Problem

    D9 says the snapshot barrier waits on pg_snapshot_xip of one pg_current_snapshot(). A snapshot's xmax is one past the highest completed xid, and xip lists only in-progress xids below xmax. When the writer holding the newest assigned xid is still running, xmax equals that xid and xip does not list it, so the barrier does not wait for it. That writer's record can then reach ready with no side row: the CI-5 R1 failure D9 exists to prevent. Reproduced twice: 1869:1869: in the TICK-745 integration run, and 731:731: in the Solution Architect's spike on PG 16.10.

    Decision

    • E1-1 Wait set = xip ∪ in-progress xids in [xmax, M). In one transaction the activity takes pg_current_snapshot() and then a fence xid M = pg_current_xact_id(), and rolls back. The range is usually small, but subtransactions make it unbounded (the TA spike measured 100,001 xids for one writer holding 100k savepoints), so the heartbeat may keep the bounds (xip, xmax, M) instead of the list. Waiting on xids assigned between the two statements is conservative, never wrong. It costs one xid per barrier attempt. On a hot standby the fence raises an error, so the barrier fails closed. Implemented in internal/fieldindex/backfill/activities.go (snapshotSQL, fenceSQL), PR #738.
    • E1-2 READ COMMITTED is a precondition. Xids above M are safe only because records writers run at READ COMMITTED and the D4 trigger is an AFTER ROW trigger (the writer's xid exists before it runs) that reads the registry with a fresh statement snapshot. No records write path may raise its isolation level, and operators must not set default_transaction_isolation above READ COMMITTED for nava_app or nava_worker (same rule as ADR-005-E1).
    • E1-3 Regression test. This is a direct newest-xid test: xmax equals the writer's xid and xip is empty, the barrier does not return until the writer commits, and the test fails with the fence removed. It is TestBarrierWaitsForTheNewestXID in PR #743 (TICK-976): red with the fence removed, green with it.
    • E1-4 Removal uses the same barrier (D11 step 2 via fieldindex.Barrier, TICK-750).
    • E1-5 The precondition fails closed. The first statement of record_field_values_sync() raises a class-25 SQLSTATE naming ADR-006-E1 when transaction_isolation is not read committed. It ships as a follow-up migration with an integration test (RR insert refused, RC insert accepted). A catalogue test pins the trigger as AFTER ROW and checks that no other records trigger reads record_index_fields.
    • Not changed: D4, D10, D11, R11; I1, I4, I7, I8; no new grant, still nava_worker; no tenant data in the wait set, heartbeat or metric.

    Options that lost

    Keep xip only (proven to miss the newest writer). Scan [xmin, M) (grows with the oldest open transaction). Read pg_stat_activity.backend_xid (needs pg_read_all_stats, and still needs a fence). Have the trigger take a lock that the flip waits on (a lock on every records write; ADR-006 D4 already rejected write-path coordination).

    Accepted risk

    ID Sev Risk Status Owner Revisit trigger / proposed fix Source
    AR-TICK-745-01 (field-index barrier assumes READ COMMITTED writers and an AFTER ROW sync trigger) 🟡 Low The ADR-006 D9 barrier (as corrected by E1) waits on the snapshot's xip plus in-progress xids in [xmax, fence). Xids after the fence are safe only because records writers run at READ COMMITTED, and the D4 trigger is AFTER ROW and reads the registry with a fresh statement snapshot. Each of these could write a record across a flip without a side row: a records write path at REPEATABLE READ or above, a role or database default_transaction_isolation at REPEATABLE READ or above, or a state-reading BEFORE ROW trigger on records. The result is a mis-filter within the same tenant, with no cross-tenant effect. No runtime detector exists; only the CI-4/CI-5 harness checks side rows. Until E1-5 ships, this is an operator and code-review rule. E1-5 (trigger guard plus catalogue test, follow-up) turns a higher isolation level into a refused write and pins the trigger timing. Residual gap after E1-5 (TICK-979 security review, PR #746): the catalogue test reads only each records trigger function's own prosrc, so it cannot see a registry read made through a helper function that a trigger calls. No trigger does this today. Accepted (ADR-006-E1, 2026-11-19) Technical Lead A proposal to raise isolation on a records write path, a change of D4 trigger timing or a new state-reading trigger on records, a records trigger that calls helper functions (then make the catalogue check follow pg_depend / called functions), or an E1-5 guard error in logs ADR-006-E1
