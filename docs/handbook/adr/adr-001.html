    ADR-001: Platform blueprint

    Status on main: ACCEPTED, 2026-10-15, approved by the product owner. Changing an invariant or a decision now needs a superseding ADR signed by the product owner.

    Normative text: ADR-001-platform-blueprint.md. Plain-language explainer: ADR-001-explained.html (source ADR-001-explained.md). Supporting material, not summarised here: rfc/ and spikes/.

    Each section below names the ADR heading it paraphrases. Where wording matters, read the original.

    Problem

    Paraphrases: "1. Invariants", "TICK-2 gap coverage".

    A multi-tenant ticketing platform must keep one tenant's data away from every other tenant on every path: the database, the identity provider, the workflow engine and the API. ADR-001 fixes the rules every later design has to keep, and four decisions that make them real.

    The invariants

    Paraphrases: "1. Invariants". Annex A.2 and A.3 were changed later by A1, A2, E3 and A6, so a row here is not always the current rule on its own; read the amendments below.

    # Rule, in short
    I1 The tenant wall is in the database: every tenant table has a tenant_id and forced row-level security. With no tenant context a query gets no rows or an error.
    I2 The tenant comes only from a platform-verified source (a validated token resolved through tenant_identity_binding, or a row the platform wrote). Never from client values, payloads or workflow inputs.
    I3 Database roles have least privilege: no superuser, no BYPASSRLS, no ownership, no role membership, no grants to PUBLIC. Every grant comes from one manifest. No SECURITY DEFINER function or RLS-bypassing view is reachable from a runtime role.
    I4 One write pipeline with optimistic concurrency; a stale write is a typed conflict.
    I5 One authorization layer, inside the query. Unreadable, other-tenant and missing records give the same response.
    I6 The durable (workflow) path is deterministic and versioned, and is entered only through the transactional outbox.
    I7 Every side effect is idempotent.
    I8 Contracts are the boundary; configuration, not code; AI is advisory.
    I9 Cascades are bounded by a causation record and a platform depth limit (amended by A5).

    Options and decision

    Paraphrases: "2. Decisions", "4. Rejected options".

    Decision What it says Main alternatives that lost
    D26 tenant resolution One shared Keycloak realm per installation (version 26.1.3 or later), one organization per tenant. The tenant is resolved from the token issuer and organization id through tenant_identity_binding; the token must name exactly one organization, otherwise 401. Fails closed. Realm per tenant; tenant id as a user attribute; auto-linking brokered logins by email; Zitadel instead of Keycloak.
    D6 API REST-first /api/v1 from an OpenAPI 3.1 contract, additive-only within a major version, RFC 9457 errors, opaque cursors, Idempotency-Key, ETag/If-Match, per-tenant rate limits. GraphQL-first, or REST and GraphQL equal in the first milestone.
    D22 Temporal access One Temporal namespace per installation, mutual TLS with a deny-by-default Authorizer that also inspects worker commands. Only the relay starts and signals workflows, from outbox rows. Workflow ids are t:<tenant>:<target_key>. Namespace per tenant; tenant in workflow input; network isolation alone; an Authorizer that checks only the API.
    D28 database roles One database role per system actor. No role has BYPASSRLS, owns anything, or is a member of any role. Backups are physical, through a REPLICATION-only role. A BYPASSRLS system role; logical-dump backups; SECURITY DEFINER functions.

    The identity provider is reached only through two core interfaces, IdentityResolver and DirectoryAdmin (Annex A.4), so a later switch is a contained adapter change.

    Consequences

    Paraphrases: "3. Consequences".

    • The project owns a custom Temporal server build (Authorizer and ClaimMapper) as a separate Go module, re-verified on every Temporal upgrade.
    • Every cross-tenant database path can be listed, and CI fails on any new one.
    • Keycloak is administered only through the platform API in the first milestone.
    • Per-target FIFO signalling costs a little on outbox inserts; the worst case must be bounded.

    Accepted risks

    Paraphrases: "5. Residuals". Each was accepted by the product owner on 2026-10-15.

    # Risk Revisit when
    R1 Temporal histories are cross-tenant data and are not encrypted in the first milestone. The first regulated-data tenant.
    R2 The migrator is all-powerful over its tables; the backup holds every byte. Any request to run DDL from a runtime process.
    R3 No tenant self-administration of Keycloak. Epic 26 scoping.
    R7 A custom Temporal server build to own. Every Temporal upgrade.
    R8 A stolen relay, core or worker certificate has wide reach (see the original for each). Any new holder of a Temporal certificate.
    R9 Head-of-line blocking per target while a signal backs off. The Epic 08 flood test.

    No dissent was recorded.
