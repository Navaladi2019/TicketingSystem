    ADR-004-E7: A1 books the 10 s interval when work is pending

    Status on main: ACCEPTED, 2026-11-07, by the Solution Architect after the Technical Architect's critique and a CTO ruling on the path. It clarifies R16 of ADR-004 and changes nothing else; R-A2 is unchanged. Normative text: the E7 record; explainer: E7-explained.html.

    Paraphrases: "Context", "Decision", "Options considered", "Consequences".

    Problem

    The sealer's first activity (A1) books the next run before the second (A2) seals. In the code, A1 used the interval that the previous run's A2 had stored, so every interval change landed one run late. After an idle period, entries written just after a run waited up to 300 s even though that run had sealed something, and a burst larger than one run's cap could wait about 600 s, breaking the documented bound and firing the sealing-lag alert on a healthy system.

    Decision

    R16's interval bullet is reworded: on the non-stale path and under the head lock, A1 checks whether the tenant has any unsealed entry. If so it books the next run 10 s ahead and stores 10 s; otherwise it books at the stored interval. A2 stores the interval for later runs (10 s if it sealed anything, otherwise doubled up to 300 s; unchanged on error).

    Bound, absent an A2 failure: an entry is sealed within the delay already booked when it was written (at most 300 s) plus one run's duration. A poison entry still blocks later entries; that is the failure-metric and chain:reseed path.

    Options that lost

    Rewording R16 to match the code and relaxing the bound to about 600 s; running A2 before A1 (ends the lineage on a crash); moving the next run's available_at forward from A2 (a new sealer write path and grant).

    Consequences

    No Temporal determinism impact: the change sits inside the A1 activity, so recorded histories replay as they are. Idempotency is unchanged.
