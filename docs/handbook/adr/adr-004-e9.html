    Handbook / adr / ADR-004-E9: the audit row for a create refused with number_space_exhausted

    Summary. The normative text is the linked docs/adr/ADR-004-E9-number-space-exhausted-audit-row.md.

    In progress: not on main yet

    ADR-004-E9: the audit row for a create refused with number_space_exhausted

    Status on main: ACCEPTED, 2026-11-14, by the Solution Architect on TICK-864. The one contested point (F1, where the row is written) was settled by the CTO tie-break; no dissent recorded. Erratum to ADR-004: extends the R2 action list (as extended by E1), adds rule R2b and acceptance test CI-A18, and adds the allocator-pool rule to docs/budgets.md. Normative text: the E9 record; explainer: E9-explained.html.

    The decision is on main; the code is not. The follow-up task under TICK-674 builds R2b, migrations A and B and CI-A18. Until it lands, a refused create returns 409 but writes no audit row.

    Paraphrases: "Context", "Decision", "Why this placement (spike S1)", "Accepted residuals".

    Problem

    ADR-005 §3.5 says a create refused with number_space_exhausted (409, the counter no longer fits the {seq:N} width under overflow: refuse) is audited. But R2 is a closed list and has no action for a refused create, so there was nothing to write.

    Decision

    • R2 gains one action, number_space_exhausted. No new subject type, envelope column or index.
    • R2b, the entry: domain record, subject entity_definition / D (the type the create targeted), both versions NULL, the refused command's actor, causation and request id. diff is one add of /number_space with four keys: epoch, scope_key, width and counter (the value that did not fit). It never carries the attempted record data, field values or the idempotency key.
    • Where it is written (CTO ruling): in a transaction of its own on the caller's API pool, after the create's transaction has ended and its connection is released. Never on the allocator pool, never while a create transaction is open. Write returns the refusal carrying the entry; internal/server/records.go appends it with tenancy.InTenantTx on context.WithoutCancel, bounded by the request deadline, so a client that disconnects does not drop the row.
    • One entry per refused attempt, each in its own transaction. If the append fails, the caller returns the refusal joined with the audit error; a refusal is never reported as success.
    • Budget rule: allocator-pool transactions are allocations only (synchronous_commit = off, about 2 ms). No synchronous-commit transaction runs on that pool.

    Effect on numbering

    There are two refusal sites with one row shape:

    Mode Site counter in the row Allocator-pool transactions per refusal
    gaps pipeline.go, the Fits check after allocate the number just allocated (already committed, so it is a gap) 1
    gapless batch.go writeCreate max + 1, given back by the rollback; the counter row is unchanged 0

    So in gaps mode five refusals show five rising counters; in gapless mode they show the same counter five times. Neither mode issues a number. ErrNumberSpaceExhausted gains Epoch and Counter.

    scope_key in the row is safe because of ADR-005 §3.4 (it holds only mapped enum codes and SQL-computed date parts, and no mask is live on those fields while the format is in use), not because of the read path: these rows are never field-masked.

    Migration

    Two goose files, each with lock_timeout = '5s': A drops audit_log_action_check and re-adds it NOT VALID (catalogue only, about 2 ms); B runs VALIDATE under ShareUpdateExclusiveLock, blocking neither reads nor audit writes. The CHECK mirrors audit.Actions(). Any later ATTACH PARTITION must carry the current CHECK definition, never a hard-coded copy.

    Why this placement

    Spike S1 put the row on the 4-connection allocator pool (RFC-019 rev 1). With tenant A retrying refused creates at full rate, tenant B's allocation p95 rose to 114 ms, 32 times its baseline, in 1 of 7 reps. The row on the API pool after the rollback passed 5 of 5 reps, with B's p95 at 2.99 to 3.71 ms against a 3.15 ms baseline.

    Accepted residuals

    # Residual Owner
    RS-E9-1 A client that keeps retrying writes one row per attempt until a wider format is published. Revisit if these rows pass 10 % of a tenant's daily audit volume, show in seal lag, or raise API-pool acquire waits. Technical Lead
    RS-E9-2 A field masked later still shows its code in earlier refusal rows (covered by the widened AR-TICK-653-01; revisit when reference-code tokens ship). Security & Multi-Tenancy Reviewer
    RS-E9-3 rejectTooDeep still writes cascade_too_deep on the allocator pool; it may move under the R2b placement if that costs one line. Solution Architect
