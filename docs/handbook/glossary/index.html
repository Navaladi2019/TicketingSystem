                  Glossary

                  Terms used across the handbook, including every term that appears in a vision-section heading. Each entry points to the page that explains it most fully. Pages for the security, database and workflow sections are written by other handbook tasks; until they exist, entries point to the section's index.

                  Tenancy and identity

                  • Tenant. One customer organisation using the shared platform. Main page: I1: tenant wall.
                  • Tenant wall. The row-level-security rule set that makes a query without a tenant return nothing. I1.
                  • Row-level security (RLS) and FORCE RLS. A PostgreSQL feature that adds an invisible "only this tenant's rows" filter to every query. FORCE applies it even to the table's owner. I1.
                  • Principal. The authenticated caller of an API request, a user or a service, resolved from a verified token inside one tenant. I2.
                  • Group. A set of principals in one tenant, changed only through the platform API (tenants cannot administer Keycloak in Milestone 1, residual R3) and mirrored from Keycloak into the platform's identity tables by the group sync (internal/groupsync); used by access rules. I5.
                  • Identity port and adapter. The core-owned interface to the identity provider and the single package that talks to Keycloak. I8.
                  • Platform-verified source. A tenant value that comes from a validated token via the identity binding table, or from a row the platform wrote. I2.

                  Database roles

                  • Database role and least privilege. One narrow database account per system actor; none is a superuser, owns objects or bypasses RLS. I3.
                  • Grant manifest. The single file listing every permission of every role; CI compares the live database with it. I3.
                  • Migrator. The one-shot job that owns the schema and runs migrations. Database.

                  Records and writes

                  • Entity definition and entity definition version. A tenant's JSON Schema description of a kind of record, and one published, immutable version of it. Database.
                  • Record. One stored item of an entity type, with a version used for optimistic concurrency. I4.
                  • Write pipeline. The single path every write takes: authorisation, defaults, schema validation, checks, commit with audit. I4.
                  • Optimistic concurrency. An update names the version it expects; a stale one is a typed conflict (HTTP 412 with If-Match). I4.
                  • Authorization layer. The access rules, compiled to SQL and agreeing with the Go single-record check. I5.
                  • ACL and ACL version. An access-control list for an entity type, and the version number of the published list a decision was made under. I5.
                  • Mask (field mask). A rule hiding a field from readers who may not see it, on write and on read. I5.
                  • Numbering mode. How a record's human-readable number is allocated, per tenant, from a counter table. I8.
                  • Idempotency key. A client-supplied key (Idempotency-Key) that makes a repeated write return the first response. I7.
                  • Idempotent. Doing it twice has the effect of doing it once. I7.

                  Audit

                  • Audit log. The per-tenant record of every change, written in the same transaction as the change. Database.
                  • Seal. The sequence number and hash assigned to an audit entry by the asynchronous sealer. Database.
                  • Chain head. The latest sealed entry of a tenant's audit hash chain; each new seal hashes the previous one. Database.

                  Workflows

                  • Outbox. A table of work rows saved in the same transaction as the change that caused them. I6.
                  • Relay. The process that reads outbox rows and starts or signals workflows. I6.
                  • Temporal and workflow. The workflow engine and a durable process it runs. Workflow code is deterministic; side effects run in activities. I6.
                  • Causation and cascade. The origin event id and depth carried by every write and outbox row; a cascade is a write that triggers further writes, bounded by a depth limit. I9.

                  Process words

                  • Invariant. A rule that must always hold; changing one needs a new signed ADR. The nine invariants.
                  • Decision (D and G numbers). D numbers are decisions in ADR-001 section 2; G numbers are the TICK-2 gaps it closes (G7 is recorded as a decision). Goals and non-goals.
                  • Goal and non-goal. What Milestone 1 sets out to do, and what it deliberately leaves out. Goals and non-goals.
                  • Configuration, not code. Tenant changes are data, never new code or schema changes. I8.
                  • Advisory AI. AI may suggest, and change data only above a recorded confidence threshold. I8.
                  • Proof and enforcement point. The test or ADR section that shows an invariant holds, and the layer that applies it. The nine invariants.
                  • Known technical risks. The CTO's register of live risks. Vision.
                  • ADR. Architecture Decision Record. Architecture decisions.
