## 2026-11-26: S29, the backfill outbox payload holds UUIDs only, and publish inserts the job row as `nava_app` (D-10-10, D-10-11)

- **Decided by:** Technical Lead, on TICK-916 (PR #921), at the Postgres & Data Modeling Specialist's request.
- **D-10-10, outbox payload (contract C3).** `outbox_payload_check` (migration 00009) accepts UUID values only, so C3's `{entity_definition_id, target_version, causation_audit_id}` cannot be stored. C3 now reads: payload `{"entity_definition_id"}`; `target_version` in `outbox.target_seq` and in the dedupe key `schema-backfill:<def>:<version>`; `causation_audit_id` on the `schema_backfills` row only. The relay builds the workflow id from `outbox.tenant_id`, the payload id and `target_seq`; activities read `default_keys` and `causation_audit_id` from the job row under RLS (D2 already checks that row). Same shape as `EnqueueFieldIndexBackfill`. No change to the payload check.
- **D-10-11, who writes the job row at publish (ADR-009 D1).** Publish writes it, in the publish transaction, as `nava_app`. D1 and its API scenario ("a forced rollback leaves no job row and no outbox row") require it, and D12 needs a `pending` row the moment the version is live: without one, filters between publish and the worker's first run miss records that lack the default, which is the bug S29 fixes. A worker-created row would also need `default_keys` in the outbox payload, which D-10-10 forbids.
  - `nava_app` gets **INSERT on `schema_backfills` only**. No UPDATE or DELETE on it, nothing on `schema_backfill_pending` or `schema_backfill_failures`, no change to any other table.
  - A `RESTRICTIVE` `FOR INSERT TO nava_app` policy adds `WITH CHECK (state = 'pending' AND rewritten = 0 AND skipped = 0 AND failed = 0 AND started_at IS NULL AND finished_at IS NULL)` on top of the standard tenant policy, so the app can only queue a job, never advance or fake one. The one-active index covers `filling`/`running` only, so a `pending` insert never trips it.
  - Lands in TICK-916's migration and grants (PR #921) with tests: as `nava_app` in tenant A, a `pending` insert succeeds; a `running` insert, a non-zero counter, or tenant B's `tenant_id` is refused; UPDATE and DELETE on all three tables, and INSERT on the other two, stay `42501`.
- **Drift:** ADR-009's grants paragraph ("`nava_app` gets SELECT only") contradicts its own D1. The plan follows D1. The Solution Architect corrects the grants line with an erratum (not blocking S29). *Trigger:* before S29's story → main PR merges.
- **Dissent:** none.
