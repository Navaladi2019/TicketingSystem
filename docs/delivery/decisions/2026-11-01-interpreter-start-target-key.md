## 2026-11-01: D-3-13 amended: an interpreter start uses the existing outbox start key `nava.interpreter:<outbox_id>`
- **Decided by:** Technical Lead, 2026-11-01, on TICK-367 (P3-22b).
- **Decision:** the relay's `target_key` for a `nava.interpreter` start is the existing outbox start form `nava.interpreter:<outbox_id>` (`outbox.Enqueue`, `relay.Claimed.IsStart`), not `interp:<uuidv5(outbox_id, definition_id)>`. The outbox id is unique per row, so a workflow id never repeats under `REJECT_DUPLICATE`. Relay and outbox code are unchanged. If P3-42 needs a key derived from the definition, that is its own Security-reviewed task.
- **Stack worker (also Technical Lead, 2026-11-01, TICK-367 option A):** the interpreter stack cases run on a separate `nava-worker-interptest` compose service (the `interptest` build, its own profile, read-only fixture mount, no host ports). Only those cases start it, inside the serial set, and their `t.Cleanup` removes it. The always-on `nava-worker` stays the production image and polls activities only, with no build args. The stack worker does not register `nava.smoke.Echo`: each suite registers its own body under that name.
- **Technical Lead, 2026-11-01: always-on nava-worker stopped for the interpreter cases.** Each interpreter stack case stops `nava-worker` before it starts `nava-worker-interptest`, and its cleanup starts `nava-worker` again and waits until it is healthy. Otherwise its unregistered `NextStep`/`ApplyStep` attempts spend retries and backoff. A test-only activity queue was rejected: it would add a test setting to workflow code.
- **Dissent:** none.
