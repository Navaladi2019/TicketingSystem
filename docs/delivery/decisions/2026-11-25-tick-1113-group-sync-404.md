## 2026-11-25: TICK-1113, group sync leaves out a user only after two 404s; a 404 that is not from Keycloak is a follow-up (`AR-TICK-1113-01`)

- **Decided by:** the Technical Lead on TICK-1113, with the Security & Multi-Tenancy Reviewer's and the Principal Software Engineer's reviews of PR #889.
- **Decision:** a user deleted while group sync reads a tenant is left out of the snapshot only when the federated-identity read and then `GET /users/{id}` both answer 404. Any other failure fails the tenant and changes nothing. A 404 from the token endpoint never counts as "not found".
- **Accepted until TICK-1141 (Low):** the rule reads the status only. If a proxy in front of Keycloak answers both reads with 404, users who still exist are tombstoned until the next good cycle.
- **Same cause, in `main` before PR #889 (Medium):** `snapshot` takes a 404 on the root group as an empty directory. That also tombstones the groups and org units and deletes the `tenant_admin_group` and `tenant_auditor_group` rows, which no later sync restores.
- **Evidence:** Security's throwaway test on the real `keycloak.Directory` at `22e08bd8` (TICK-1113 comment, 2026-11-25 19:18 UTC) returned no error and 0 users, and 0 users and 0 groups for the root group. The effect on the rows is from reading `internal/groupsync/apply.go`; it was not run on PostgreSQL.
- **Why not in PR #889:** the proposed fix for the root group (fail on an empty directory) would keep the users of a tenant whose root group was deleted on purpose. That needs a decision first.
- **Deferred:** the fix, to TICK-1141. **Owner:** the Technical Lead. **Trigger:** TICK-1141 itself; before that, any installation with a proxy or load balancer between group sync and Keycloak.
- **Deviation:** the token-endpoint rule was not in the first decision. The Principal Software Engineer's review found that such a 404 could drop users who still exist.
- **Dissent:** none.
