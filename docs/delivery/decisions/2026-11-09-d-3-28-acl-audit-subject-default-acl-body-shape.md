## 2026-11-09: D-3-28, S10 contract amendment A3: ACL audit entries get the subject acl_policy; the default incident ACL lets a requester raise its own incident; a non-object PUT body is 400
- **Decided by:** the Technical Lead on TICK-620 (P3-35), on the CI run of PR #531. Dissent: none.
- **Why:** (1) ACL publishes were audited under `entity_definition` with the ACL version as `version_after`. A transaction that creates an entity type (v1) and publishes its ACL (v1) wrote two entries with the key (transaction, subject, definition id, version 1), and the second append failed with `audit_log_default_commit_key`. The two version chains also shared one subject, so the audit trail could not tell schema v2 from ACL v2. (2) With the default incident ACL as first written, a requester could read an incident but never raise one: S9.4 answered 403. (3) The OpenAPI validator already answers 400 `validation_failed` to a body that is not a JSON object, so a test that expected 422 for `[]` was wrong.
- **Decision (A3):**
  - ACL publishes are audited under the subject type `acl_policy`, `subject_id = entity_definition_id`, `version_before/after` = ACL versions. It is registered in `internal/audit/subjects`, `audit_log_subject_type_check` is extended by migrations `20261109130000` (NOT VALID) and `20261109130100` (VALIDATE), and `db/audited-tables.yaml` and the `acl_versions` trigger name `acl_policy` (this overrides the TICK-615 choice). The same-transaction fixture (entity type v1 plus ACL v1) stays one transaction and is a regression test.
  - Default incident ACL v1 gains one rule, `default-requester-new`: read and write for `Requester` where `state eq new`. The rest is unchanged: service-desk read and write where `assignment_group_id` is in `my_groups`, requester read on every state, admins group read and write on everything. M1 has no null or "unassigned" Cond, so the admins group triages unassigned incidents.
  - A PUT body that is not a JSON object is `400 validation_failed`. `422 invalid_access_policy` is for a well-formed object that breaks policy rules.
  - Accepted as written: `request` and `change` get no default ACL and fail closed until an admin publishes one; a tenant without a `service-desk` group gets the default without that rule. Both are in the operator guide.
- **Deferred:** QA suggested service-desk write on unassigned incidents. That needs a null Cond, which changes the compiler and the I5 agreement suite. It reopens when a tenant needs the service desk to triage unassigned incidents.
- **A4 (same day, same decision, TICK-620 PR #531):** the S9.4 kit creates an incident with no `requester`, so even with `default-requester-new` the row's requester was null and Alice's create was 403. The record pipeline now sets `requester_id` to the caller on a `user` or `ai` create when the payload leaves the requester property out, before `CanWrite` runs. An explicit value (null included) is kept as sent and goes through `CanWrite`; system sources (`rule`, `workflow`, `function`, `system`) get no default. The S9.4 kit is not changed. Tests: `records_requester_default_integration_test.go` (default to the caller; a non-admin naming another user is 403; a system create leaves it null). Dissent: none.
- **A5 (same day, same decision, TICK-620 PR #531):** the CI stack run showed that the stack seed gave tenant A an admins group and tenant B none, and `reconcile-default-acl` stopped being usable for B. `nava-onboard reconcile-default-acl` runs each tenant in its own transaction. A tenant that fails (for example, no admins group row) is logged with its id and reason, gets nothing published and stays fail-closed; the batch moves on to the next tenant. At the end it prints a summary of published, already-present and failed tenants and exits non-zero if any failed. It never publishes a default that leaves out the admins rule. `seed.sh` now creates tenant B's admins group too. Test: `reconcile_acl_integration_test.go` (three tenants, the middle one without the row: the other two are published, the middle one is untouched, the run fails; a rerun after the row is added publishes only the middle one). Dissent: none.
- **A6 (same day, same decision, TICK-620 PR #531):** the first stack run on the real default ACL failed `s9_records` at S9.9: Alice, the requester, moved her own incident to `in_progress` and got 403. The default is right and the S9 kit is wrong: requesters do not triage (`default-requester-new` writes only while `state eq new`, checked before and after). S9.9 to S9.13 (and S9.19, AC3) now run as tenant A's admin, S9.4 stays Alice's, and a new S9.8a has Alice PATCH her incident to `in_progress` and expect 403, with S9.8b asserting the version is unchanged. The stack case `s9_records` expects the history `create` by Alice and `state_change` by the admin. Also in this PR: the isolation harness cleanup writes the `acl_policy` delete entries the `acl_versions` commit check requires. Dissent: none.
