Story S2: a query without the right tenant returns nothing

A plain-language explainer of what this story built, why it matters, how we know it works, and what to check before you accept it. No prior knowledge of the architecture is assumed.

In one paragraph. Many customer organisations ("tenants") will share one database. This story makes the database itself refuse to show one customer's data to another, even if our application code has a bug. Every part of the platform now logs in to the database as its own user, with only the permissions it needs. And automated checks on every code change fail if anyone weakens those protections.
All 4 acceptance criteria pass Waiting on your ACCEPTED / REJECTED

1. The problem, in everyday terms

Think of the database as a large shared filing cabinet. Every customer organisation (a tenant) keeps its tickets, users and groups in the same cabinet. The single worst thing that can happen is for Company A to see a ticket that belongs to Company B.

The usual protection is "the application code remembers to filter by customer". That breaks the first time a developer forgets a filter. This story adds a second, independent protection inside the database: every drawer is locked unless the request names exactly one tenant, and then only that tenant's folders are visible.

Before this story

One forgotten filter could expose every customer's data.

After this story

A forgotten filter returns nothing or an error. The database enforces the wall, not the developer's memory.

2. How the wall works

  1. Every request names its tenant. The platform's database helper (InTenantTx) opens a short transaction and stamps it "tenant = A". The stamp is valid only inside that transaction.
  2. Every customer table has the wall switched on and forced. "Forced" means even the table's owner can't skip it.
  3. Without a valid stamp, the wall shows nothing. That covers a missing tenant, a blank tenant, and a stamp left behind by a previous request on a reused (pooled) connection.
  4. A code check (lint rule) stops developers from setting the tenant stamp by hand anywhere except the helper, so nobody can make it last longer than one transaction.

3. Each part of the platform gets its own key

Previously one database user could do everything. Now each component logs in as its own user, which can touch only the tables and columns it needs. None of them is an administrator, none can bypass the wall, none owns any table, and none inherits rights from another user.

Database userWhich componentWhat it can do
nava_appThe main APIRead and write tickets and requests, behind the wall
nava_workerBackground workflow workersLike the API, but narrower
nava_relayEvent deliveryOnly the outgoing-events queue (the "outbox"). Cannot read tickets.
nava_purgeCleanup jobDeletes expired housekeeping rows, and nothing else
nava_onboardNew-customer sign-upCreates and activates a tenant
nava_groupsyncSync of users and groups from the login systemWrites users, groups and org units
nava_backupBackupsCopies raw database files only. Cannot open a query session at all.
nava_migratorSchema changesOwns the tables, never used by running services

All of these permissions are written in one file, db/grants.yaml. It is the only place a permission may come from. If the real database ever differs from that file, the difference is removed. A brand-new database that differs makes the build fail.

4. Automatic guards on every code change

Protections decay when nobody checks them. These checks run in CI (the automated test pipeline) on every pull request, and a change that fails any of them can't merge.

CheckWhat it catches
CI-1 wall on every tableA new customer table without the forced wall. Also catches an unexpected access rule ("policy") that isn't on the approved list.
CI-2 isolation suite (make isolation)Seeds two tenants and tries every database user against every customer table with no tenant, a blank tenant, and a leftover tenant. Every attempt must get 0 rows or an error.
CI-3 user attributesA service user that becomes an administrator, can bypass the wall, owns a table, or inherits another user's rights.
CI-4 permissions match the fileA permission added by hand instead of through db/grants.yaml.
CI-9 user reachProves, for example, that the event-delivery user can't read tickets and the backup user can't log in for queries.

6. Problems found on the way, and fixed

A copied access rule could have leaked data. The security reviewer showed that copying an approved rule onto the tickets table would have given every tenant's tickets to the API, and the check would have let it through. The check now matches each approved rule on table and name, and rejects duplicates. Fixed before merge (PR #48).

A hand-added permission was quietly removed instead of failing the build. The first acceptance run found that criterion 3 failed: the system cleaned up the bad permission silently, so CI stayed green and nobody would have noticed the mistake. Now, on a fresh database, the same situation fails the build and names the permission (PR #139, with stricter tests in PR #145). We re-tested it and it now goes red.

7. Also delivered in this story

  • Cleanup job (nava-purge): deletes expired duplicate-request keys, sent events and finished workflow references. It has its own minimal database user, refuses to start if that user has admin powers, and has indexes so cleanup stays fast.
  • Safer diagnostics: tracing data sent to monitoring now uses an allow-list, so new fields (which might hold customer data) are dropped unless someone approves them explicitly.
  • Locked-down administrator: exactly one database administrator exists, reachable only from inside the database machine, and default public access to the main database is closed.

8. What you'll see that might look odd

3 lines read ALLOWLISTED In the isolation report, three lines say ALLOWLISTED instead of 0 rows. These are deliberate, approved exceptions from the architecture decision (ADR-001):

  • binding_lookup for the API and the user-sync job. Before anyone is logged in, the system must look up "which tenant does this login belong to?". It reads only that mapping, not tickets.
  • The event-delivery user's outbox rules. It delivers events for all tenants, so it reads the outgoing queue across tenants, but nothing else.

No user-attributes section in the report Your criterion 2 mentions a "report section". The report doesn't print one. The same facts are proven by automated tests and the CI-3 check instead. If you'd like it printed in the report, say so and I'll add a small follow-up task.

10. Not in this story

This story protects the database layer only. You won't see any screens or ticket features here. Login, the ticket API and the user interface come in later stories of the same plan (PLAN-001), and they build on this wall.

Glossary

Tenant
One customer organisation using the platform. Its data must never be visible to another tenant.
Row-level security (RLS)
A PostgreSQL feature that filters which rows a query can see, according to rules ("policies") stored in the database itself.
FORCE row-level security
Applies those rules even to the table's owner, so nobody skips the wall by accident.
Role / database user
The identity a component uses to log in to the database. Permissions are attached to it.
Grant
A single permission, such as "the event user may read the outbox table".
Connection pool (PgBouncer)
Reuses database connections between requests for speed. That's why "a tenant left over from a previous request" had to be tested.
Migration
A versioned script that changes the database structure.
CI
The automated pipeline on GitHub that builds and tests every proposed change before it can merge.
ADR-001
The accepted architecture decision record that set these rules.
