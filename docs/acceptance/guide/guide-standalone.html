Prerequisites

Do these once per fresh stack, from a clone of main. About 10 minutes, most of it the first image build.

You need

  • Docker Desktop (or Docker Engine with compose v2), with about 8 GB of memory for it.
  • Go 1.26 (for make dev-ca, make demo-outbox and the optional harnesses).
  • Git Bash on Windows, or any POSIX shell. make.
  • Bruno (desktop app, usebruno.com) to click through. For the headless run, Node.js, verified with 22 (npx fetches the pinned Bruno CLI, @usebruno/cli@4.3.0).

git clone https://github.com/Navaladi2019/TicketingSystem.git

Windows (Git Bash) notes

  • Run everything from Git Bash, not PowerShell or cmd. The Makefile and the two scripts set MSYS_NO_PATHCONV=1 themselves, so container paths such as /run/... are not rewritten (TICK-277).
  • If you type a docker command with a container path yourself, prefix it: MSYS_NO_PATHCONV=1 docker compose exec ....
  • Line endings: if sh tools/seed.sh says $'\r': command not found, your clone converted the scripts to CRLF. Run git config core.autocrlf input and re-clone, or sed -i 's/\r$//' docs/acceptance/guide/tools/*.sh.
  • Docker Desktop must use the WSL 2 backend; give it 8 GB of memory (Settings › Resources).

The local stack starts healthy

Story S1, TICK-43. Kit: docs/acceptance/s1-platform-foundation.md.

What you can test

One docker compose up starts PostgreSQL, PgBouncer, Keycloak, Temporal, the Collector, nava-core, the worker, the relay, the purge, nava-onboard and nava-groupsync. nava-core reports its dependencies on /healthz, its readiness on /readyz and its metrics on /metrics.

A query without the right tenant returns nothing

Story S2, TICK-44. Kit: docs/acceptance/s2-tenant-isolation.md.

What you can test

Tenant isolation is enforced by PostgreSQL row-level security: a query with no tenant, an empty tenant or another tenant gets 0 rows. Over HTTP, the only tenant data route on main is GET /api/v1/me, so the collection shows that naming another tenant in a header, the query or the body never changes which tenant answers.

A tenant user signs in and is scoped to their tenant

Story S3, TICK-45. Kit: docs/acceptance/s3-tenant-signin.md.

What you can test

A seeded user signs in through Keycloak (realm nava, client nava-web) and calls GET /api/v1/me. The tenant comes only from the token's organization and the platform's own binding table. A missing, garbage, tampered, expired, foreign or ID token is 401 invalid_token; a token that names no organization or two is 401 tenant_unresolved.

There is no web UI yet. Bruno's token request does the sign-in that the Keycloak login page will do for the web app. To see the login page itself, open http://localhost:18081/realms/nava/account and sign in as alice@tenant-a.test.

An operator onboards a tenant

Story S4, TICK-46. Kit: docs/acceptance/operator-onboards-tenant.md. Operator reference: docs/operator/onboarding.md.

What you can test

The operator operator@nava.test creates a tenant with one call to nava-onboard. A replay with the same Idempotency-Key returns the same answer and creates nothing; the same key with a different body is 409 idempotency_key_reuse; a domain another tenant owns is 409 domain_claimed with no hint of the owner. A tenant token is 403, and the tenant ingress (nava-core) answers the operator route 501.

nava-onboard publishes no port, on purpose: the tenant ingress must not reach it. tools/tunnels.sh up forwards 127.0.0.1:18082 to it for this test only. The operator reference shows the docker compose exec way instead.
The new admin's first sign-in goes through the tenant's own identity provider in a browser, which Bruno cannot drive. Step 7 runs the recorded harness for it.

Group changes and deprovisioning take effect within 10 minutes

Story S5, TICK-47. Kit: docs/acceptance/s5-group-changes-within-10-minutes.md. Design: ADR-002 (group_paths).

What you can test

nava-groupsync copies each tenant's users and groups from Keycloak every NAVA_GROUPSYNC_INTERVAL (default and maximum 5 minutes). Removing Alice from a group, or disabling her, reaches GET /api/v1/me on her existing, unexpired token after the next cycle: at most 5 minutes of sync plus 5 minutes of token life, so within 10 minutes.

To test in seconds instead of minutes, put NAVA_GROUPSYNC_INTERVAL=15s in .env before docker compose up (Prerequisites does this). The 10-minute bound itself was measured with the default in the S5 kit.

Troubleshooting

The usual reasons a check turns red, and how to reset.

401 on every call

SymptomCauseFix
401 invalid_token for a fresh tokenThe token's issuer is not KEYCLOAK_PUBLIC_URL/realms/nava (you called Keycloak through another host or port, or changed KEYCLOAK_PORT without KEYCLOAK_PUBLIC_URL).Use the environment as shipped (keycloak_issuer_url = http://localhost:18081), or set KEYCLOAK_PORT and KEYCLOAK_PUBLIC_URL together, restart the stack and match both URLs in bruno/environments/local.bru.
401 invalid_token after a whileAccess tokens live 5 minutes.Run the folder's sign-in request again.
401 tenant_unresolved for Alice or BobThe tenants are not seeded, or no group sync has run since.sh docs/acceptance/guide/tools/seed.sh.
401 on a Keycloak admin request (S3.13, S5.x)The admin token lasts 60 s.Send again: the pre-request script fetches a fresh one.

403

403 forbidden on /api/v1/operator/tenants means a valid tenant token was sent. Use the operator sign-in (S4.1, client nava-operator-cli).

502, connection refused, socket hang up

WhereCauseFix
127.0.0.1:18082, :19090–:19095, :18233The tunnels are not running (they stop when the stack is recreated).sh docs/acceptance/guide/tools/tunnels.sh up again.
:18233 onlyThe Temporal UI is not started.COMPOSE_PROFILES=operator in .env, then docker compose up -d, then the tunnels again.
:18080 or :18081The stack is down or still starting.docker compose ps; wait for healthy.
502 from KeycloakKeycloak is still importing the realm (first boot, about a minute after the container starts).Wait for docker compose ps keycloak to say healthy.

The stack does not start

  • all predefined address pools have been fully subnetted: old Docker networks. docker network prune (removes unused networks only).
  • A port is taken: set NAVA_CORE_PORT, KEYCLOAK_PORT and KEYCLOAK_PUBLIC_URL=http://localhost:<KEYCLOAK_PORT> in .env, and the matching URLs in bruno/environments/local.bru.
  • ca.pem: no such file: run make dev-ca first.
  • Startup over 5 minutes on a busy machine is normal; docker compose up --wait keeps waiting.

Alice is stuck (disabled, or out of service-desk)

A run stopped half way through S5 can leave Alice disabled or out of her group. Run S5.15 (re-enable) and S5.8 (re-add to service-desk), wait one sync, then S5.17. Or in the Keycloak console: Users › alice › Enabled on; Groups › t › tenant A › service-desk › Add member.

Reset everything

sh docs/acceptance/guide/tools/tunnels.sh down
docker compose down -v          # deletes all data: tenants, users created by S3, workflows
docker compose up --wait
sh docs/acceptance/guide/tools/seed.sh
sh docs/acceptance/guide/tools/tunnels.sh up

Re-seed only

sh docs/acceptance/guide/tools/seed.sh is idempotent: it inserts what is missing and runs one group sync.

Logs

docker compose logs --since 5m nava-core nava-onboard nava-groupsync | grep -i -E 'error|warn|refused'

Every error response's instance is urn:nava:request:<id>; grep that id in the logs to see why. Logs never contain tokens.
