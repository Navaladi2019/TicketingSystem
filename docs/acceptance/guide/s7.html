A committed outbox row runs exactly one tenant-scoped workflow

Story S7, TICK-49. Kit: docs/acceptance/outbox-row-runs-one-workflow.md.

What you can test

When the platform commits a change that starts background work, the relay hands it to Temporal exactly once, as a workflow whose id names the tenant. Its follow-up signals arrive in commit order. Running the demo twice with the same key adds nothing. There is no tenant HTTP route for this: the demo is a command, and the operator watches it in the Temporal UI.

Click by click

  1. Run the demo twice with the same key.Git Bash
    make demo-outbox DEDUPE_KEY=accept
make demo-outbox DEDUPE_KEY=accept
    Both runs print the same start row, signal row 1, signal row 2 and workflow id t:00000000-0000-4000-8000-0000000000a1:nava.smoke.relay:<start row>.
    The second run prints different ids, or no internal network for compose project: the stack is not up.
  2. Open the Temporal UI: http://127.0.0.1:18233 (the tunnels script opens it; or run make operator-tunnel in a second terminal). Choose namespace nava.Browser
    Workflows lists one row for that workflow id, status Running (no worker runs the demo type, by design).
    Two rows for one id, or the page does not load (Troubleshooting › Temporal UI).
  3. Click the workflow id, then the History tab.Browser
    WorkflowExecutionStarted, then two WorkflowExecutionSignaled events named demo.note, in the order of signal rows 1 and 2.
    One signal, three, or out of order.
  4. Run Bruno S7.1 and S7.2: the same checks through the Temporal UI's HTTP API.Bruno
    S7.1 picks the demo's own workflow: the id in the environment variable demo_workflow_id (paste the workflow id the demo printed), or the most recently started tenant A nava.smoke.relay workflow when it is empty. That id has exactly one execution, and S7.2 finds exactly two demo.note signals in its history. Other nava.smoke.relay workflows on the stack (another tenant's, or another DEDUPE_KEY) do not change the result; set demo_workflow_id when you ran the demo with more than one key.
    S7.1 finds no tenant A demo workflow: run the demo first. demo_workflow_id is not listed: it is from another stack; clear it.
  5. Optional: look at the outbox rows.Git Bash
    docker compose exec -T postgres sh -c 'PGPASSWORD=$(cat /run/pg_superuser_password) psql -U pgadmin -d nava' <<'SQL'
SELECT kind, attempts, dispatched_at IS NOT NULL AS dispatched FROM outbox ORDER BY created_at;
SQL
    Three rows for the key, each dispatched once (attempts 1).
    Six rows, or a row still pending a minute later.

Not repeated here

The crash drill (kill the relay between claim and start) and the cross-tenant signal denial are in the S7 kit and in the CI-6 report (ci6-report artifact of the latest ci run), not in this guide: they need a test build of the relay.
