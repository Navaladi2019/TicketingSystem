An operator onboards a tenant

Story S4, TICK-46. Kit: docs/acceptance/operator-onboards-tenant.md. Operator reference: docs/operator/onboarding.md.

What you can test

The operator operator@nava.test creates a tenant with one call to nava-onboard. A replay with the same Idempotency-Key returns the same answer and creates nothing; the same key with a different body is 409 idempotency_key_reuse; a domain another tenant owns is 409 domain_claimed with no hint of the owner. A tenant token is 403, and the tenant ingress (nava-core) answers the operator route 501.

nava-onboard publishes no port, on purpose: the tenant ingress must not reach it. tools/tunnels.sh up forwards 127.0.0.1:18082 to it for this test only. The operator reference shows the docker compose exec way instead.
The new admin's first sign-in goes through the tenant's own identity provider in a browser, which Bruno cannot drive. Step 7 runs the recorded harness for it.

Click by click

  1. Make sure the tunnels are up.Git Bash
    sh docs/acceptance/guide/tools/tunnels.sh up
    tunnels: 127.0.0.1:18082 -> nava-onboard:8081 (and the other two).
    no default network for project nava: the stack is not up, or you set another COMPOSE_PROJECT_NAME in this shell only.
  2. Run S4.1 (operator) and S4.2 (tenant A admin) sign-ins.Bruno
    Both 200. The operator token has audience nava-operator-api and realm role nava-operator.
    401 invalid_grant for the operator: the realm was not imported.
  3. Run S4.3–S4.7: no token, tenant token, the tenant ingress, no Idempotency-Key, a private IdP address.Bruno
    401 invalid_token; 403 forbidden; 501 not_implemented; 400 validation_failed with errors[0].pointer; 422 invalid_idp_config.
    Any 2xx: a caller or a body that must be refused got through.
  4. Run S4.8 Onboard a new tenant.Bruno
    201 with {"state":"active","tenant_id":"…"}. The domain is onb-<random>.test, new on every run.
    422 invalid_idp_config: the IdP URLs must be https on a public address (the request uses a public IP literal). 5xx: see docker compose logs nava-onboard.
  5. Run S4.9 (replay) and S4.10 (same key, different body).Bruno
    S4.9: 200 with exactly the S4.8 body. S4.10: 409 idempotency_key_reuse.
    S4.9 is 201 or another tenant id: a second tenant was created.
  6. Run S4.11–S4.14: the same domain under a new key, seeded tenant A's domain, a forged tenant id, and /me on nava-onboard.Bruno
    409 domain_claimed twice, with neither the owner's id nor the domain in the body; 201 with a server-derived id (not the forged one); 404 not_found.
    A body naming the owning tenant, or the forged tenant id accepted.
  7. Optional: look at what onboarding wrote.Git Bash
    docker compose exec -T postgres sh -c 'PGPASSWORD=$(cat /run/pg_superuser_password) psql -U pgadmin -d nava' <<'SQL'
SELECT t.id, t.state, d.domain FROM tenants t JOIN tenant_email_domain d ON d.tenant_id = t.id ORDER BY d.domain;
SELECT tenant_id, email, consumed_at FROM pending_invite;
SQL
    Two new tenants, both active: S4.8's with domain onb-<run>.test and S4.13's with onb2-<run>.test, next to tenants A and B. Each has one pending invite (admin@onb-<run>.test, admin@onb2-<run>.test), not yet consumed. No tenant has an onb3- domain: S4.7's refused request created nothing. In Keycloak (admin console › realm nava › Organizations) there is a new organization with an identity provider.
    The tenant is provisioning, or there are two tenants for one key.
  8. The admin's sign-in through the tenant's own IdP: run the recorded harness (about 70 s).Git Bash
    NAVA_S4_EVIDENCE=$PWD/s4-evidence.md \
  go test -tags 'identitystack acceptance' -count=1 -v -run '^TestS4Acceptance$' ./internal/identitystack
    --- PASS: TestS4Acceptance. Open s4-evidence.md: every line reads PASS, including "Criterion 2" (each admin signs in through their IdP and /me shows their new tenant) and "Criterion 3" (a user federated to another tenant's IdP cannot be made admin).
    Any FAIL line in s4-evidence.md.
