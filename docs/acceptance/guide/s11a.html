The workflow interpreter runs a definition on Temporal (timer, branch, signal)

Story S11a, TICK-334 (story branch TICK-334/workflow-interpreter, not on main yet). Kit: docs/acceptance/s11a-workflow-interpreter.md.

What you can test

A workflow definition in our own format (internal/workflow/def/testdata/fixture-v1.json: a 5 s timer, a branch on the record's priority, a wait for the approve signal, a record update, the end) runs on Temporal through the one generic workflow type nava.interpreter. Publishing a new version never changes a run already in flight, and a worker killed in the middle of a record update applies it once.

The stack runs the interpreter with test fakes for the definition store, the records and the record writer (nava-worker-interptest, built with the interptest tag): the database-backed ones come with later stories. The demo stops the always-on nava-worker while it runs, so the fake worker is the only one on the queue; make demo-interpreter-down puts it back.

Click by click

  1. Check out the story branch and start a fresh stack with the Temporal UI (Prerequisites 1 and 2, with COMPOSE_PROFILES=operator in .env). The demo also needs the test overlay, which defines the interpreter worker: add it to .env.Git Bash
    git checkout TICK-334/workflow-interpreter
cat >> .env <<'EOF'
COMPOSE_PATH_SEPARATOR=";"
COMPOSE_FILE="compose.yaml;deploy/compose/compose.test.yaml"
EOF
make dev-ca
docker compose down -v && docker compose build && docker compose up --wait
    Every service ends Healthy. Keep the two values quoted: the demo script reads .env with the shell.
    A service stays unhealthy: Troubleshooting.
  2. Put the interpreter worker in place and open the Temporal UI tunnel (second terminal).Git Bash
    make demo-interpreter-up
make operator-tunnel        # second terminal, leave it running
    fixture v1 (51a11000-…-000000000001) installed for tenant-a and tenant-b, then nava-worker stopped; nava-worker-interptest healthy and the only nava-tq poller. http://127.0.0.1:18233 shows namespace nava.
    no internal network for compose project: the stack is not up.
  3. Criterion 1. Start a high-priority run for tenant A, and a low-priority one.Git Bash
    make demo-interpreter TENANT=a KEY=try-high PRIORITY=high
make demo-interpreter TENANT=a KEY=try-low PRIORITY=low
    Each prints workflow id: t:00000000-0000-4000-8000-0000000000a1:nava.interpreter:<start row>. In the UI, both have Workflow Type nava.interpreter. After 5 s the high one has a fired 5 s timer and a pending 1d timer: it is waiting for approve. The low one is Completed: it took the else edge straight to the end.
    No workflow after 10 s: make demo-interpreter-status TENANT=a KEY=try-high shows the start row's last_error.
  4. Send the approve signal to the waiting run.Git Bash
    make demo-interpreter-approve TENANT=a KEY=try-high
make demo-interpreter-writes
    The run is Completed within a few seconds; its history shows nava.interpreter.signal, then ApplyStep, NextStep and nava.workflow_ref.Close. writes prints one call with "set":{"approved":true} and "applied":true for that workflow id.
    The run stays Running: check the signal row with make demo-interpreter-status TENANT=a KEY=try-high.
  5. Criterion 2. Start a v1 run and publish fixture v2 while it waits on its 5 s timer, then start a run on v2. Fixture v2 branches to approval only when priority is critical.Git Bash
    make demo-interpreter-pinning TENANT=a KEY=try-pin PRIORITY=high
make demo-interpreter TENANT=a KEY=try-v2 PRIORITY=high
    pinning prints fixture v2 (…-000000000002) published for tenant a, while the v1 run waits on its timer, a few seconds before its timer fires (compare with TimerFired in the history). The v1 run still waits for approve (v1's branch) and its input shows definition_version_id …001; after make demo-interpreter-approve TENANT=a KEY=try-pin it completes with mark_approved. The v2 run (input …002) completes after its timer without waiting.
    The v1 run completes without waiting for approve: it read v2.
  6. Criterion 3. Restart the worker with the pause-after-commit hook, start a run, then let crash send approve, wait until the update_record write has committed, SIGKILL the worker and start it again.Git Bash
    make demo-interpreter-up PAUSE=1
make demo-interpreter TENANT=a KEY=try-crash PRIORITY=high
# wait 10 s for the timer and the branch
make demo-interpreter-crash TENANT=a KEY=try-crash
# wait 20 s: the killed attempt times out (10 s) and is retried
make demo-interpreter-writes
    crash prints ApplyStep committed its write and paused, killed: … running=false exit=137, the killed attempt's call (attempt 1, applied) read from the volume, then same container started again … healthy. The run is Completed; History shows 2 • nava.interpreter.ApplyStep (attempt 2, last failure activity StartToClose timeout). writes shows attempt 1 "applied":true and attempt 2 "applied":false under one key, and one applied-effect line for that key.
    Two applied lines for one key: the effect was applied twice.
  7. Isolation. As tenant B, try to signal tenant A's waiting run (use a record id a tenant A run printed). Optionally, also start a tenant B run that reuses that UUID: it does not cross tenants, see below.Git Bash
    make demo-interpreter-up PAUSE=0
make demo-interpreter-approve TENANT=b KEY=iso RECORD_ID=<tenant A record>
make demo-interpreter TENANT=b KEY=iso-start RECORD_ID=<tenant A record>
    The cross-tenant proof is the signal: it is refused before any row is written, outbox: record not found, because row-level security hides tenant A's record and run from tenant B. Tenant A's run is unchanged. CI covers the worker side: TestInterpreterCrossTenantIsNotFound. The optional start is not a cross-tenant check: records is keyed by (tenant_id, id), so it creates tenant B's own record with the same UUID, and its run t:00000000-0000-4000-8000-0000000000b1:nava.interpreter:… fails on its first step as nava.WorkflowRejected (not found) because tenant B's fixture store has no such record. Nothing crosses tenants.
    Tenant A's run receives a signal, or tenant B's run reads tenant A's record.
  8. Criterion 4 is a CI check: read the unit job of the latest ci run on the story branch (green), and of demo PR #347, which adds an activity before every timer (red).Browser
    The story branch run is green. The demo PR's unit job fails TestReplayRecordedHistories on all four timer histories with [TMPRL1100] … a matching Timer command was expected.
    The demo PR's unit job is green: the replay gate missed a non-deterministic change.
  9. Clean up.Git Bash
    make demo-interpreter-down
docker compose down -v
    nava-worker-interptest removed; nava-worker healthy again.
