"Tickets in my region": when a ticket type is small, read its tickets instead of visiting every unit

In three sentences. (1) For a ticket type with few records under a very large region, the current query visits every unit of the region looking for them, so it gets slower as the org chart grows. One benchmark row failed the 150 ms budget at 9,099 units. (2) In that case the query now starts from the other side: it turns the region into an in-memory set once, then reads the type's own records and keeps those inside the set. A count the list already runs decides which side to start from. (3) The spike passed every line of its contract (worst case 75.85 ms at the largest certified tree), results are unchanged by construction, and nothing is added that a tenant can configure.

1. The problem in plain words

An org unit is a box in the company's organisation chart ("EMEA", "EMEA / Germany"). A policy can say in my region: an agent sees a ticket if it was raised in the agent's unit or in any unit below it. The set of those units is the agent's subtree, written S. The ticket list has to answer within 150 ms at the 95th percentile (p95: 95 of every 100 requests are at least that fast).

Amendment A2 made this fast for the common case. Its query starts from the units: for each unit in S, it looks up that unit's tickets. That is cheap when the units hold many tickets of the type being listed. It is wasteful for a concentrated type: one with, say, 20,000 records in the whole tenant, almost none of them under S. The query then visits all 9,099 units and finds almost nothing, at about 3.4 to 5.9 microseconds per unit. The re-measurement (TICK-1037) scored that row at 161.57 ms, over budget.

3. The decision

  1. A third query shape, R. The region condition becomes "this ticket's unit is in the set of units under U". PostgreSQL builds that set once as a hash table (an in-memory lookup that answers "is X in the set?" in constant time) and checks each of the type's records against it. A small trick, wrapping the test in IS TRUE, stops the database from rewriting it back into the unit-by-unit form.
  2. Choosing R. Before the list, A2 already runs a quick probe. A3 adds a count of the subtree's units to the same statement, stopping at N̂e / α, where N̂e is the tenant's estimated number of records of this type. If the count reaches that cap, the subtree is big next to the type, and R is used. Otherwise the probe carries on exactly as in A2. No extra round trip to the database.
  3. α = 3.3, measured. R costs about the same at every subtree size; A2 grows with it. The two lines cross at about 6,000 units for a 20,000-record type, so α = 20,000 / 6,000 ≈ 3.3 (see the chart).
  4. Skip the count when R cannot win. For a large type such as the main ticket type (400,000 records), R could only win on a tree far above the certified 10,111 units, so the count is skipped and the probe costs exactly what it did under A2.
  5. Same results, always. Every shape asks the same yes/no question of each ticket. A wrong estimate or count changes speed, never which tickets you see. An error returns 500; it never silently switches shape.
