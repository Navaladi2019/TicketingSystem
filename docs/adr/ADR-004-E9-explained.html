Auditing a create that was refused because the number space is full

In one sentence. When a record cannot be created because its number format has run out of digits, the platform now writes one audit entry that says which type and which numbering scope is full. That entry is written after the failed create has let go of its database connection, and never on the small connection pool reserved for handing out numbers.

The problem in plain words

Every record gets a number such as INC-202611-0042. An admin can choose a number format with a fixed number of digits (the width) and the rule overflow: refuse. When the counter no longer fits the width, for example the 10,001st record of the month in a 4-digit format, the create fails with number_space_exhausted (HTTP 409). The numbering decision, ADR-005, says that refusal must be audited.

The audit log (ADR-004) accepts only a fixed, closed list of actions, such as create, update and publish, and the database enforces that list. None of them describes "a create that was refused". So the audit entry ADR-005 asks for could not be written. Erratum E1 met the same gap for cascades that go too deep, and E9 fixes this case the same way.

Three questions we had to answer

QuestionAnswer
What is the entry "about"? No record exists.The entity type (for example "Incident"). The only fix is for an admin to publish a wider format on that type, so the refusals sit in the type's history next to that fix. The platform already knows this kind of subject, so nothing new is added to its vocabulary.
Is it safe to store the scope key? This is the name of the counter that is full, for example e1|d:202611|f:BLR.Yes. It holds only short codes the platform builds (a month, a mapped branch code), never typed-in field values. The numbering rules forbid using a field that any reader has masked. It shows no more than every number already issued in that scope. Reviewers checked that audit reads do not mask these entries, so the safety comes from those numbering rules. If codes that point at other records are ever allowed in numbers, the question is reopened.
A full scope refuses every create. Should we cap the entries?No: one entry per refused create, as for cascades. Each entry is a real refused attempt. A cap would need extra state on the busiest row in the create path, or a per-server memory that forgets on restart. A metric and the existing 90 % alert give the signal.

The surprise: where the entry is written matters

The platform has two connection pools to the database:

  • the API pool, 20 connections, used by requests;
  • the allocator pool, 4 connections shared by all tenants, used only to hand out numbers. Each allocation takes about 2 ms because it does not wait for the disk to confirm (asynchronous commit).

An audit entry must wait for the disk (synchronous commit), which took about 20 ms. The first revision of the design (rev 1) wrote the entry on the allocator pool. A spike (a short, timed experiment), S1, tested it: one tenant hammered a full scope at its full rate limit while a second tenant created records normally.

Options considered

OptionOutcome
Entry on the allocator pool, inside the write pipeline (rev 1)Rejected: failed S1
A new, dedicated small pool just for these audit entriesRejected: not measured, and adds a component and a connection-pooler entry
Entry on the API pool while the create is still openRejected: a request would hold one connection while waiting for another. That is the starvation bug fixed in TICK-657
Entry on the API pool after the create has endedChosen (CTO tie-break): measured, nothing new to run
Make the scope the subject, or hash the scope key, or cap the entriesRejected: see "Three questions" above

The decision

  • A new action: number_space_exhausted joins the closed list of audit actions, through a two-step database migration.
  • One entry per refused create. It is about the entity type and records four facts: epoch, scope key, width and the counter value that did not fit. It carries no record data.
  • Where the entry is written: the write pipeline hands the entry back with the refusal. The HTTP handler (internal/server/records.go) writes it in its own transaction, after the create's transaction has ended, for the same tenant as the caller's token. The append is bounded by the request's own deadline and runs on context.WithoutCancel of the request context, so a client that disconnects after the refusal does not drop the entry (one entry per refused attempt, E1 RS-E1-2), and a stalled append never holds an API connection past the request.
  • A new budget rule in docs/budgets.md: no transaction that waits for the disk runs on the allocator pool. The one known exception is the rare "cascade too deep" entry (RS-E9-3).

The change to make

A follow-up task under TICK-674 implements this:

  • the entry at both refusal points (default gaps mode, and strict gapless mode);
  • the two migrations;
  • a metric, records_number_space_exhausted_total;
  • nine acceptance tests (CI-A18 a–i). Test (i) proves that no allocator connection ever writes the entry.

Nothing existing is migrated: these entries are new. TICK-674 itself merges first, without the entry.

Status

ACCEPTED on 2026-11-14. The CTO settled the one contested point, where the entry is written, after spike S1. Three reviews of the new placement approved it:

  • the Technical Architect's;
  • the Security & Multi-Tenancy Reviewer's, which found no isolation gap;
  • the Postgres & Data Modeling Specialist's, on the budget line.

Next, the CTO creates the plan, and the follow-up task under TICK-674 builds it.
