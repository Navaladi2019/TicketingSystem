The backfill "wait for everyone in flight" step could miss the newest write

In three sentences. (1) When an admin marks a field filterable after data exists, a background job copies old records into a search table. Before it starts, it waits for every save that was already running when the switch was flipped. (2) The database list we used to find those running saves leaves out the newest one, so the job could start while that save was still running and miss its record. (3) The fix takes a second marker number right after the list, and also waits on any save numbered between the two. The code in PR #738 already does this; this erratum makes the design say the same thing.

1. The problem in plain words

Every database change runs inside a transaction, a unit of work that is saved all at once or not at all. PostgreSQL numbers each writing transaction with a transaction id (xid), counting up. ADR-006 keeps a filterable field's values in a side table. A database trigger fills it on every save, and only once the field's switch is on.

When the switch flips, a save that started a moment earlier may not have seen it, so it writes no side row. The barrier (ADR-006 D9) exists for exactly this: it takes a snapshot, the database's own list of "who is running right now", and waits until all of them finish. Only then does the backfill copy the old records.

The snapshot has an upper mark called xmax, which means "one past the newest finished transaction". Its list of running transactions (xip) only covers numbers below that mark. If the newest-numbered transaction is still running, it sits exactly on the mark and is not on the list. The PostgreSQL manual says so: "there might be active IDs higher than xmax".

The earlier design spikes passed because other saves kept finishing after the held one, which moved the mark past it. The "held save is the newest" case was never set up. An engineer found it while testing PR #738.

3. Options considered

OptionVerdict
Keep the list only (D9 as written)Rejected: it misses the newest running save, as shown twice.
List + fence: take a marker number M right after the snapshot, and also wait on running numbers from xmax up to MChosen: exact, usually only a few numbers to check, no new permission.
Check every number from the oldest running one up to MRejected: also correct, but slower when one long transaction is open; the list already covers that range.
Read running transactions from the activity view (pg_stat_activity)Rejected: needs a broader monitoring permission, and still needs the same marker.
Make every save take a lock the switch waits forRejected: adds a cost to every save for a rare event; ADR-006 already chose the barrier instead.

4. The decision

E1-1: wait set
In one transaction: snapshot first, then fence M. Wait on the snapshot's list plus every running number in [xmax, M). Waiting on a save that started just after the snapshot is harmless; it only waits a little longer. Usually only a few numbers are involved. A save that uses many savepoints (sub-steps inside one transaction) adds one number per savepoint, though: the architect's test reached 100,000. So the job may store just the two end points of the range instead of the full list.
E1-2: a rule that was implicit is now written down
Saves numbered after M began after the switch, and they see it because saves run at the database's default isolation level, READ COMMITTED: each statement looks at the latest committed data. If a save ran at a stricter level (REPEATABLE READ), it could keep an old view and slip past. The old design had the same hole. This also depends on the copy step running after the record row is written. Rule: no code or operator setting may raise the isolation level for record saves, and the copy step must stay an after-write step.
E1-5: make the rule enforce itself
A small check at the start of the copy step refuses any save that is not at READ COMMITTED. A wrong setting then causes a visible error instead of a silently missing search entry. It ships as a follow-up change, with its cost measured in the existing write-speed test.
E1-3: a test that pins it
This test creates the "newest save still running" case on purpose. It checks that the barrier waits for it, and it fails when the fence is removed. The erratum is not accepted until that test is merged.
E1-4: removal too
Removing a filterable field uses the same barrier, so it gets the fix for free.

5. The fix and migration

No migration. PR #738 already ships the fenced barrier (internal/fieldindex/backfill/activities.go). Nothing has been released with the old rule: the backfill workflow is new in that PR. This erratum aligns the design text with the code.

6. What we are accepting

IDSeverityRisk
AR-TICK-745-01LowThe guarantee assumes record saves run at READ COMMITTED. A future code path or a database setting at a stricter level could leave one record out of a filter, inside the same tenant only, until it is saved again. No other tenant is affected. Once E1-5 lands, such a save is refused instead.
