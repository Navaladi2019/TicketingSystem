ADR-001 amendment A5, explained

The whole decision in three sentences. (1) Our signed blueprint rejects a change when a chain of automatic changes comes back to the same record, and that also rejects the most ordinary workflow there is: "when a ticket is created, set a field on it". (2) We change the rule so each workflow starts at most once per record per chain: a second start is skipped and logged, and the change itself goes through. (3) You accept one limitation: a workflow cannot run twice on the same record within one chain. A new user action starts a new chain. The review also found that running workflows messaging each other could loop forever. Rev 1 closes that gap: every automatic change is one step deeper than the message that caused it, so the depth limit stops the loop.
Why this needs your signature. The rule's purpose, no endless chains of automatic changes, is unchanged. Its wording changes from "reject the change" to "skip the repeated workflow start". That changes what the rule means, so this is an amendment, not an erratum (a fix to wording that was simply wrong). The CTO has ruled, and the Technical Architect has reviewed it once. This is the one revision. For this amendment, nava has delegated the sign-off to the Technical Lead.

1. The problem in plain words

A record is one ticket, such as an incident or a request. A workflow definition is a small automated process a tenant admin publishes, for example "when an incident is created, set its priority from its category". When a record changes, the workflows whose trigger matches start. When a workflow changes a record, more workflows may start. That chain is a cascade.

A cascade can run forever: workflow D changes record R, which starts D again, which changes R again. The blueprint's invariant I9 (an invariant is a rule every design must keep) guards against this in two ways. A hard depth limit allows at most 8 automatic changes in a row. A cycle rule catches loops: every change carries its origin, the id of the user action that started the chain, and the rule says:

I9 today (being replaced)
The pipeline … rejects a cycle (the origin seen again on the same record), with a typed error and an audit entry.

3. The decision

Decision text (new I9)
Cascades are bounded. Every write and every outbox row carries a causation record: an origin event id plus a depth. A write at depth 0 mints a new, non-NULL origin id. A workflow's write is one deeper than the start or signal that caused it. The pipeline rejects any write beyond a hard platform depth limit with ErrCascadeTooDeep and an audit entry, and the workflow run fails without retrying. A workflow definition starts at most once per (tenant, origin, record). When a write would start definition D on record R a second time under origin O, the start is suppressed, the write commits, and a cascade_cycle audit entry records O, R and D. The writer gets no error. The cycle key and the depth come only from causation stored by the platform under the writing tenant's RLS, never from an outbox payload or tenant-authored definition data. The limit is platform configuration, not tenant configuration (8, PLAN-001 D-P7).

How it is built

  • A new table, cascade_start, holds one row per workflow start (about 200 bytes each, an estimate; kept for good in Milestone 1, because records are never deleted yet), keyed by (tenant, origin, record, workflow). The database refuses a second row with the same key. If the insert succeeds, the workflow starts. If the row already exists, the start is skipped. This runs in the same database transaction as the change, so either all of it happens or none of it does.
  • The tenant is the first part of the key, and the table sits behind the same tenant wall as every other table: row-level security, the PostgreSQL feature that hides other tenants' rows. Two tenants can never collide, and neither can see the other's rows.
  • The origin is taken from the change the platform stored itself, never from data a workflow passed along, so a workflow cannot forge its way past the rule.
  • The depth limit of 8 is unchanged and still stops every other kind of chain.
  • The check is built so the code cannot skip it. The only way to queue a workflow start takes a "ticket" that only the check hands out, so code that tries to start a workflow without one does not compile.

Workflows that message each other (added in rev 1)

A workflow that is already running can wait for a message (a signal) saying "record R changed". The review found a gap. Suppose workflows A and B both wait on R, and each changes R when told. Each change messages the other, and nothing new is ever started, so the start rule never fires. If every change were stamped with the depth of the workflow's original start, the depth would never rise and the pair would loop forever.

Decision text (rule A5-7, excerpt)
Each interpreter write carries the causation of the most recent delivery the run handled: after the start, (start.origin, start.depth + 1); after a record_changed signal s, (s.origin, s.depth + 1). Every write is exactly one deeper than the delivery that caused it, so no causal chain exceeds the limit. … update_record returns ErrCascadeTooDeep as a non-retryable temporal.ApplicationError … and the run fails.

The rejected change is also marked "do not retry". Without that mark, the workflow engine would by default retry the failed step forever, and the stuck workflow would never finish.

Glossary

Amendment
A change to the meaning of a signed decision. An erratum only fixes wording that was wrong.
Audit row
A permanent entry in the record's history that says what happened and why.
Cascade
A chain of automatic changes, each one started by the one before it.
Depth
How many automatic steps a change is from the user's own action. Capped at 8.
I9
The ninth invariant of ADR-001: cascades are bounded.
Origin
The id of the user action that started a chain. Every change in the chain carries it.
Row-level security (RLS)
The PostgreSQL feature the tenant wall is built on: each query sees only its own tenant's rows.
Signal
A message to a workflow that is already running, as opposed to starting a new one.
Non-retryable
An error the workflow engine must not retry, so the workflow stops instead of trying the same step again.
Spike
A short, timeboxed experiment that settles a factual question.
Tenant
One customer organisation. Every row belongs to exactly one tenant.
Workflow definition
An automated process a tenant admin publishes. The platform runs it when its trigger matches.
