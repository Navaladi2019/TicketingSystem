ADR-001 erratum E3, explained

The whole decision in three sentences. (1) Our signed blueprint says the onboarding service may read "its own provisioning row" in the tenant table. (2) The database rule we actually shipped lets it read its own row in any state, because PostgreSQL cannot activate a tenant otherwise. (3) We correct the words of the blueprint, not the database, and you accept one small residual: the onboarding service can see four fields of the one tenant it just created.
How serious is this? Not a security gap. No tenant can see another tenant. The onboarding service is bound to one tenant per transaction and sees only that tenant's single row, which it wrote itself minutes earlier. This is a case of the paperwork lagging the code, found by a reviewer doing their job.

1. The problem in plain words

Each customer of the platform is a tenant. The table tenants has one row per customer, with an id, a state (provisioning while being set up, then active), an onboarding_request_hash (a fingerprint of the request that created it, so a repeated request is recognised) and a created_at timestamp.

A dedicated database login, nava_onboard, creates tenants. Our blueprint (ADR-001, Annex A.3) lists what each login may do. For nava_onboard it says:

ADR-001 Annex A.3, as signed

“INSERT on tenants and tenant_identity_binding. SELECT on its own provisioning row.”

While reviewing PR #80, the Postgres & Data Modeling Specialist noticed that the database rule is wider than those words. The rule says "own row", full stop, with no "provisioning" condition. So after the onboarding service flips its tenant to active, it can still read that row. The signed text says it should not. One of the two had to change.

2. Background: how PostgreSQL row security works

Row-level security (RLS) is a PostgreSQL feature where each table carries policies: small rules that decide, per login and per kind of statement, which rows are visible or writable. Our tenant wall rests on it: every tenant table has a policy that says "only rows whose tenant matches the tenant of this transaction".

Policies come in kinds. A SELECT policy says which rows a login may read. An UPDATE policy has two parts: which existing rows may be changed (USING) and what the changed row is allowed to look like afterwards (WITH CHECK).

The detail that matters here is a documented rule about UPDATE. When an update statement needs to read the table, for example because it has a WHERE id = ... clause, PostgreSQL also runs the SELECT policy, and it runs it on both the old row and the new row. If the new row would not be readable, the update fails with an error.

PostgreSQL 16 reference, CREATE POLICY, table "Policies Applied by Command Type", row UPDATE, SELECT-policy column

“Filter existing row [a] & check new row [a]”

“[a] If read access is required to either the existing or new row (for example, a WHERE or RETURNING clause that refers to columns from the relation).”

3. Why the words cannot be implemented as written

Activating a tenant is one statement: UPDATE tenants SET state = 'active' WHERE id = <my tenant>. The WHERE reads the id column, so the SELECT policy is applied to the new row. If that policy only allowed provisioning rows, the new row, which is active, would fail it. PostgreSQL would refuse the activation.

6. The decision

Decision text, ADR-001-E3

“The words change; the code does not. In Annex A.3, row Onboarding (nava_onboard), the clause ‘SELECT on its own provisioning row.’ reads from now on ‘SELECT on its own row (the tenant of its transaction, in either state).’”

The signed ADR-001 file is not edited. The erratum is a separate file beside the two earlier amendments, the same way errata E1 and E2 were recorded. A test now pins the behaviour: TestT09OnboardReadsOnlyOwnRowInEitherState (PR #85). After activation, the onboarding service reads its own tenant's active row and zero rows of any other tenant, or of any tenant when none is set.

7. What you are accepting

#Residual riskOwnerWe look again when
RS8The onboarding login, while working for tenant A, can read A's row after activation: id, state, onboarding_request_hash, created_at. It wrote three of those itself. It cannot read any other row or any other tenant; that part of the rule is unchanged and already enforced by a CI test.Security & Multi-Tenancy Reviewerthe tenants table gains a column the onboarding login must not see (then we restrict the grant to named columns), onboarding stops running inside a per-tenant transaction, or the onboarding API lets a caller influence which tenant it is bound to
The condition that makes "own" mean something. The onboarding service is bound to a tenant by a setting called app.tenant_id. That value must be computed by our server from the operator's identity and the request's idempotency key, and never taken from the caller (request body, path, query string or header). If the onboarding API (task T21) ever let a caller pick it, an operator could point the onboarding service at any active tenant and read its row. The Security & Multi-Tenancy Reviewer will hold T21's review to this, with one adversarial test: a second operator replaying the first operator's key gets a different tenant and sees nothing.

There is no migration, no change to database grants or policies, and no code change to approve. The tenant wall (invariant I1) is untouched. Narrowing the onboarding login's read grant to named columns is optional hardening that Delivery may choose; it is not part of this decision.

Glossary

Annex A.3
The section of ADR-001 that lists every database login and what it may do.
Erratum
A correction to a decision record where the text and the implementation disagree and the text is the one that is wrong. E1 and E2 came before this one.
nava_onboard
The database login used only to create and activate tenants.
Policy (RLS)
A PostgreSQL rule attached to a table that says which rows a login may read or write.
Provisioning / active
The two states of a tenant: being set up, and ready for use. Nothing moves back.
Row-level security (RLS)
The PostgreSQL feature our tenant wall is built on. Each query sees only the rows its policies allow.
Spike
A short, timeboxed experiment that settles a factual question.
SQLSTATE 42501
PostgreSQL's "insufficient privilege" error code. Row security violations report it.
T21
The delivery task that builds the onboarding API, the only production caller of the onboarding login.
Tenant
One customer organisation. Every table row belongs to exactly one tenant.
