ADR-006 amendment A3: keep a slow custom field's value on the ticket row, in a shared spare column

Record: docs/adr/ADR-006-A3-promoted-filter-slots.md · Issue TICK-1039 · Evidence: docs/adr/ADR-006/spikes/a3-promoted-slots/ (TICK-1039 arms, PR #920) · Write-path cost: TICK-1205, not yet run · Amends ADR-006 D2, D4, D7, D12, D13 and A1-6.

Why this is still a draft. The design that passed is one we turned down twice before, because of what it costs every ticket save. That cost has not been measured yet. TICK-1205 measures it, and this page does not ask for a decision until that report is in.

Words used here

p95
The time that 95 out of 100 requests beat. Our target for a ticket list is 150 ms.
Filterable field
A custom field a tenant defines (for example "priority") that users can filter lists on.
Side table (D7)
Today's design. Each filterable value is copied into a separate table, and the list asks "does this ticket have a matching row there?" (an EXISTS check) for each ticket it considers.
Row ACL
The rule that an agent sees only tickets in their assignment groups, plus tickets shared with them, raised by them or assigned to them.
Index
A sorted lookup structure. The database updates every index on a table each time a row is saved, so each index adds write time.
Slot
A spare, typed column on the tickets table (records) that holds one promoted field's value. The same slot can mean different fields for different tenants and ticket types.
I8
A platform rule: a tenant's configuration change never adds tables or columns to the database (no "tenant-motivated DDL").
RLS
Row-level security. PostgreSQL itself refuses to return another tenant's rows.

The problem

A list shows the newest 51 matching tickets. With the side table, the database usually walks tickets newest-first and checks each one. That is fast when matches are common and recent. It is slow when the matching tickets are old, or hidden from this agent: the walk goes through everything the agent can see and finds little. On a 400,000-ticket type, an agent who sees half the tickets waited 2.2 seconds for a value none of their tickets had. A1's planned fix ("adaptive", which picks a walk from an estimate) did worse, up to 4.4 s, because it moved the same walk somewhere else.

The decision (proposed)

An operator can "promote" a slow filterable field. Its value is then also kept in a spare typed column on the tickets table, with an index on tenant, ticket type, value, assignment group and update time. Lists that filter on that field use the column. Every other field keeps today's design unchanged.

  • No new column per field. The tested design added a column for the field. That breaks I8 and would pile up columns for every tenant's fields. Instead, one migration adds a fixed handful of spare columns (proposed: 2 per value type, 8 in all). Each has one index that covers only tickets where the column is filled. Promoting a field just records "field X of type Y uses slot 1" and copies the values in.
  • Who runs the database change: nobody, per field. The spare columns ship once, written by the Postgres specialist, reviewed by Security and applied by the normal deploy. After that, promotion is configuration.
  • Which fields: only fields an operator approves, only single-value fields, and the default allowance is zero. The signal to promote is the slow-list log that A1 already added: a tenant's type showing filters over the limit, or a type with more than 400,000 tickets.
  • Safety: the column is on the tickets table, so RLS already isolates it. Its values are never returned to users, only compared. A masked field still cannot be filtered.
  • While copying: the field keeps filtering through the side table, so users see no error while a promotion or a removal runs.

A new column per promoted fieldBreaks I8, locks the tickets table on each add, and columns pile up across tenants.

Evidence

  • 44 scored cases (4 designs × 11 fixtures), each with its query plan, on an idle host (transport floor 0.54–1.52 ms): docs/adr/ADR-006/spikes/a3-promoted-slots/.
