ADR-006 amendment A3: keep a slow custom field's value on the ticket row, in a shared spare column

Record: docs/adr/ADR-006-A3-promoted-filter-slots.md · Issue TICK-1206 · Evidence: docs/adr/ADR-006/spikes/a3-promoted-slots/ (TICK-1039 arms, PR #920; TICK-1205 write path, PR #995; steered-order prototype) · Amends ADR-006 D2, D4, D7, D12, D13 and A1-6.

Where this stands. The cost we were worried about, what this design does to every ticket save, is now measured, and it is acceptable. The measurement also found a new problem: some lists still ignore the new index. Rev 1 changes the design to remove that problem. One scored test run on the real benchmark (called SP-4) has to confirm the fix before anyone is asked to approve.

Words used here

p95
The time that 95 out of 100 requests beat. Our target for a ticket list is 150 ms.
Filterable field
A custom field a tenant defines (for example "priority") that users can filter lists on.
Side table (D7)
Today's design. Each filterable value is copied into a separate table, and the list asks "does this ticket have a matching row there?" for each ticket it considers.
Row ACL
The rule that an agent sees only tickets in their assignment groups, plus tickets shared with them, raised by them or assigned to them.
Index
A sorted lookup structure, like a book's index. The database updates every index on a table each time a row is saved, so each index adds write time.
Slot
A spare, typed column on the tickets table (records) that holds one promoted field's value. The same slot can mean different fields for different tenants and ticket types.
Planner
The part of PostgreSQL that decides how to run a query, for example which index to read. It decides from estimates, and PostgreSQL offers no "hints" to overrule it.
WAL
The database's write log. More WAL means more disk writes and more data to replicate.
I8
A platform rule: a tenant's configuration change never adds tables or columns to the database.
RLS
Row-level security. PostgreSQL itself refuses to return another tenant's rows.

The problem

A list shows the newest 51 matching tickets. With the side table, the database walks tickets newest-first and checks each one. That is slow when the matching tickets are old, or hidden from this agent: on a 400,000-ticket type an agent waited 2.2 seconds. TICK-1039 found one design that passed all 11 test cases: keep the field's value on the ticket row, in an index that also holds the ticket's assignment group. We had turned that design down twice because of what it might cost every ticket save. TICK-1205 measured that cost.

The new problem, and the fix

When the newest tickets of a type do not carry the value being filtered on (a value that was common and is rare now), the planner still assumes the value is spread evenly over time. So it walks the tickets newest-first, through an index that knows nothing about the value, and throws away 100,000 tickets before it fills a page. The new index could have answered directly. PostgreSQL gives us no way to tell the planner to use it.

The fix removes the choice instead of fighting it. Lists on a promoted field sort by a copy of the "last updated" time that is stored only for promoted tickets, and that only the new indexes contain. The newest-first walk can no longer produce rows in the right order, so the planner has to use the new index. Users see the same order, because the copy always equals the real time.

Prototype on a small copy of the problem, single runs, not a scored benchmark. SP-4 repeats it on the real benchmark.

The decision (proposed)

An operator can "promote" a slow filterable field. Its value is then also kept in a spare typed column on the tickets table, with two indexes: one by assignment group, one without. Lists that filter on that field sort by a copy of the update time that only these indexes hold. Every other field keeps today's design unchanged.

  • Spare columns, not a column per field. One migration adds 2 spare columns per value type (8 in all) plus the sort-time column. Promoting a field records "field X of type Y uses slot 1" and copies the values in. I8 holds.
  • Limits: only fields an operator approves, only single-value fields, the default allowance is zero, and at most 4 promoted fields per ticket type. 4 fields × 2 indexes is the point measured at +25% on ticket creation.
  • Query shape, picked by a fixed rule: no ACL → one index read. An agent with a few groups (provisionally up to 8) → one short read per group, merged. More groups → one read and a sort. SP-4 sets the number.
  • After copying values in, the indexes are rebuilt online, because copying made them 1.5–2× larger than needed.
  • Safety: the columns are on the tickets table, so RLS already isolates them. They are only compared and sorted on, never returned. No special database privilege is added.
  • While copying: the field keeps filtering through the side table, so users see no error.
