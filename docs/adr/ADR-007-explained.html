Words used on this page

Host app
Someone else's product (an IT service desk, a loan system, a visa portal) that shows our records inside its own pages or calls us from its servers.
Tenant
One customer organisation on the platform. Its data must never be visible to another tenant.
Keycloak
The sign-in server we already run. Each tenant is one “organization” inside it.
Access token
A short-lived (5 minutes) signed pass that Keycloak issues after sign-in. Our API reads who the user is and which tenant they belong to from it.
azp
A field inside the token naming the application the user signed in through. Keycloak signs it, so it cannot be forged by the caller.
Web component
A custom HTML tag (here <nava-records>) that a host drops into its page like any other tag.
CORS
The browser rule that decides whether a page on one website may call an API on another. Get it wrong and the widget fails in every browser.
SDK
A code library that wraps our API so a developer does not hand-write HTTP calls.
Audit log
The tamper-evident record of who changed what (ADR-004).

The problem

The product is meant to be embedded: a loan company should be able to show and create loan applications inside its own portal, without its users opening our app. Two things are needed: a widget for screens, and a library for servers. The hard part is identity. The host app has its own signed-in user; we must turn that user into one of our users in exactly the right tenant, without giving the host app a way to pick the tenant or impersonate people. Our first rule (I2, ADR-001) says the tenant comes only from a source the platform verified, never from anything the caller sends.

Options considered

OptionResultWhy
Host app signs users in through our Keycloak, like any other appChosenNo new trust path. The token passes the same fail-closed checks that are already tested.
Swap the host's own login token for ours (“token exchange”)RejectedA second way to create user tokens, outside the hardened sign-in flow. Revisit if a host's users are in no identity provider the tenant has connected.
Host's server says “act as user X” in a headerRejectedThe caller would choose who acts. One leaked password would act as every user in the tenant.
Host signs its own user passes and we trust themRejectedEvery host would become an identity authority for our tenants.
Widget inside an iframeNot in v1Browsers now block the cookies an iframe needs to sign in by itself. Revisit if a host has untrusted scripts on its page.
Hand-written SDKsRejectedThey drift from the API contract. We generate from the contract instead.

The decision

What happens on every embedded request

AreaWhat we decided
Sign-inThe host app is registered by our operator as a Keycloak application. Its users are sent to Keycloak and back; if they are already signed in to their company login, they see no prompt.
Tenant opt-inA tenant admin switches each host app on, and lists the website addresses it may run from. Off means refused on the very next request.
Servers with no userA host's server signs in as its own “integration” user, a member of exactly one tenant, with normal permissions. It can never act as someone else.
AuditEvery change records “user Y, via host app X” (a new audit field, via_client_id). Older audit entries keep verifying.
Fair useA host app gets at most half of its tenant's request allowance by default, so it cannot crowd out the tenant's own staff.
Widget v1List, view and create records of one type. Forms come from the record type's definition; the server does all validation and hides masked fields. Works under strict browser security settings.
SDK v1TypeScript, generated from our API contract; its version follows the API version. A second language comes with the first customer who needs one.

What is being accepted (residual risks)

RiskWhy it is acceptableWhen we revisit
Medium Scripts on the host's page can read the user's token.The token lasts 5 minutes, works only on our API, only for that host app, from listed websites, and only with the user's own permissions. The host already holds the user's session.A host with untrusted third-party scripts on that page: build the iframe version.
Low A host server's leaked password acts as its integration user in one tenant.One tenant only, least privilege, can be switched off instantly, every action audited.Anyone asks for an integration user across tenants (refused).
Low Server-to-server calls skip the website-address check.The host-app gate and the 5-minute token still apply.Evidence of tokens replayed from servers.

No tenant-isolation gap was found, so nothing needs the human's decision under the merge policy.

Evidence

  • Code read: the tenant resolver (internal/identity/keycloak/keycloak.go) picks the tenant from the token's organization and never reads azp, so adding a refuse-only gate cannot change the tenant (critique F1).
  • Keycloak 26.8.1 source read: asking for a specific organization only returns ones the user belongs to (F2); service accounts can be added to an organization (F10).
  • Bugs caught on paper: two rev-0 settings would have broken the widget in every browser (missing CORS header and methods, F5); a rate-limit ordering flaw would have let a host drain its tenant's allowance (F6). Both are fixed in the decision.
  • Not yet measured: four short experiments (spikes S1–S4) are the first plan tasks. Each has a fixed pass/fail rule and a pre-decided fallback, listed in the ADR. S1 failing on the token itself would reopen this ADR.

What gets built

In order: the four spikes; the host-app tables and gate; CORS; the rate-limit change; audit envelope v2; the TypeScript SDK; the widget. The Technical Lead's plan (Plan ADR-007) splits this into stories.
