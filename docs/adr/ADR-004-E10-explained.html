Sealing the "NUL was escaped" flag into the audit hash

In one sentence. When an admin repairs a ticket type whose old version contains a NUL character, the audit log stores a slightly rewritten copy of the old version plus a yes/no flag saying so. That flag is sealed into the log's tamper-evident hash, but only when it is "yes", so every entry written before today still checks out exactly as it did.

The problem in plain words

A NUL is character number zero. A few ticket-type definitions saved before 3 November 2026 contain one. The database's binary JSON type (jsonb) refuses NUL, so when an admin publishes a clean replacement, the platform cannot write the audit entry that describes the change, and the admin gets an error. That publish is the admin's only way to fix the type, so it must work (decided on TICK-1121).

The fix writes each NUL in the old version as the six visible characters \u0000 before computing the change list (the diff). An admin can also type those six characters on purpose. Without a marker, someone reading the audit log later cannot tell "this was a NUL we rewrote" from "the admin typed this". So the entry gets a flag, diff_nul_escaped.

The audit log is a hash chain. Each entry's important columns (its envelope) are fingerprinted with SHA-256, and each fingerprint is linked to the previous one. Changing any envelope column afterwards breaks the chain, and the verifier reports tampered. A flag outside the envelope could be flipped by anyone with write access, and nobody would notice.

Three questions we had to answer

QuestionAnswer
1. Adding a column to the fingerprint changes the fingerprint. How do the entries already sealed still verify?The flag is included in the fingerprint only when it is yes. Every old entry is "no", so its fingerprint input is byte-for-byte what it was.
2. Who can see the flag?Everyone who can already see diff_truncated (the E1 flag that works the same way): the audit reader role, the audit read API, and both export formats.
3. Two keys of one object can become identical after rewriting: a<NUL>b next to a typed a\u0000b, or two keys that both hold a NUL and rewrite to the same text. Refuse the publish?No. In that rare case the diff becomes one step: "replace the whole document with the new version". It is still a correct diff, it contains nothing from the old version, and the admin's repair goes through.

How "only when yes" keeps old entries valid

In an exported file, a missing member means "no", true means "yes", and an explicit false is rejected as a malformed line, so each value has exactly one written form.

Options considered

OptionVerdictWhy
Flag in the fingerprint, only when yesChosenOld entries unchanged; flips detected both ways; no extra state.
Flag always in the fingerprint (how E1 added diff_truncated)RejectedEvery already-sealed entry would change its fingerprint and read as tampered. E1 could do it only because the log was empty then.
Fingerprint the flag only after a cut-over pointRejectedThe verifier would have to trust where the cut-over is; in an exported file that value is unprotected.
A new "envelope version" memberRejectedIt needs the same "missing means old" rule anyway, plus a second format to maintain.
Flag outside the fingerprint (the agreed fallback)RejectedAnyone with write access could flip it unseen.
Refuse the publish when keys collideRejectedBlocks the admin's only repair path, for data they did not just send.

The change to make

  • Database (TICK-1170, Postgres & Data Modeling Specialist): audit_log.diff_nul_escaped boolean NOT NULL DEFAULT false. A constant default means no table rewrite. Grants beside diff_truncated; no role may UPDATE it.
  • Hash code: one "emitted only when true" member in internal/audit/chain; the sealer reads the column; the verifier accepts the old and the new CSV header.
  • Publish path (PR #928): sets the flag when at least one NUL was rewritten, and uses the whole-document replace on a key collision.
  • Order matters, and the database enforces it: nothing may write the flag as "yes" before the hash code is live, or those entries would be sealed without it and fail verification forever. Until then, a database trigger refuses any new entry with the flag set to yes; the trigger is removed in the same change that teaches the hash code about the flag.
  • Two layers stop later edits: no role may update the column, and the existing audit guard trigger is extended to refuse any change to it.
  • CSV exports: an empty cell in the new column means "no" (the member is left out), true means yes, and anything else is rejected.

The evidence

  • Spike e10 (docs/adr/ADR-004/spikes/solution-architect/e10/): the "only when yes" member was patched into the real hash code. All existing golden test vectors and the verify, export and seal test suites passed unchanged. A "yes" flag changes the fingerprint, stripping it is detected, and an explicit false or null is rejected.
  • The diff library only copies values from the new version, so the old version can reach the diff only through key names. That is why the whole-document replace contains no NUL.

Review and changes made

The Technical Architect found no blocking problems and asked for four corrections, all taken in revision 1:

  • A collision also happens when two keys holding a NUL rewrite to the same text. The draft code in PR #928 missed that case and silently dropped a key (shown by the reviewer's spike, 5 of 5 runs). The rule now defines a collision as "two keys whose rewritten forms are equal", checked against the rewritten keys.
  • The CSV verifier reads an empty cell as "null", which the new flag rejects; the rule now says an empty cell means "no".
  • The audit guard trigger lists the protected columns by name, so it is extended to include the flag.
  • The landing order is enforced by a database trigger instead of relying on people merging in the right order. A trigger was chosen over a table constraint because adding the constraint would scan and lock the whole audit table.
