The audit check could get quadratically slower on big imports

In one sentence. The database check that ensures every change has an audit entry could reuse a plan built while the month's audit table was tiny, which made big imports quadratically slow. We now make the check plan itself fresh on every call. That costs a fixed, small amount per write, and the slowdown is gone in every situation.

Words used here

Commit check
A database trigger. When a transaction saves (COMMIT), it confirms that every changed record has a matching audit entry from the same transaction (ADR-004 decision 2). Each changed record costs one small lookup, called a probe.
Query plan
The database's recipe for answering a query, for example "read the whole table" (a Seq Scan) or "jump straight to the row through an index" (an Index Scan). Making the recipe is called planning.
Cached (generic) plan
To save time, PostgreSQL may make a recipe once and reuse it on later calls, without looking at the current values or the table's current size.
Partition
The audit table is split by month. Early in a month, the current month's piece is tiny.
Pooled session
Our connection pooler (PgBouncer) hands one database connection to many unrelated transactions in turn, so anything that connection has cached carries over to the next customer.
O(n²)
"Quadratic": doubling the import size roughly quadruples the time. Linear (O(n)) means doubling it doubles the time.

The problem

Early in a month, the current audit partition holds a few dozen rows on 2 pages. For one probe, reading those 2 pages really is the fastest recipe, so PostgreSQL picks a Seq Scan, which is correct. After five calls it caches that recipe, and the pooled connection keeps it. When a later customer on that same connection imports 4,000 records, every one of the 4,000 probes at COMMIT re-reads the whole partition, which by then holds the import's own rows. Commit time rose from 173 ms at 1,000 records to 2,923 ms at 4,000, a 16.9× increase for 4× the work. The implementer of P5-11 found this and stopped, as the rules require.

Options we considered

OptionDoes it remove the fault on pooled connections?Outcome
Plan fresh on every call (force_custom_plan on the function)Yes, by construction. Nothing is cached, so nothing carries overChosen
Reorder the index key or rewrite the lookupNo. Reading 2 pages still wins, and it still gets cachedRejected
Forbid table scans, or make index reads look cheaperNo. The database then caches another recipe that is just as slow, or one that only flips at a different sizeRejected (measured)

Only change the test so it accepts the slow caseNo. The slowdown shipsRejected on its own. The new test is kept alongside the fix
Pre-create and pre-analyse partitionsWorse. PostgreSQL then treats the empty partition as known-empty and picks the scan from the very first callRejected (measured)
Re-analyse on a schedule, or recycle pool connections oftenOnly shortens the window, and depends on jobs and settings staying right everywhereRejected: this moves the risk to operational discipline

The decision

  1. The check function gets one more setting line: SET plan_cache_mode = force_custom_plan. No connection or session setting can override it.
  2. The lookup keeps reading its inputs from local variables, so tests can prove from the captured recipe that it was freshly planned.
  3. CI fails if anyone removes the setting.
  4. The tests now check the recipe that actually runs at COMMIT. They also reproduce the pooled-connection case under both the default setting and the adversarial one. A copy of the function without the fix must still show the slowdown, which proves the test can see it.
  5. The cost budget is rebased to the measured numbers (below).

Rollout: one normal database migration. Connections that already hold the bad recipe pick up the change on their next transaction. No restarts are needed.

What it costs: the new budget

MeasuredCeilingWhat we saw
Per audited write, on one long-lived connection, at 200, 1,000 and 5,000 writes≤ 300 µs per call, and roughly flat (largest ÷ smallest < 1.5)With the fix: 248–251 µs, flat. Today's function: 50 → 234 µs, getting worse as the partition grows
Per record in a 10,000-record import, fresh connection≤ 175 µsWith the fix: 120–142 µs. Same cost with 38 partitions as with 2

In plain terms, each audited write gets about 0.2 ms slower, and a 10,000-record import's save step goes from about 0.1 s to about 1.3 s, growing in a straight line. Today's path can take 2.9 s at only 4,000 records. A ms (millisecond) is a thousandth of a second, and a µs (microsecond) is a millionth.

38 partitions is the shape the budget is measured at. That is three years of months plus two, because nothing purges audit data in the first release. Planning gets a little slower as partitions accumulate, so this is the cautious size.

Measured in CI only, against a same-run reference. On a laptop, the same test varied by about 2× within an hour, so laptop numbers are only background. Each CI run also measures today's function on the same machine. A ceiling breach counts as real only if the ratio between the two functions is also out of range. Otherwise it is a noisy machine: re-run, and do not escalate.

What we are accepting

  • A fixed planning cost on every audited write (AR-TICK-502-01). It is small and linear, and it is the price of a result that does not depend on what an earlier, unrelated customer did on the same connection.
  • The budget covers up to 38 partitions (AR-TICK-502-02). If the retention design (Epic 30) keeps more, both measurements are re-run at that count. If they fail, the cheaper option S3 is the planned next step.
  • A future PostgreSQL version could change how this setting works. The pooled-connection test runs on every database upgrade and would catch it.

Tenant isolation, permissions and the audit format do not change.
