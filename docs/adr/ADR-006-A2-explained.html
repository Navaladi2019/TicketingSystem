ADR-006 amendment A2: the ticket count gets a time limit, and may say "unknown"

Record: docs/adr/ADR-006-A2-count-time-budget.md · Issue TICK-1022 · Evidence: docs/adr/ADR-006/spikes/a2-bounded-probe/ (runs 1–5, and a2-11/ for the spikes that ended rev 1) · Amends ADR-006 D7 and the list response · CTO ruling: option (C2) · Technical Architect: no blocking item, two test additions taken · Security & Multi-Tenancy Reviewer: approved, three tests and one rewording taken · Accepted by the Solution Architect, 2026-11-21.

Words used here

total
The number of matching tickets the user may read, shown next to a list. It is counted only up to 1,000 ("1,000+").
Row ACL
The rule that decides which tickets a user may read. A narrowing ACL hides most of them; the test agent sees about 5–6%.
Side table
A table with one row per ticket per filterable field, so a filter such as "priority = 3" can use an index. It is shared by all tenants; row-level security keeps each tenant to its own rows.
Band (ii)
Filters matching 40% or more of the tickets, for a user with a narrowing ACL. The agreed limit is 350 ms at p95, the time 95% of requests beat.
Statement timeout
A PostgreSQL setting that cancels a query running longer than a given time. A savepoint lets the request carry on after that cancellation.

The problem

A support agent who sees only their group's tickets filters on a common value such as "priority = 3". The page of tickets comes back fast. The count beside it sometimes took 0.2 s on one fresh install and 0.03 s on the next, and 0.6–1 s under load. Which way PostgreSQL counts depends on things nobody controls per request: when vacuum last ran, other tenants' edits, and whether the value sits on the agent's own tickets or on tickets they can't see.

Rev 0 and rev 1 tried to make PostgreSQL always pick the fast way. The tests showed that no rule can know beforehand which way is fast. Forcing the "fast" way on a value that sits on hidden tickets cost 0.3–0.6 s more, and the extra pre-check leaked a 0.2–0.5 s timing signal about hidden tickets.

Options considered

OptionOutcome
Refresh statistics, vacuum, or change cost settingsDid not fix it, or could not be run by the app (runs 1–3).
Force a per-ticket lookup, with pre-checks and guards (rev 0/1)Failed its own test: up to +557 ms when the value sits on hidden tickets.
Decide from a small sample of the user's ticketsNot tried: an unlucky sample makes it walk every ticket, up to about 3 s.
Accept the slowness as a budget exceptionIt would never close by itself: a permanent hole.
Add a real database column per filterable fieldToo heavy now; kept as the long-term option.
Give the count a time limit (chosen by the CTO)Bounds the time in every case, with no guessing.

The decision

  1. The count may run for at most 200 ms.
  2. If it finishes, the answer is as today: an exact number, or "1,000+".
  3. If it doesn't, the page of tickets is still returned in full. The response says total_state: unknown with total: null, and the screen shows "50+" (the matches already listed) instead of a number. It never shows 0.
  4. If the first page holds every match (fewer than a full page), the count is skipped entirely: the number is exact and free.

Evidence

  • Without the limit, the count in this band took 32–114 ms on one machine and up to 0.6 s per request in the spikes. The 8-client p95 reached 578–983 ms on the failing install.
  • The page itself took 4–21 ms in this band in every measurement, which is why the page gets no limit here.
  • The statement-timeout mechanism already exists in the product for slow filters, so this reuses tested code.

What must be true before the code merges

  • The 94 ms page share is measured on a fresh install, on a machine that passes the usual quietness checks (a busy machine makes the number meaningless). If it is larger, the 200 ms shrinks by the same amount, to no less than 100 ms. Below that, the CTO decides again.
  • A forced slow count returns the page with "unknown", never an error, and the request carries on normally. A test on the real slow plan checks that the database stops the count within 15 ms of the limit.
  • After a stopped count, the request is still bound to the same tenant, and the database connection goes back to the pool clean for the next tenant.
  • All the security tests from the earlier attempt carry over. Another tenant's data never changes this tenant's results. A value only on hidden tickets looks exactly like a value that doesn't exist.
  • The acceptance kit passes the band (ii) cell within 350 ms on two fresh installs in a row.

What is being accepted

The count may say "unknown" under load. Users then see "50+" rather than an exact number. An alert fires if more than 5% of filtered lists say "unknown" in an hour.

A small timing signal stays, and gets smaller. How long the count takes depends partly on tickets the user can't see, and that already shows in response time today. "Unknown" is a yes/no reading of that same time, so it reveals nothing new. Above 200 ms, every slow count now looks the same, which hides more than today. Asking about a single value that exists only on hidden tickets always gets an exact 0, because the count is skipped. A cleverer query that mixes in visible tickets still runs the count, but its time reflects hidden tickets only in bulk, as today. The Security & Multi-Tenancy Reviewer approved this and rated it Info: one hidden ticket changes the time by about a microsecond, far below normal variation, and nothing from another tenant is read.

Slow pages are not fixed here. In one test shape, a user who sees half the tickets filtering on a value that sits only on hidden tickets, the page itself took 2–3 s. That is tracked separately (TICK-992).

Invariants

Tenant wall and tenant source hold: no new query, and the count is today's query under row-level security. No new database rights. Results are never wrong: the total is exact, "1,000+", or honestly "unknown".
