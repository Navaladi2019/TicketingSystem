ADR-006 amendment A2: a cheap capped count decides how the database counts a broad filter

Record: docs/adr/ADR-006-A2-d7-bounded-count-probe.md · Issue TICK-1022 · Evidence: docs/adr/ADR-006/spikes/a2-bounded-probe/ · Amends ADR-006 D7 · Security & Multi-Tenancy Reviewer: approved. Technical Architect: no blocking item; accept once spikes S-A2-anti and S-A2-skew pass.

Words used here

Side table (rfv_text, rfv_num, …)
A table holding one row per record per filterable field, so a filter such as priority = 3 can use an index. It is shared by all tenants; row-level security (RLS) keeps each tenant to its own rows.
Row ACL
The rule that decides which records a user may read. A narrowing ACL hides most of them (the test agent sees 6%).
Capped count
The total a list returns, counted only up to 1,001.
Visibility map
PostgreSQL's note of which table pages are known to be readable by everyone without checking each row. Vacuum sets it; edits clear it. The planner uses it to guess cost.
Hash join
A plan that reads all matching rows of one side into memory first. With 192,000 rows and 4 MB of working memory it spills to disk.
p95
The time 95% of requests beat.

The problem

A support agent who can see only their group's tickets lists tickets with priority = 3, a value that half the tickets have. On one freshly built stack this took 34 ms; on another, built the same way, 217 ms, and 578–983 ms p95 under 8 clients. The budget is 350 ms.

The page of results was always fast. The total was not. PostgreSQL has two ways to count it, and it chooses by guessing costs from the visibility map, which depends on when vacuum last ran. That changes after a bulk backfill and after ordinary edits, and because the side table is shared, one tenant's edits change another tenant's plan.

Options considered

OptionResult
Refresh statistics (ANALYZE) when a field becomes readyDid not help: 255 ms with it, 202 ms without. Statistics were not the cause.
Run VACUUM when a field becomes readyThe worker is not allowed to, and edits undo it within hours.
Tell the planner random reads are cheap (random_page_cost = 1.1)Three of five broad filters still took the slow plan. Rejected.
Always force the per-record probe for ACL usersFixed broad values, broke rare ones: up to 8.3 s for a 2% range.
Accept a budget exception for this bandKept as the fallback. The slowness is avoidable, so an exception is the wrong tool.
Count first, cheaply, then decide (chosen)Holds in every band measured.

The decision

For a list where the user's ACL narrows what they see and a data field is filtered:

  1. Count that value's side rows in the tenant, stopping at 20,000. This costs 0.3–18 ms because it stops early.
  2. If it reached 20,000, the value is broad. Then count the records the user can see, stopping at 30,000 (the visible-set guard).
  3. If the user sees 30,000 records or fewer, write the total statement so the database can only use the per-record probe. No settings or hints: the SQL shape itself rules out the hash join. The guard matters because the probe stops early only when matches exist. If the user's records rarely carry the value, it walks every visible record, and that walk must stay small.
  4. Otherwise, for any field after the first three filtered fields, and for the page of results always, the SQL stays exactly as today.

ADR-006 rule D7 said no query other than the list itself may read a side table. A2 rewrites D7 to allow exactly this one bounded count, and the code check that enforces D7 is updated to allow that one site only.

What must be true before the code merges

  • This amendment is accepted.
  • A test reads the database's plan for each field type and operator and fails if a broad count still uses a hash join, or if the 20,000 count stops using its index. It runs on every PostgreSQL upgrade too. This, not the SQL trick, is the guarantee; it catches a PostgreSQL upgrade that changes behaviour.
  • A test proves the page and the count select the same records.
  • Three spikes, with pass and fail written down first. Anti-correlated: a broad value that none of the agent's records carry, at 6% and 50% visibility, must be no more than 10 ms slower than today. This tunes the 30,000 guard. Skew: a value common in another tenant but rare in this one must still count through the index in 20 ms or less. Multi-field: three broad filters together must be no more than 10 ms slower than today.
  • Security's tests: no pre-count on a rejected request or for an admin; another tenant's rows never make a value broad; the counts never appear in logs or metrics.
  • The acceptance kit passes the 40% ACL cell inside 350 ms on two fresh stacks in a row.

What is being accepted

A timing signal inside a tenant (R13, Low, approved by Security). The 20,000 count ignores the row ACL. By timing repeated range filters, a user could find the value where the 20,000th record sits, counting tickets they cannot open, and could then notice when one hidden ticket crosses that line. They never see those tickets, their count or their content, and only fields they may read are involved. Today's plan already leaks a fuzzier version of this. Nothing crosses the tenant wall. If a field is secret, it needs a field mask; a row ACL alone does not hide totals. The exact size of the timing step is measured before merge.

The 20,000 and 30,000 limits are tuned for types up to about 400,000 records. The existing trigger for re-measuring (a tenant passing 400,000 records) covers re-tuning both. Users who see more than 30,000 records keep today's plan, which is the cheaper one at that visibility.

Budgets do not change. The band keeps its 350 ms limit from A1; A2 makes it reliable, it does not claim 150 ms.

Invariants

Tenant wall (I1) and tenant source (I2) hold: the count runs as the app role under row-level security with the tenant from the verified login. No new grants (I3); the existing custom-plan setting of the app role is now a named dependency. Results and totals are unchanged (I5), with the timing note above. Write path, workflows and cascades are untouched.
