DRAFT · 2026-11-21 ADR-010-A2 · issue TICK-1040 · amends ADR-010 D7, R1, R8 · evidence: SP-1b (TICK-969), SP-1c (TICK-1038), the S31 rerun (TICK-951, PR #814) · waits on SP-1d

"Tickets in my region" stops walking the org tree on every request

In three sentences. (1) The first version of "tickets in my region" rebuilt the list of every unit under you on each request and sent it into the ticket query, which made a regional agent's ticket list about 94 ms slower (200 ms for the largest trees) when the budget had less than 4 ms to spare. (2) We now keep the org tree flattened in a table that is rebuilt whenever the directory changes, and before each list we count "are there more than 1,000 tickets under you?" to pick the faster of two equivalent queries. (3) It is fast enough everywhere we measured except mid-sized districts (about +5.7 ms against 3.8 ms of room), and one more experiment (SP-1d) decides whether that gap closes or goes to the CTO.

1. The problem in plain words

An org unit is a box in the company's organisation chart, copied from the company directory (Keycloak) every 10 minutes by a job called groupsync: "EMEA", "EMEA / Germany", and so on. Story S31 lets an access policy say in my region: an agent sees a ticket if the person who raised it belongs to the agent's unit or any unit below it. "Every unit below it" is the unit's subtree.

The ticket list has a speed budget: 150 ms at the 95th percentile (p95: 95 of every 100 requests are at least this fast) with 800,000 tickets loaded. The support-agent list already uses most of it, leaving 3.8 ms of headroom. Any new rule must fit inside that.

The design accepted in ADR-010 (decision D7) found the subtree on each request by walking the tree, collected every unit id in the program, and passed the whole list into the database query. When the real feature was measured (TICK-951):

Subtree sizeExtra time per list (p95)Verdict

The database itself answered in 3 to 4 ms. The time went on walking the tree and on handing the database thousands of ids to plan around. So the fix has to stop doing both.

2. Options considered

OptionVerdict
Keep D7 (walk per request, pass the list of ids)Rejected: +94 ms at region, +200 ms at 10,000 units.
C1: let the database read the subtree from the flattened table inside the query (IN (SELECT …))Rejected as the final form. Correct, but the database guesses how many tickets a subtree holds from a sampled statistic. For districts the guess is wrong by 8.5×, and the plan it picks flips between runs (+30 to +37 ms in one, fine in another). Used only in the interim.
C2: hand the database the subtree as a pre-computed array (= ANY(ARRAY(…)))Fast for small subtrees; disastrous for big ones (reads 380,048 tickets, about +1 s at the top of the tree). Safe only when we already know the subtree is small.
W0: walk the tickets newest-first and check each one against the flattened table (the "walk")Fast for big subtrees; slow for tiny ones (it must scan 6,396 tickets to find a page from a 220-ticket area, +30.6 ms).
A quick count picks C2 or W0 per requestChosen: each shape is used only where it is fast. Worst measured case +5.7 ms (district).
Store a ticket count per unit and pick from thatRejected for now: another table that must stay exact on every ticket create and move, for the same answer the count gives fresh in about a millisecond.
A planner-hint database extensionRejected: a new component in the database image for one rule; plain SQL (OFFSET 0) already does it.
Relax the 150 ms budgetNot proposed: that is a product decision, and not warranted while SP-1d is untested.

3. The decision

  1. Flatten the tree once. A table org_unit_closure (a closure table: one row for every "unit A is at or above unit B" pair) holds only paths through units that still exist. When the directory removes a unit, groupsync rebuilds the tenant's rows in the same database transaction as the tree change, so the two can never disagree. A full rebuild for 10,111 units takes about 0.3 s.
  2. Single ticket: "is this ticket in my region?" becomes one lookup in that table, at most 0.32 ms. The code that walked the tree, and the 10,000-unit limit that protected it, are deleted.
  3. Ticket list: first a probe, a count that stops at 1,001: "how many tickets of this type sit under these units?" At 1,000 or fewer, use C2 (now safe, because we know it is small). Above 1,000, use the walk W0. Count and page use the same shape.
  4. Both shapes ask the same question of every ticket. The probe only chooses how to ask, never who sees what. A test suite runs every case through C2, W0 and the single-ticket check and fails on any difference.
  5. Guards: the region part of a list reads at most about 1,000 tickets; at most 4 probes per request; a probe error fails the request rather than guessing. The 1,000 threshold is fixed in code, the same for every tenant.

4. The fix and the migration

All of it is already planned as tasks under story S31; this amendment adds no new task, it fixes their content.

TaskWhat it does
TICK-1032Adds org_unit_closure, tenant-walled like every other table (row-level security, tenant id in every key), and fills it for existing tenants.
TICK-1033groupsync rebuilds it in the same transaction as each tree change.
TICK-1034Single-ticket check on the table; deletes the per-request walk and the 10,000-unit limit; lists use C1 meanwhile (correct, not yet fast enough).
TICK-1036The probe switch: C2 at ≤ 1,000, the walk above. Not C1.
TICK-1035The agreement suite: every case through C2, the walk and the single check, including a removed middle unit and lopsided districts.
TICK-1037Re-measures on a quiet machine. S31 is not accepted until this passes the budget.

There is no data migration for tickets: their stored org unit does not change. Only how it is matched changes.

Caveat: the machine was busy with other work during SP-1c, so these are reliable for comparing mechanisms but are not budget-grade. That is what SP-1d's quiet-machine pass and TICK-1037 are for.

6. What is being accepted (residual risks)

Mid-sized districts are still over budget (open, not accepted)
About +5.7 ms typical against 3.8 ms of room. Two fixes are queued in SP-1d: a cheaper probe for big subtrees, and removing four "and not already matched" checks the list adds to every branch (39 % of the district's cost). If those fail, the Solution Architect takes it to the CTO as "win back budget elsewhere". The story is not accepted until this is closed.
If SP-1d cannot make the probe cheap at the top of the tree
The threshold drops from 1,000 to 500. The lopsided "thin" district then costs about +7.8 ms. Everything else in this amendment stays.
Timing hint (Info, proposed as AR-TICK-1040-01)
Because the list picks its query from the count, its speed could hint whether more than 1,000 tickets sit under the agent's own units. It never changes which tickets anyone sees, never crosses tenants, and the count is never returned or logged. The security reviewer confirms or blocks this.
A database upgrade could change the walk's plan
The OFFSET 0 behaviour is verified on PostgreSQL 16.10 only. A plan test in CI fails if an upgrade changes it.
