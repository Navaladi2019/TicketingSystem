ACCEPTED · 2026-11-21 ADR-010-A2 · issue TICK-1040 · PR #818 · amends ADR-010 D4, D7, R1, R8 · evidence: SP-1b to SP-1e (TICK-969, 1038, 1041, 1043), two critique rounds, the crossover cells, the S31 rerun (TICK-951)

"Tickets in my region" stops walking the org tree on every request

In three sentences. (1) The first version of "tickets in my region" rebuilt the list of every unit under you on each request and handed it to the ticket query, which made a regional agent's list about 94 ms slower (200 ms for the largest trees) when the budget had only a few milliseconds to spare. (2) We now keep the org tree flattened in a table that is rebuilt whenever the directory changes. Before each list, a quick count decides between two equivalent queries: one for small regions, one for large. The switch point grows with how many tickets the tenant has. (3) The mechanism is settled: the slowest case we measured dropped from +85 ms to about +25 ms. Whether that fits the 150 ms budget is measured on the real handler before the story is accepted. A miss goes to the CTO with costed options.

1. The problem in plain words

An org unit is a box in the company's organisation chart, copied from the company directory every 10 minutes by a job called groupsync: "EMEA", "EMEA / Germany", and so on. Story S31 lets an access policy say in my region: an agent sees a ticket if the person who raised it belongs to the agent's unit or any unit below it (the unit's subtree).

The ticket list must answer within 150 ms at the 95th percentile (p95: 95 of every 100 requests are at least this fast) with 800,000 tickets loaded, and it already uses most of that.

The original design (ADR-010 decision D7) found the subtree on each request by walking the tree, then passed every unit id into the database query. The real feature measured +94 ms at a 1,011-unit region and +200 ms at 10,000 units. The database answered in 3 to 4 ms; the time went on the walk and on planning around thousands of ids.

2. What we learned while fixing it

Four quick experiments (spikes) and a hostile review shaped this. In order:

StepWhat it showed
SP-1b, SP-1cA flattened tree works. Single-ticket checks cost ≤ 0.32 ms. No single query shape is fast at every region size: some are fast only for small regions, others only for large ones.
Critique, round 1Three gaps, all found with test data the earlier spikes didn't have:
• the index ignored ticket type, so a region full of other records was slow;
• the "small region" query could still pick the wrong plan;
• the total count could cost a full second for an agent whose only access is "my region".
SP-1dA cheaper way to count "how many tickets are under these units". It never looks at more than the threshold, however big the tree.
Critique, round 2A ticket type that is rare, or concentrated in a few units, can still be slow under a very large region: the check visits every unit. Rare types now skip the probe (+71 ms becomes +7.7 ms). Concentrated types are a named risk.
Crossover cellsThe two query shapes cost the same at about 3,650 tickets, which sets the switch formula's constant to 0.8. The slowest case at the switch is about +25 ms, down from +85 ms.
SP-1eWith the fixes in place:
• the type-aware index takes a mixed region from 220 ms to 1.9 ms;
• the new count takes a region-only agent from about 1 s to about 3 ms;
• the small-region query (C3) has a plan that can't change.
It also showed that a fixed threshold of 1,000 tickets put the slowest case at its worst point: +85 ms just above 1,000.

3. The decision

  1. Flatten the tree once. A table org_unit_closure (a closure table: one row for every "unit A is at or above unit B" pair) holds only paths through units that still exist. groupsync updates a tenant's rows in the same database transaction as the tree change, one tenant at a time, so a reader never sees a half-changed tree. Corrected by erratum E4: a change replaces only the affected rows; the full rebuild is for the first import and for repair.
  2. Single ticket: one lookup in that table. The code that walked the tree, and the 10,000-unit limit that protected it, are deleted.
  3. Tidy the start units. If an agent belongs to both "EMEA" and "EMEA / Germany", "Germany" is dropped, because it's already covered. Otherwise its tickets would be counted twice.
  4. Ticket list, total count: the region part is always counted with the capped method, which stops at the list's existing 1,001 cap.
  5. Ticket list, the page: a quick probe counts the region's tickets of this type, stopping at the threshold K*.
    • At or below K*, the page uses C3: read just the region's tickets and sort them.
    • Above K*, it uses W0, the walk: go through all tickets newest-first and keep the region's, until the page is full.
  6. The threshold K* is where the two cost the same. C3 reads the region's tickets, so it gets slower as the region grows. The walk reads about (page size × all tickets of the type ÷ the region's tickets), so it gets faster. Measured, they meet at K* = 0.8 × √(page size × tickets of that type). For the benchmark tenant that is about 3,600, kept between 1,000 and 20,000. At the switch point, both shapes read about K* tickets.
  7. Where the ticket total comes from. A new small table holds each tenant's ticket total per type, refreshed hourly per tenant. A missing or stale number only costs speed, never correctness.
  8. Every shape asks the same question of every ticket. The probe chooses how to ask, never who sees what. A test suite runs every case through every shape and the single-ticket check, and fails on any difference.
  9. Rare ticket types skip the probe. If a type has no more tickets in the whole tenant than K*, the walk is cheap whatever the region size, so the walk is used for both the page and the total.
  10. Policy limit: a policy may name at most 4 different starting points for "in region". None may be nested inside another or repeated. Breaking either rule is refused when the policy is saved.
  11. No refusal on tree size. We measured up to 10,111 units per tenant. Above that, an alert fires, but groupsync keeps syncing: refusing a sync would also stop removed people from losing access.

4. Options considered

OptionVerdict
Keep D7 (walk the tree per request)Rejected: +94 ms at region, +200 ms at 10,000 units.
One query shape for every size (C1, C2, the walk alone)Rejected. Each one is slow at some size. Two of them pick their plan from a sampled statistic, so the same request can be fast one day and slow the next.
A per-unit index (L1)Rejected. It is a 62 MB index with an extra cost on every ticket save, and it takes 1.1 s at the top of the tree.
A fixed threshold of 1,000 (the first draft)Rejected: it puts the slowest case just above 1,000 (+85 ms for a region-only agent).
Two thresholdsRejected: more branches without a lower worst case.
Ticket totals from the numbering counter, or from database statisticsRejected. The counter resets each numbering period. Database statistics would show one tenant the other tenants' volumes.
Capped count, plus a probe switching C3 and the walk at K*Chosen: both shapes read about K* tickets at the switch and fewer elsewhere, with no new index on tickets.

From SP-1e, on the 800,000-ticket benchmark: the extra time per list, typical / 95th percentile, in ms, with the first draft's fixed threshold of 1,000. "Agents" have other access too, which fills the page early. A "region-only" caller sees tickets only through "in my region", which is S31's own acceptance persona. The region-only failures all sit just above the fixed threshold and fall as the region grows. That is the walk's cost curve, and it is why the switch moves to K*. A last set of measurements finds the exact crossover. The crossover cells then measured the fix. With the switch at K*, the slowest set (an even 4,500-ticket region) costs +25.5 ms typical for a region-only caller. Every other set is +19 ms or less. The worst cell before the fix was +85 ms.

Also measured:

  • The type-aware index takes the probe from 220 ms to 1.9 ms on a mixed region.
  • The capped count costs 0.7 to 3.2 ms, against 0.6 to 1.1 s before.
  • Every shape returned the same tickets, in the same order, for every caller tested.

The benchmark host was shared with other work, so these numbers compare shapes reliably but are not a budget.

6. What is being accepted (residual risks)

The slowest case may still be over budget (open)
The slowest case is an agent who sees tickets only through "my region", with a region just above K*. TICK-1037 measures it against 150 ms directly. If it fails, the CTO gets two costed options: a dedicated index, which adds a cost to every ticket save, or a product decision on the budget for this kind of user.
Ticket types concentrated outside a large region
Suppose a policy covers most of a 9,000-unit tree, and the type's tickets sit in a few units outside it. The check then visits every unit, at about 10 µs each, which comes to +94 ms. The budget measurement (TICK-1037) includes this case. If it fails, it goes to the CTO with a spike for a different query.
Dormant regions
If every ticket in a large region is older than nearly everything else, the walk has to read far before it fills a page. A metric shows when the walk is used. The fix is the same dedicated index.
Stale ticket totals
If the hourly refresh lags, K* is slightly off. That costs speed only, never who sees what. An age metric alerts at 3 hours.
Timing hint (Low, accepted by the security reviewer)
Response time can hint whether more than K* tickets of a type sit under a policy's units, including tickets the agent can't open. Through K*, it can also hint at the tenant's rough ticket volume. It never crosses tenants and never changes who sees what.
Database upgrades
The two plan-fixing tricks (OFFSET 0 and a materialised sub-query) are verified on PostgreSQL 16.10. A plan test in CI fails if an upgrade changes them.
