Catching old records up when a field gets a default

RFC-021 · issue TICK-897 · Epic 04 · author: Solution Architect · 2026-11-15

DRAFT, waiting for critique round 1 The decision record (ADR-009, assumed number) is written only after the critique and one revision.

In plain words

1. Goal. When a tenant admin changes a record type so that a field gets a default (the value a record gets when nobody sets one), every existing record should behave as if it had that value. Opening a record, listing records and searching must all agree.
2. Today. The platform saves the new version of the type and stops there. Old records never get the value written into the database. Opening one shows the default anyway, because the display code fills it in as it reads. Searching does not fill it in. So a ticket can show priority: 3 when you open it, and still be missing when you search for priority 3. A record only catches up when someone edits it.
Open ticket #1042
priority: 3 (filled in on read)
Search: priority = 3
#1042 not found (the database has no priority stored)
3. What's new. Three changes.
  1. A background job writes the default into every old record, using the same write path as a normal edit, so each change is checked and recorded in the audit log. It works through one tenant and one record type at a time, in small batches, and pauses between batches so live users don't notice.
  2. Until the job finishes, searches count the default as a match. Results are correct from the moment the admin publishes, not hours later.
  3. A field that must be unique cannot have a default. A default would give every record the same value, and the second record would already be a duplicate.
We expect this to work because the normal edit path already fills in defaults on every edit. The job is just an edit with nothing changed, applied to every record that was never edited.
4. Who is affected.
  • End users and integrations: search, lists and single records give the same answer. A user who has a record open in an edit form while the job rewrites it gets a "record changed, reload" message once.
  • Tenant admins: the record-type page shows the job's progress and any records it could not update.
  • Workflow authors: nothing fires. The job's writes do not count as "record updated" events, because the value people see did not change.
  • Operators: a burst of database writes on large record types. Each job is limited to one tenant, and the number of tenants running a job at once is capped.
5. Risks. How long a 100,000-record type takes, and how much database log it produces, is not measured yet. The Technical Architect measures it in round 1. While the job runs, searching on the defaulted field is slower. Sorting by that field may place not-yet-updated records with the empty values until the job ends. A record that fails the checks is skipped and listed for the admin, and searches stay correct but slower until it is fixed.
6. How we'll know it worked. Mid-way: a search for the default value returns the old records while the job is still running (test CI-7). At the end: every old record has the value stored, has exactly one audit entry from the job, and no workflow was started (CI-2). Another tenant's records are never touched (CI-3). A load test on 100,000 records gives the time and the impact on live writes (CI-12).

How the job runs

Admin publishes
a version that adds a default
→
In the same database transaction: the version, a job row (schema_backfills), and a start message (outbox row)
→
The relay starts the job. The tenant id comes from that message, never from anything else
→
Batches of 100 records. Each one is a normal checked write with an audit entry and no events
→
Final check: every record holds the value → done

Outbox row: a message saved in the same transaction as the change that caused it, so a job starts if and only if the publish really happened.

Who the job runs as, and why it cannot cross tenants

QuestionAnswer
Which identity?The system actor schema-backfill. The audit log records it in place of a person. Database role: the existing worker role nava_worker. No new role, and no permission to skip row-level security (the database rule that hides other tenants' rows).
Where does the tenant come from?Only from the start message the publish saved under that tenant's security rules. The job's other inputs are never trusted for the tenant.
How much does one job cover?Exactly one tenant and one record type. No code loops over tenants.
If the tenant setting were missing?Every query also says tenant_id = …, so a missing setting returns zero rows, never all rows.
Can a tenant start it by hand?No. Only publishing a version starts it. Tenant scripts and workflows cannot reach it.

The five questions, answered

#QuestionProposed answer
1Backfill?Yes. A durable job through the normal write path: one audit entry per record, the record's version number goes up (so its ETag, the version tag clients send back when they save, changes), throttled per tenant. If a newer version is published mid-way, the old job hands over to a new one that applies every default.
2Which version shapes reads?Everywhere a record is shown: the stored values, plus the current version's defaults for fields the record does not hold. The audit log is the exception: it always shows what was actually stored at the time.
3Must filters match defaults?Yes. While the job runs, a search that the default would satisfy also matches records missing the field. This works on both search paths. After the job ends, the stored values already match, so nothing extra is needed.
4Uniqueness on stored or effective values?Stored values. A unique field may not have a default, so the two can never differ.
5Other change types?Unchanged, except that "make an existing field required" is allowed when it has a default (the job fills it in). Removing a field, narrowing a list of allowed values, and adding a required field with no default stay refused.

Options considered

OptionResultWhy
A. Job through the write path, plus searches that match defaults while it runsRecommendedCorrect from the moment of publish. Extra cost only while the job runs.
B. Never write the value. Every search computes defaults foreverRejectedEvery search pays forever and cannot use the indexes. The default logic would be copied into the database's own code.
C. One bulk database update per tenantRejectedIt skips the checks, the version number and the audit log, which the platform requires for every write.
D. Records catch up only when editedRejectedThat is today's bug. Records nobody edits never catch up.
E. Refuse searches on the field while the job runsRejectedSafe but unusable for hours on large types.

Evidence

  • The bug in code: reads fill in defaults (internal/server/records.go:247-252, records_list.go:453). The search filter reads only stored data (records_list.go:216). The uniqueness check reads only stored data (internal/records/store/unique.go:65).
  • Normal edits already fill in defaults and move the record to the current version (internal/records/pipeline/pipeline.go:758-821). The job reuses this.
  • Every edit today starts "on updated" workflows (eventsink.go:88-130). That is why the job's writes must not count as events.
  • Spikes: none yet. The 100k measurement is planned for critique round 1 (CI-12).
