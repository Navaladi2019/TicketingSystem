Catching old records up when a field gets a default

RFC-021 · issue TICK-897 · Epic 04 · author: Solution Architect · 2026-11-15

REVISED (rev 1), after critique round 1 Security, Postgres and the Technical Architect each asked for changes. This revision makes them. The decision record (ADR-009, assumed number) follows once the blocking items are re-checked.

In plain words

1. Goal. When a tenant admin changes a record type so that a field gets a default (the value a record gets when nobody sets one), every existing record should behave as if it had that value. Opening a record, listing records and searching must all agree.
2. Today. The platform saves the new version of the type and stops there. Old records never get the value written into the database. Opening one shows the default anyway, because the display code fills it in as it reads. Searching does not fill it in. So a ticket can show priority: 3 when you open it, and still be missing when you search for priority 3. A record only catches up when someone edits it.
Open ticket #1042
priority: 3 (filled in on read)
Search: priority = 3
#1042 not found (the database has no priority stored)
3. What's new. Three changes.
  1. A background job writes the default into every old record, using the same write path as a normal edit, so each change is checked and recorded in the audit log. It first makes a list of the records that need it. Then it updates them one record at a time, each in its own small database step, so a person editing a record never waits for more than one record's update. It covers one tenant and one record type, and pauses between groups of records.
  2. Until the job finishes, searches count the default as a match. Results are correct from the moment the admin publishes, not hours later. When only a few records are left, the search uses the job's own list, so it stays fast.
  3. A field that must be unique cannot have a default. A default would give every record the same value, and the second record would already be a duplicate.
We expect this to work because the normal edit path already fills in defaults on every edit. The job is just an edit with nothing changed, applied to every record that was never edited.
4. Who is affected.
  • End users and integrations: search, lists and single records give the same answer. The "last updated" time does not move, so lists sorted by it stay in the same order while the job runs. A user who has a record open in an edit form while the job rewrites it gets a "record changed, reload" message once.
  • Tenant admins: the record-type page shows the job's progress and any records it could not update.
  • Workflow authors: nothing fires. The job's writes do not count as "record updated" events, because the value people see did not change.
  • Operators: a burst of database writes on large record types. Each job is limited to one tenant, and the number of tenants running a job at once is capped.
5. Risks. Measured on test hardware: each record takes about 7 milliseconds and writes about 4 KB to the database log. A 100,000-record type therefore takes roughly 12 minutes plus pauses and writes about 400 MB of log. With one record per step, live edits slowed by 1.7% in a 20,000-record test. The first design, which locked 100 records at a time, slowed them by up to 416%. The full 100,000-record run of the new design is not measured yet. Sorting by the defaulted field may place not-yet-updated records with the empty values until the job ends. A record that fails the checks is skipped and listed for the admin, and searches stay correct.
6. How we'll know it worked. Mid-way: a search for the default value returns the old records while the job is still running, both when many and when few are left (test CI-7). At the end: every old record has the value stored, has exactly one audit entry from the job, keeps its "last updated" time, and no workflow was started (CI-2). Another tenant's records are never touched, and no tenant workflow can start the job (CI-3). A load test on 100,000 records must keep live edits within 25% of their normal speed (CI-12).

How the job runs

Admin publishes
a version that adds a default
→
In the same database transaction: the version, a job row (schema_backfills), and a start message (outbox row)
→
The relay starts the job. The tenant id is written into the job's name, taken from that message
→
The job lists the records that lack the value (schema_backfill_pending)
→
One record per step: a normal checked write with an audit entry and no events, and the record is crossed off the list in the same step
→
List empty → done. Records that failed are kept on a separate list for the admin

Outbox row: a message saved in the same transaction as the change that caused it, so a job starts if and only if the publish really happened.

Who the job runs as, and why it cannot cross tenants

QuestionAnswer
Which identity?The system actor schema-backfill. The audit log records it in place of a person. Database role: the existing worker role nava_worker. No new role, no new permission on existing tables, and no permission to skip row-level security (the database rule that hides other tenants' rows).
Where does the tenant come from?Only from the job's name, t:<tenant>:schema.backfill:…. The relay builds the name from the start message the publish saved under that tenant's security rules. The job takes no tenant as an input, so nobody can hand it a different tenant.
How much does one job cover?Exactly one tenant and one record type. No code loops over tenants.
If the tenant setting were missing?Every query also says tenant_id = …, so a missing setting returns zero rows, never all rows.
Can a tenant start it by hand?No. Only publishing a version starts it. The workflow engine's permission rules mark it "start-only": only the relay may start it, so tenant workflows cannot start it or restart it.

The five questions, answered

#QuestionProposed answer
1Backfill?Yes. A durable job through the normal write path, one record per step: one audit entry per record. The record's version number goes up (so its ETag, the version tag clients send back when they save, changes), and its "last updated" time stays as it was. Throttled per tenant. If a newer version adding another default is published mid-way, the old job hands over to a new one that applies every default. No database lock on the record type is needed.
2Which version shapes reads?Everywhere a record is shown: the stored values, plus the current version's defaults for fields the record does not hold. The audit log is the exception: it always shows what was actually stored at the time.
3Must filters match defaults?Yes. While records still lack the value, a search that the default would satisfy also matches them. This works on both search paths. With many records left it scans. With few left it uses the job's list (0.45 ms against 98.6 ms measured). After the job ends, the stored values already match.
4Uniqueness on stored or effective values?Stored values. A unique field may not have a default, so the two can never differ.
5Other change types?Unchanged, except that "make an existing field required" is allowed when it has a default (the job fills it in). Removing a field, narrowing a list of allowed values, and adding a required field with no default stay refused.

Evidence

  • The bug in code: reads fill in defaults (internal/server/records.go:247-252, records_list.go:453). The search filter reads only stored data (records_list.go:216). The uniqueness check reads only stored data (internal/records/store/unique.go:65).
  • Normal edits already fill in defaults and move the record to the current version (internal/records/pipeline/pipeline.go:758-821). The job reuses this.
  • Every edit today starts "on updated" workflows (eventsink.go:88-130). That is why the job's writes must not count as events.
  • Postgres spike (round 1, 100k-record type in 10 tenants): about 4 KB of database log per record at every group size. The "missing value" search took 98.6 ms when only 34 records were left, and 0.45 ms using the job's list.
  • Technical Architect spike (round 1, real write path): locking 100 records at a time slowed live edits by 416% at 100k. One record per step slowed them by 1.7% at 20k. Rewriting "last updated" made a client paging through the list miss 10% of records. The worker role cannot lock the record-type table (permission denied), so the design no longer locks it.
