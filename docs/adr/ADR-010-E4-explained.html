ACCEPTED · 2026-11-25 ADR-010-E4 · issue TICK-1118 · corrects ADR-010-A2 (section A2-2, one grant in A2-1) · source: TICK-1054, whole-story review of PR #867

The design said "rebuild the whole region tree on every change". What was built changes only the affected part. We keep what was built and correct the design

In plain words

Goal
Make the accepted design say how the product really keeps its list of "which office or region is below which" up to date. That list decides who sees "tickets in my region".
Today
A background service reads each customer's offices and regions from the company sign-in system every 5 minutes and stores them. Next to them it stores a ready-made list: for every unit, all the units below it. The design says that when anything changes, the service throws away that customer's whole list and builds it again, and holds a special "only one at a time" marker while it does so. The engineers shipped something else, so the design is wrong for anyone who reads it later.
What's new
Nothing in the product. The corrected design says three things. A change replaces only the part of the list it affects. The whole list is built only the first time, when a check finds it wrong, or when an operator asks for it. The "only one at a time" marker is the one the service already held for its whole run. We expect this to work because we compared the partial way with the full way on 3,563 random changes, and they never differed.
Who is affected
Users see no difference. A customer with about 10,000 units has a moved office handled in about 0.1 seconds instead of 0.8 to 2 seconds. Engineers and reviewers get a design that matches the code.
Risks
If some part of the list is wrong for another reason (a program fault, or someone editing the database by hand), a change to other offices no longer repairs it. It is repaired in the next round that brings in other changes but no office change, or after the service restarts with no office change waiting. Until then, a rule such as "tickets in my region" or "all tickets except this office's" can show a person tickets it should not or let them change those tickets, or hide some it should show, but only within their own company. There is no time limit until that next round. We accept this as a medium risk, as rated by the security reviewer.
How we'll know it worked
Already checked: the random comparison above, and tests that move, remove and bring back units and compare the list each time; they run on every code change. At the end: a reader with no background can describe from the design how the list is kept current, and that matches the code.

1. The problem we faced

The table is called org_unit_closure (a closure table: one row for every pair "unit A is at or above unit B"). The service that writes it is called group sync; it copies users, groups and units from Keycloak, the sign-in system, for one customer (tenant) at a time. The second amendment to the access-policy design (ADR-010-A2) described the writing in section A2-2. Four statements there do not match the code:

The design saidWhat is built
Delete and re-insert the tenant's whole table on every tree change. No partial updates.Replace only the affected units' rows (delta write). The full rebuild is kept for the first import and for repair.
Take a lock made for this purpose; a second rebuild waits.No such lock. Group sync already holds one lock per tenant for its whole run; a second run skips that tenant until its next turn.
Write an audit entry for the change.None. The units mirror Keycloak, and the list is computed from them, so neither is configuration kept here.
A full rebuild of 10,111 units takes about 0.3 s.0.8 to 2.0 s in the automated test runs.

How it happened. The partial-write task (TICK-1054) was parked until a speed or size trigger fired. It was started because the task before it was finished; I found no record that a trigger had fired. Its scope was approved, but the accepted design was not amended first.

2. Options considered

OptionVerdict
Correct the design to what is builtChosen: it gives the same rows, and is faster for a moved unit.
Change the code back to a full rebuildRejected: 0.8 to 2 s inside every tree-changing run, against 0.07 to 0.47 s for one moved unit or region, for the same rows. It would be faster only for a large import into a small existing tree (4 to 9 s today, tracked as TICK-1123).
Also add the lock the design namedRejected: the existing lock already covers every group-sync write of this table. A second lock protects nothing and adds an order to get wrong.
Check the whole table on every runNot now: at most 0.13 to 0.48 s per large tenant every 5 minutes, for a fault nobody has seen. It is the fix if one appears.

3. The decision

E4-1. Partial write
In the same database transaction as the tree change, so both are saved or neither is. The affected units are the changed ones, everything that was below them, and everything now below them. Their rows are deleted and written again by walking up from each unit to a root.
E4-2. Full rebuild
Three cases: the table is empty for that tenant; a run with no unit change finds the stored and the computed sets differ; an operator runs the repair function. The query plan is fixed so that a freshly filled database does not make it slow (39 s became 0.65 s in the test that exposed this).
E4-3. One lock
Group sync's own lock, taken before it reads Keycloak. The lock the design named must not be added.
E4-4. Same rows
After a partial write, the affected units' rows are exactly what a full rebuild gives. Four named tests must stay green.
E4-5 to E4-8
No audit entry. Measured times. What a run does not check (the risk below). Group sync may also read the table, which the design's list of database permissions had left out.

4. The fix or migration

Text only: section A2-2 and its explainer point to this erratum. No code, database or configuration change, and nothing to deploy. The code is on the S31 story branch and reaches main with that story; this erratum does not hold it.

5. What we accept (residual risk)

IDSeverityRiskWhen we look again
AR-TICK-1118-01MediumA wrong row outside the changed units lasts until the next applied run with no tree change, with no time limit. An extra row grants through "in my region" and hides through "not in this region"; a missing row does the reverse. Either can let a user read or change tickets outside their rules, or refuse them tickets inside their rules. A list's total can also be lower or higher than the tickets its pages show (inferred from code). Inside one tenant only: row-level security (the database's own tenant filter) and foreign keys that carry the tenant id are unchanged. Only a group-sync fault, the migration role, a database superuser or someone holding group sync's database password can cause it; no user's sign-in can. No metric counts repairs (TICK-1124 adds one).Any such row found in a live tenant, or a second program that writes the table or the units. Then the check runs on every cycle.
