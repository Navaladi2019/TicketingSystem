ADR-004, explained

The whole decision in four sentences. (1) Every change, to a ticket or to the configuration that governs tickets (forms, SLAs, approval rules, access rules and so on), writes one entry into a single audit log, in the same database transaction as the change itself. (2) A background "sealer" links the entries into a chain of fingerprints, so a later edit or deletion is detectable. (3) A tenant admin or auditor can export any slice of the log, and a small offline tool proves that the slice is complete and unaltered. (4) Personal data can still be erased later without breaking that proof.

1. The problem in plain words

The founder's buyer research (2026-11-02) named the audit trail as the gate for regulated buyers. Their objection was specific: audit history must cover configuration changes (somebody edited the SLA rule, or loosened an approval policy), not only changes to tickets. Buyers will test it by making a real change and then exporting the audit.

Before this decision there was no audit table at all. Record types (S8) kept their published versions, but nothing tied that history into a log that could be exported. Twelve epics now carry an acceptance criterion pointing at this decision. Epic 05 was held back from building its audit table until this was settled, so that nobody would have to retrofit it later.

2. What we decided

QuestionAnswer
One log or two?One One table, audit_log, holds ticket changes, configuration changes, and the audit log's own events (exports, erasures). An auditor sees "the SLA rule changed at 10:02, then this case breached at 10:40" in one timeline.
Can a change ever slip through without an entry?No The database itself refuses to commit a change to an audited table unless the same transaction wrote its audit entry. If the change is rolled back, the entry goes with it.
Can someone quietly edit or delete history?Not without detection Nobody's runtime credentials can update or delete audit content. On top of that, the entries are chained by fingerprints (see §3), so any edit made directly in the database breaks the chain.
How do buyers get the data?A streamed export as JSON Lines (one JSON object per line) or CSV, filtered by time, subject or change set. The export is itself logged before it starts. An offline command, nava audit verify, checks the file.
Can secrets leak into the log?No A change that would put a password or API key into the log is rejected outright, including when the secret is buried inside a larger value.
Can users see data they are not allowed to see?No Field masks (hidden fields) apply to the audit too, at the moment it is read, for whoever is reading it.
What about the record types already published (S8)?They are copied into the log once (a "backfill"), so the log is complete from day one.
New ADR or a change to the blueprint (ADR-001)?A new ADR, plus a small amendment, ADR-001-A6, for three narrow additions: a new database role for erasure, a permission that lets onboarding start the sealer, and a rule for background jobs that are not tied to a ticket. No core rule of the blueprint changes.

3. How the fingerprint chain works

A hash is a short fingerprint of some data: change one byte of the data and the fingerprint changes completely. Each sealed audit entry stores the fingerprint of its own contents combined with the previous entry's fingerprint. So entry 101 depends on entry 100, which depends on entry 99, and so on. Change, delete or reorder any entry and every later link stops matching.

Why the chain is built "after" the change, not during it. If every change had to add itself to the chain at the moment it was saved, all the changes in one customer's account would have to queue behind each other, and one slow import would stall everyone. Instead, changes are saved immediately, and a background job (the sealer) links them into the chain a few seconds later. For a busy tenant the delay is about 10 seconds, and at most 5 minutes after a quiet period.

4. Exports that prove they are complete

An auditor rarely wants everything. They ask for "all SLA changes in March". Those entries are scattered through the chain, with ticket changes in between. If we exported only the matching entries, a deleted SLA entry would look just like a normal gap. So the export also includes a stub for every entry in between: just its number and fingerprints, no content. The verifier can then walk the whole chain without gaps and still learns nothing about the entries the auditor did not ask for. The range always starts one entry before the window, so deleting the very first entry is caught too.

5. Erasing personal data without breaking the proof

Privacy law can require us to erase a person's data (Epic 30). Erasing would normally break the fingerprints. To avoid that, the chain fingerprints a salted fingerprint of the change details rather than the details themselves. A salt is random bytes mixed in, so the fingerprint cannot be reversed by guessing. Erasure removes the details and the salt, while the chain still checks out. Only one dedicated role, nava_erasure, can do this, and only in that one way. Every erasure writes its own entry naming what it erased. An entry that was blanked without such a record shows up as tampered. One whose record is not sealed yet shows up as pending.

6. Options we turned down

OptionWhy not
Separate logs for tickets and configurationTwo timelines and two exports: exactly the gap buyers complained about.
Build the chain at the moment of savingAll saves in an account would queue on one lock.
A shared "wake the sealer" marker written by every save (our first draft)Measured: saves waited about 4 seconds behind each other, and two saves could deadlock (the database aborts one of them).
Show existing record-type history through a view instead of copying itA second reading path that the chain and the export would not cover.
Only unfiltered exports are verifiableBuyers test filtered exports.
Anchor the chain outside our database in M1 (write-once storage, timestamping service)A new vendor dependency and a recurring cost. The CTO deferred it (see §7).

8. Evidence

  • The commit check works: a save without its audit entry fails at commit. Spike runs by the Technical Architect and the Postgres Specialist (PostgreSQL 16.10), archived under docs/adr/ADR-004/spikes/.
  • Red to green on the first draft's flaws:
    • red The shared wake-up marker made saves wait 3.9 to 4.0 s, and the onboarding role could not run the check ("permission denied"). green In the revised design, saves never touch the marker, and every writer's permissions are generated from one list, which CI checks.
    • red Rewriting the timestamp inside the database was shown to fail on a partitioned table, and a per-tenant unique sequence key is impossible on one. green The design checks the timestamp instead of rewriting it, and the head-row lock replaces the unique key.
  • Review: the Technical Architect, the Security & Multi-Tenancy Reviewer and the Postgres Specialist each raised blocking items in round 1 and approved in round 2. Their conditions are written into the ADR as rules. No isolation gap was found between customers.

9. Words used on this page

Transaction
A group of database writes that either all happen or none do.
Tenant
One customer organisation. Its data is walled off from every other tenant.
RLS (row-level security)
The database rule that makes every query see only the current tenant's rows.
Hash / fingerprint
A short value computed from data. Any change to the data changes it.
Sealer
The background job that links new audit entries into the chain.
Stub line
An export line carrying only an entry's number and fingerprints, so the chain can be checked without revealing that entry.
Outbox / relay
Our only safe way to start background work: write a row with the change, and a relay process starts the job from it.
Partitioning
Storing a big table in time slices, so old slices can be archived cheaply later (Epic 30).
