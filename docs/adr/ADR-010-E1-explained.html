ACCEPTED · 2026-11-19 ADR-010-E1 · issue TICK-993 · amends ADR-010 test list and RFC-022 CI-6 · source: PR #765 (TICK-938)

Converted access rules give the same answers, but two pieces of their SQL are written differently

In three sentences. (1) ADR-010 promised that old-format access rules, converted to the new format, would produce exactly the same database query text as before, so a test could catch any accidental change. (2) In 8 of 48 test cases the new query is written differently in two harmless ways. It means the same thing, and in one case it lets the database pick a better index. (3) We change the test to allow exactly those two rewrites and nothing else, and we record that one of them can change the database's plan, measured as the same speed or faster.

1. The problem in plain words

An access rule decides which tickets a user can see. ADR-010 introduced a new rule format. Tenants' existing rules (format 1) are converted to it in memory when they are read. For ticket lists, the rules become a SQL filter split into branches, one per alternative ("I raised it", "it is assigned to me", "it is shared with my group"), so the database can use a separate index (a lookup structure, like a book index) for each.

The safety test CI-6 compared the converted rules' branches with the old ones: same number of branches, same SQL text, same bind arguments (the values sent alongside the query, such as the user's id). In PR #765 the branch count matched in all 48 cases. The text and arguments differed in 8.

2. Why rewrite (b) can change the plan, and why that is fine

The database's planner estimates how many rows each condition keeps, then picks the cheapest index. In the affected branch, the rule says "assigned to me" twice: once as the subject, and once in an extra condition. In the old form, one was a list test (= ANY) and the other a plain equality, so the planner did not see that they were the same test. It counted it twice, guessed about 1 row, used the assignee index, and then threw away 1,280 rows. In the new form both are plain equalities. The planner recognises them as one test, guesses correctly, and uses the requester index instead (40 rows thrown away).

3. Options considered

OptionVerdict
A: allow exactly the two named rewrites in the testChosen: no code change, the test stays exact everywhere else, and it still catches regressions in every fixture.
B: change the code so the text is identicalRejected: it rewrites every converted rule, and breaks a planner rule ("constants only at the top") that both the database filter and the Go check rely on, only to keep text the database ignores or plans worse.
Skip the 8 cases in the testRejected: the skipped fixture is the only one that exercises every kind of subject together, so a permanent skip would hide future bugs.
Allow "any text that means the same"Rejected: not testable. A reviewer could not tell an allowed change from a bug.

4. The decision

Converted old-format rules produce the same number of branches, and the same SQL text and bind arguments, up to two rewrites: (a) a constant true is removed; (b) a "the caller" condition renders as = $n::uuid with a single-id argument, where the old code used = ANY($n::uuid[]) with a one-item list. Rewrite (b) can change the index chosen within a branch; it was measured as neutral or faster. The test normalizes (a) and (b), and never skips a case.
E1-1: rewrite (a) is allowed
The database drops it before planning. Same plan in every measurement.
E1-2: rewrite (b) is allowed, and the plan change is admitted
Same rows. It may pick a different index; measured the same or faster on two data shapes.
E1-3: the test enforces it
Before PR #765 merges, the "pending" skip is replaced by a comparison that rewrites the old expected text in exactly these two ways, and only for the caller's own id. Turning a real multi-value list into a single value would still fail the test.
E1-4: no code change
The planner and converter stay as they are in PR #765.

5. The fix and migration

No migration and no data change. Only the test's rule changes, inside PR #765 (TICK-938). Stored access rules are untouched.
