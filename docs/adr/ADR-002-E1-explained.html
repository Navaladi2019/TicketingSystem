ADR-002 erratum E1, explained

The whole decision in three sentences. (1) To let the /me endpoint read a user's group paths, ADR-002 switched off a set of code-safety checks for the whole file that endpoint lives in. (2) We replace that with an exemption on the one line that needs it, plus a small CI script that fails the build if anyone moves, copies or widens that exemption. (3) You accept one small residual: the same line of code could be moved into a different handler in that file, and only code review would notice.
How serious is this? Low, and not exploitable today. No tenant can see another tenant's data through this; group paths are the caller's own tenant's display text. The point is to stop a guardrail from quietly being off for the file where new API handlers get written.

Terms used here

linter
A tool that reads source code and fails the build when it finds a forbidden pattern. We run golangci-lint, which bundles many linters.
forbidigo
The linter that bans specific calls. We use it for three rules: no raw HTTP client (use our instrumented one), no logging of database query parameters (otelpgx), and since ADR-002, no reading of group paths (GroupPaths) except by /me.
exclusion
A line in .golangci.yml that turns a linter off for a whole file or folder.
//nolint directive
A comment in the code that turns a linter off for one line. If it sits on its own line above package or func, it covers the whole file or function instead.
nolintlint
A linter that checks the //nolint comments themselves: that they name a linter, give a reason, and actually suppress something.
gate
A short CI script that fails the build when a fixed condition is not met.
generated-file header
The comment // Code generated ... DO NOT EDIT.. golangci-lint skips every linter on a file that carries it, because machine-generated code is not hand-reviewed.

1. The problem in plain words

ADR-002 made group paths (names like /service-desk/tier-2) display-only: they may be shown to the user, never used to decide what someone may do. To enforce that, a lint rule forbids calling GroupPaths anywhere, and exactly one place, the GetMe handler behind GET /api/v1/me, is allowed.

The linter cannot say "allowed in this one function". So ADR-002 turned forbidigo off for the whole file internal/server/api.go. That also turned off the other two rules for that file. A new handler added to api.go could use a raw HTTP client, log query parameters, or read group paths, and CI would stay green. The Security & Multi-Tenancy Reviewer flagged this on TICK-268 (finding 2, Low).

2. Why "just put a comment on the line" was not enough

The first draft (RFC-006 rev 0) moved the exemption onto the one line and counted that there was exactly one such comment. Both reviewers broke it in round 1, and both found a third trick in round 2:

TrickWhat it doesWho found it
Move the one comment above package serverSame comment count, but now it exempts the whole file againBoth reviewers, round 1
Move it above func GetMeExempts the whole functionTechnical Architect, round 1
Write //nolint:FORBIDIGO or //nolint: forbidigoThe linter honours it; a simple text count does not see itTechnical Architect, round 1
Add // Code generated by hand. DO NOT EDIT. to api.goEvery linter skips the file, with no config change and no new commentBoth reviewers, round 2 (F3)

3. Options considered

OptionResult
Keep the file exclusionrejected It is the finding.
Narrow the exclusion to the GroupPaths messagerejected Still the whole file for GroupPaths.

One-line comment, pinned word for word by a CI gate that also checks the config and generated-file headerschosen About 50 lines of shell script. Every trick fails the build.
A custom code check that allows only the GetMe functiondeferred The ideal shape, about 60 lines plus tests. Worth it when a second exemption is needed.

4. The decision

ADR-002-E1, Decision (abridged to its four steps)
  1. No forbidigo exclusion for internal/server/api.go.
  2. One line-scoped waiver. raw, err := h.paths.GroupPaths(ctx, p.TenantID, p.PrincipalID) //nolint:forbidigo // ADR-002: GetMe is the one allowed GroupPaths caller
  3. nolintlint enabled, with require-specific: true, require-explanation: true and allow-unused: false.
  4. scripts/ci/nolint-allowlist.sh, run from make lint, with three checks. Each one fails closed: Directives, Config, Generated files (F3).

5. What changes, and how

There is no runtime change. One Delivery task, created by the CTO after you sign, does five things:

  1. Deletes the two-line api.go exclusion from .golangci.yml and turns on nolintlint.
  2. Adds the comment to the one call line in GetMe.
  3. Adds scripts/ci/nolint-allowlist.sh to make lint, with the PR showing it red before and green after. It must also show each trick from section 2 failing.
  4. Keeps the existing lint fixture count at 6.
  5. Deletes the one existing //nolint comment that nolintlint reports as unused (in a test file).

ADR-002's signed text is not edited. This erratum sits beside it and replaces its "Lint rule" row and its residual R-b.

This replaces ADR-002's R-b, which was much wider: any handler in api.go could read group paths, and all three rules were off for the file.

8. Platform invariants

These were checked against the nine invariants in ADR-001 §1. The change touches lint configuration, one comment and one CI script. It touches nothing that runs in production. I5 (one authorization layer) is strengthened: the rule that keeps group paths out of authorization now has a one-line gap instead of a whole-file gap. The other eight are not touched.
