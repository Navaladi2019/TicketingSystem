ADR-001 amendment A6, explained

In one sentence. The signed blueprint (ADR-001) lists every database role and what it may touch. The new audit log needs three narrow additions to that list. None of them weakens the wall between customers or changes how background jobs are started.

1. Why an amendment at all

ADR-001 is signed, and its role table and outbox rules can only change through an amendment. ADR-004 (the audit log) was designed to need as little of this as possible. Three things could not be avoided.

2. The three additions

#WhatWhyHow it is kept narrow
A6.1A new role, nava_erasurePrivacy erasure (Epic 30) must blank personal data in audit entries. No existing role may change audit entries, and that rule must stay true for them.It runs inside one customer at a time. It can blank only the four erasure columns, once per entry, and every erasure writes its own audit entry. It cannot even read the data it erases. Its password lives only with the job runner, never on application servers.
A6.2Onboarding may book the first run of the audit sealerThe sealer keeps itself alive by booking its next run. Something has to book the first one when a new customer is created.Onboarding may insert only a sealer booking (kind = 'audit.seal'), and only for the customer it is still setting up. It cannot read the outbox table.
A6.3A rule for background jobs not tied to a ticketThe blueprint's booking rules assume every job belongs to a ticket. The sealer belongs to a customer's audit chain instead.The job id format, the relay and the start options are unchanged. Only the bookkeeping differs: the sequence number comes from the chain's own head row, and no ticket link is written. The sealer advances that number; the manual restart (chain:reseed) reuses it as is, so only the sealer can ever change it.

3. What does not change

  • The list of database policies that may look across customers stays at 10. None is added.
  • Background jobs are still started only by the relay, from a row committed with the change that caused them.
  • The job id scheme is unchanged.
  • Adding the sealer to the Temporal server's list of allowed job types is a separate policy change with Security review, under amendment A1. It is not part of A6.

4. What we are accepting

AR-TICK-409-06 Whoever holds the nava_erasure password could blank audit details and record an erasure entry for it. That would be visible as an erasure, but the detail would still be gone. Mitigation: the password lives only with the job runner. Revisit if anyone else ever needs it.

5. Evidence and review

  • The Technical Architect checked A6.3 against the relay code (internal/relay/relay.go, internal/relay/dispatch.go, internal/outbox/outbox.go) and confirmed it conforms to the blueprint's start rules (D22).
  • Security confirmed A6.1 and A6.2 are as narrow as needed, after four tightenings that are now written into the amendment and ADR-004.

6. Words used on this page

Role
A database login with a fixed list of permissions.
Outbox / relay
The outbox is a table where background work is booked, in the same transaction as the change that needs it. The relay is the process that starts the work.
Sealer
The background job that links audit entries into a tamper-evident chain (ADR-004).
Provisioning
The state of a customer account while it is still being set up.
