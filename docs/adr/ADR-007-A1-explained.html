ACCEPTED · 2026-11-14 ADR-007-A1 · issue TICK-843 · RFC-018 rev 1 · amends ADR-007 D1 and D13 · trigger: spike S1 (TICK-806) FAIL · evidence: S1, S1b

Host apps always say which organization they sign the user in for

In one sentence. When another company's application embeds our platform, it must tell our sign-in service which customer (tenant) the user is signing in for, every time. The platform gives it that value, computed from the tenant's own id. Without this, a user who belongs to two customers could not sign in the first time, because the sign-in service had no way to ask them which one.

Words used here

Tenant and organization
A tenant is one customer of the platform; its data is walled off from every other tenant. In Keycloak (our sign-in service) each tenant is an organization with a short name, its alias, for example t-<tenant id>.
Host app and embedding client
Another application that shows our screens or calls our API for its users (ADR-007). Each one is registered as a Keycloak client; we call it an embedding client.
Token and organization claim
After sign-in, Keycloak hands the app a signed token. Its organization claim says which organization the user signed in for. Our API trusts only that signed value to choose the tenant.
Resolve
The platform code that checks a token and picks its tenant. It insists on exactly one organization in the token, otherwise it refuses with 401 tenant_unresolved. This amendment does not change it.
Brokered sign-in and IdP hint
Customers sign in with their own company login (their identity provider, IdP). Keycloak passes the user on to it ("brokers"). The IdP hint (kc_idp_hint) tells Keycloak which company login to use, so the user is not asked.
Picker
A Keycloak page that asks a user in several organizations to choose one.
Spike
A short, timeboxed experiment against the real software to settle a question of fact.

The problem

ADR-007 allowed a host app to ask for "any organization" and rely on Keycloak's picker for users in more than one. Spike S1 showed this does not work on a user's first sign-in through their company login: Keycloak sends the user to the company login before it would show the picker, and when they come back it does not know which organization they meant. The token carried no organization at all, so our API refused it (3 of 3 runs, in Chrome with third-party cookies blocked and in Safari's engine). Nobody was let into the wrong tenant. The user was simply locked out.

Options considered

OptionWhat the evidence showedOutcome
1. The host always names the organizationWorked in S1 for exactly the failing case: a two-organization user, first sign-in, organization named, landed in the right tenant in both browsers.Chosen
2. Our SDK retries the sign-in after the refusal, so the picker appearsThe picker only appears once a Keycloak session exists; the full retry loop was never tested.Rejected: our widget must never run sign-in itself (ADR-007 D7), and it risks redirect loops.
3. Change Keycloak's sign-in steps to show the picker earlierNot tested, and Keycloak's source shows the picker needs a user that does not exist yet on a first sign-in.Rejected: cannot work, and it would change sign-in for our own web app too.
4. Keycloak's "redirect by email domain" settingNot tested; it addresses a different problem (being asked for a username).Rejected; no spike planned.

The decision

  • Every host app sign-in request names the organization (organization:<alias>) and, normally, the company login to use (kc_idp_hint).
  • The host gets both values from our API when the customer turns the host app on (GET or PUT /api/v1/embedding-clients/{client_id}). The platform computes them from the caller's own tenant id and reads no table, so it cannot hand out another customer's values.
  • The new GET is for tenant admins only, answers "not found" identically whether the host app exists or was never enabled by this tenant, and is audited. A PUT that tries to set the two values is refused (400 unknown_field).
  • Nothing changes in how the API decides the tenant, in the Keycloak configuration, or in our own web app.

What happens when the host names the wrong organization

This was the second open question from S1, now settled by Keycloak's source code and a second spike, S1b. In every case no token ever lets the user into a tenant they are not in.

SituationWhat the user seesEvidence
Wrong organization, no company-login hintKeycloak's own username/password form, a dead end for a company-login user (residual RR-A1-1)S1 (with an existing session) and S1b (without)
Wrong organization, with the hintSign-in completes, but the token names no organization and our API refuses it (401). The host can show an error.S1b, 3/3, for host apps and for our own web app
Organization that does not existKeycloak sends the host an invalid_scope error at onceS1b
A brand-new user signs in for the first time with the wrong organizationRefused this time; they are still added to their own organization, so the next correct sign-in worksS1b, 3/3. This disproved a feared risk (RR-A1-5), now withdrawn.

The fix and the rollout

  • No migration. The two computed values and the new GET are added in the story that builds the embedding-client endpoints (TICK-815). The stories S23 and S26 stay parked until this amendment is accepted and the plan (PLAN-008) is updated.
  • Tests that previously expected a refusal for a wrong organization are rewritten to the behaviour above (CI-E2, new CI-E14 a–d, CI-E15, CI-E16 a–g). Each also checks the one rule that matters: no token names an organization the user is not in.
  • Our two demo customers in the development setup use hand-picked names, not computed ones. They stay as they are. Tests of Keycloak's behaviour keep using them; tests of the computed values and the acceptance kits use customers created through the normal onboarding process, set up by a small script.

Evidence

  • S1 (TICK-806, docs/adr/ADR-007/spikes/s1-host-client-token.md, PR #652): bare "any organization" failed on the first brokered sign-in, 3/3, both browsers. Naming the organization passed. red
  • S1b (TICK-843, docs/adr/ADR-007/spikes/s1b-hinted-wrong-alias.md and s1b-raw.log): with the hint, a wrong organization gives a token without an organization and a 401, 3/3, for both client types; a first-time user still joins their own organization. green for the behaviour adopted here.
  • Reviews: Security found that reading the values from a database table could leak another customer's login name; computing them from the tenant id fixed it (approved on re-check). The Technical Architect checked Keycloak 26.8.1's source for every case and ran S1b. The CTO adopted S1b as measured.
