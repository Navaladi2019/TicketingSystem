Access rules: smaller limits, a size limit, and saving only from the API

In one sentence. An access-rules document may now hold at most 128 tests and 32 KiB of text, and only the API's own database login may save one; this keeps ticket lists inside their time budget, keeps saving a document cheap even for a hostile one, and removes a save path that nothing uses and that the security check could not handle.

Words used here

Access-rules document
For each ticket type, a tenant admin saves one document that says who may read or change which tickets (ADR-010). It is made of conditions (named yes/no tests) and policies that combine them with and/or/not.
Leaf
One basic test inside a document, for example "the ticket's state is new" or "the user is in group X". A policy that uses a condition counts that condition's leaves.
Cap
A fixed upper limit the platform enforces on every document, the same for every customer. A document over a cap is refused when the admin saves it.
Publish
Saving a new version of the document. It writes one row to the database table acl_versions.
CHECK and trigger
Two database-side safety nets on that table. The CHECK re-validates the document's shape and caps. The trigger confirms every user, group and org-unit id in it belongs to the same customer. They run even if the application code has a bug.
Database login (role)
Each service connects to the database as its own login with its own rights. nava_app is the API's; nava_worker is the background workflow worker's.
I3
A platform rule (ADR-001): database rights are per role, and no function may run with its owner's rights instead of the caller's (SECURITY DEFINER is banned), so no function can quietly bypass the tenant wall.
p50 / p95
The median time, and the time that 95 % of attempts beat.

The problem

ADR-010 introduced composable access rules and set provisional limits: up to 1,024 tests per document. It asked a measurement (SP-2) to confirm them before the feature ships. SP-2 found three things:

  1. 1,024 tests is too many for the ticket list. Every list request turns the rules into one database filter. At 256 tests a single page already takes the whole 150 ms list budget; at 128 it stays at 44 ms or less.
  2. The limits counted tests, not size. A document could stay inside every limit and still be 1 MiB, padded with unused conditions or very long id lists. Checking such a document on save took 0.15 to 0.6 s.
  3. The background worker had the right to save a document, but the id check could not work for it. The worker's login cannot see users, so the check would refuse every user id. The usual fix would break I3.

Options considered

QuestionOptionsChosen
How many tests?Keep 1,024; 256; 128128: the measured point where a list stays in budget. Real documents today use at most 4 branches.
How to bound size?Separate limits on unused conditions and on ids per test; a byte limit of 16, 32 or 64 KiBOne byte limit, 32 KiB. One number covers every way to make a document big. 16 KiB is too tight for real id lists; 64 KiB doubles the worst case for nothing.

The decision

  1. Limits: nesting depth 8, 16 items per group, 64 policies, 128 tests per policy and per document.
  2. Size: the saved document is at most 32,768 bytes, counted on the database's own text form of the document. The API refuses a larger one with a clear error (422 document_too_large, pointing at /rules) before touching the database. A separate database rule refuses it too, and does so before the expensive shape check runs.
  3. Who saves: only nava_app may insert into acl_versions. The worker keeps read access, loses write access and loses the right to run the check functions. If a future feature needs the worker to save rules, that needs its own amendment.

The evidence

We built the largest documents of seven different shapes that fit in 32 KiB and timed saving each one, with the size rule and the 128-test limits in place, on PostgreSQL 16.10 (two runs, on a busy shared machine, so each figure is a range):

The size rule works exactly at the boundary: 32,768 bytes is accepted, 32,769 is refused. The earlier estimate for the worst case was 10–15 ms; the measured worst case is higher, about 17–41 ms, because the checks walk every reference in the document. It is still about 15 times cheaper than before, and it only affects an admin saving rules, never a user listing tickets.

For the save-rights change, we traced every place that saves an access-rules document: the access API and tenant onboarding. Both connect as nava_app. No worker code saves one.

What we are accepting

  • A hostile admin can make one save cost up to about 70 ms of database time, in their own tenant only. Saving is admin-only and versioned. We will revisit if the worst case passes 100 ms, or if a tenant saves more than once a second for a minute.
  • The API and the database count the size separately. A test checks that they agree. If they ever disagree, the database refuses with the same error the admin would have seen, so the only effect is where the refusal comes from.
  • A future need for the worker to save rules will need a new decision, because the id check must be able to see that tenant's users as the worker.
  • The separate masks part of the row (which fields are hidden) has no byte limit yet; the 1 MiB request limit still bounds it.
