PROPOSED · REV 1 · 2026-11-19 ADR-010-A1 · issue TICK-971 · amends ADR-010 D4 and R6 · source: SP-2 report (TICK-933, PR #727) · evidence: SP-2, A1 cap bench at 32 KiB and 128 KiB

Access rules: smaller limits, a configurable size limit, and saving only from the API

In one sentence. An access-rules document may now hold at most 128 tests. The document and its field-hiding rules may each be at most 32 KiB of text, a number the platform operator can change for the whole installation. Only the API's own database login may save one. Together these keep ticket lists inside their time budget, keep saving cheap even for a hostile document, and remove a save path that nothing uses and the security check could not handle.

Words used here

Access-rules document
For each ticket type, a tenant admin saves one document that says who may read or change which tickets (ADR-010). It is made of conditions (named yes/no tests) and policies that combine them with and/or/not, and it is stored in the rules column. It is not a ticket: nothing here limits tickets or their data.
Masks
The rules, saved alongside, that hide individual fields from some users. They are stored in the masks column of the same row.
Leaf
One basic test inside a document, for example "the ticket's state is new" or "the user is in group X".
Cap
A fixed upper limit the platform enforces on every document. A document over a cap is refused when the admin saves it.
Operator setting
A value that the people who run the installation set in its deployment configuration (an environment variable). Tenants and their admins can neither see nor change it.
Publish
Saving a new version of the document. It writes one row to the database table acl_versions.
CHECK and trigger
Safety nets inside the database on that table. A CHECK re-validates a value. The trigger confirms that every user, group and org-unit id belongs to the same customer. Both run even if the application code has a bug.
Database login (role)
Each service connects as its own login, with its own rights. nava_app is the API's login; nava_worker is the background workflow worker's.
I3
A platform rule (ADR-001): database rights are given per role, and no function may run with its owner's rights instead of the caller's (SECURITY DEFINER is banned).
p50 / p95
The median time, and the time that 95 % of attempts beat.

The problem

ADR-010 introduced composable access rules with provisional limits (up to 1,024 tests per document) and asked for a measurement, SP-2, to confirm them. SP-2 and the review found three problems:

  1. 1,024 tests is too many for the ticket list. At 256 tests one list page already uses the whole 150 ms budget. At 128 it stays at 44 ms or less.
  2. The limits counted tests, not size. A document inside every limit could still be 1 MiB, padded with unused conditions or long id lists, and took 0.15 to 0.6 s to check. The review found the same for masks: 1 MiB of masks took about 0.3 s.
  3. The background worker could save a document, but the id check could not work for it, and the usual fix would break I3.

The decision

  1. Test limits: nesting depth 8, 16 items per group, 64 policies, and 128 tests per policy and per document. These are not configurable.
  2. Size limit: the rules and the masks may each be at most NAVA_ACL_MAX_DOCUMENT_BYTES, an operator setting. The default is 32 KiB, and the allowed range is 16 KiB to 128 KiB. Any other value stops the API from starting. The API refuses a larger document with a clear error before touching the database: 422 document_too_large, pointing at /rules or /masks.
  3. Database safety net: the database refuses anything over the 128 KiB ceiling, whatever the setting, and does so before any expensive check runs. It does not read the setting itself, because the API's own login could change such a value and then it would be no safety net.
  4. Who saves: only nava_app may insert into acl_versions. The worker keeps read access but loses write access and the right to run the check functions.

The evidence

We built the largest rows of nine shapes that fit under the limit and timed saving each one with every check in place. We did this at the default (32 KiB) and at the ceiling (128 KiB), twice, on PostgreSQL 16.10. The machine was shared with about 30 other containers, so each figure is the range over the two runs.

The limit works exactly at the boundary for both the rules and the masks: a document at the limit is accepted, and one byte more is refused. The worst row costs at most about 90 ms at the default and at most about 340 ms at the ceiling, which is why the ceiling is 128 KiB. It only affects an admin saving rules, never a user listing tickets.

For the save-rights change, we traced every place that saves an access-rules document: the access API and tenant onboarding. Both connect as nava_app. The Technical Architect and the security reviewer each reproduced the trace.

What we are accepting

  • A hostile admin can make one save cost up to about 90 ms of database time at the default, and about 340 ms if the operator raises the limit to the ceiling. The cost falls on their own tenant only. We revisit if the worst case grows past 10× a realistic save at the default, or 50× at the ceiling, measured on the same machine in the same run (3–4× and 19–27× today).
  • The database's safety net is the ceiling, not the operator's value. A code path that skipped the API's checks could save up to 128 KiB. Only the API's login can save, and both of its callers go through the checks.
  • The API and the database count the size separately. A test checks that they agree. If they ever disagree, the admin sees the same error, from the database instead.
  • Lowering the setting leaves already-saved documents in place. Re-saving one that is now too big gets the error.
  • A future need for the worker to save rules will need a new decision.
