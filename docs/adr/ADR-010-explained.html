QuestionHow can tenant admins build ticket and workflow access rules from reusable pieces (AND, OR, NOT), without code, while keeping the database filter and the single-ticket check giving the same answer?
DecisionAdmins write named conditions and combine them into named policies, all stored as one versioned document per ticket type. Rules only ever grant access. A broken rule is refused when it is saved, and if one ever reached the database it would grant nothing.
Not decided hereWhether the later workflow expression language (Epic 10) builds on this format (open, owner: CTO). Rules on tenant-defined fields wait for TICK-900.

1. In plain words

Goal: what are we trying to do?

Let each customer's admin decide who may see and work on which tickets by combining simple, named building blocks. For example, the admin can write "managers in the assigned group may work on a withdrawal request, but not if they raised it themselves", without anyone writing code.

Today: how is it done now, and what are the limits?

Today a rule is a flat list: "these people may see tickets where all of these things hold". There is no "or" and no "not", so separation of duties cannot be written. Nothing can be reused, so the same idea has to be copied into every rule. Adding these later without a design would mean rewriting the code that applies rules, and the test that proves the database and the program agree.

What's new, and why we expect it to work

Admins name a condition once, such as is_requester, and use it in many policies. A policy combines conditions with AND, OR and NOT. Every rule only adds access, so the outcome never depends on the order of the rules. The rules are a small, fixed set of building blocks, and each block has exactly one translation into a database filter and one into a program check. That is why the two can be tested against each other on thousands of random cases, which we already do for today's rules.

Who is affected

Tenant admins get composition, reuse and clearer explanations. Support agents and the people who raise tickets see no change until an admin edits rules: existing rules are converted automatically and behave the same. Operators, the people who run the platform, get three new counters on their dashboards and a small change to the directory sync, the job that copies users, groups and org units from the login system every few minutes. Engineers on Epic 03 and Epic 06 build the pieces in the plan.

Risks: what could go wrong, and what we accept

Region-based access ("tickets from my part of the organisation") could be slow for very large organisations. A short experiment, a spike, measures this before we build. A user who moves between org units keeps their old region access until the next directory sync, which is within 10 minutes, the same as for groups today. Size limits on rules could block an unusually large policy.

How we'll know it worked

Mid-way: two spikes, one on region access speed and one on the save-time check's cost. At the end: the random agreement test passes, including the new NOT and empty-value cases. Every existing rule gives the same answers and the same database filter as today. The 800,000-ticket benchmark stays within 150 ms. A deleted org unit no longer stops the directory sync.

Condition
A named yes/no test about a ticket and the person asking, such as "I raised this ticket".
Policy
A named rule that grants an action (read or write) when its combination of conditions is true.
Allow-only
Rules can only add access, never take it away. You get access when any policy says yes.
Database filter (SQL predicate)
The rule translated into the "WHERE" part of a database query, so a list only ever contains tickets you may see.
Agreement test
A test that builds thousands of random rules, users and tickets and checks that the database filter and the single-ticket check in the program always agree.
Tombstone
Marking a row as deleted instead of removing it, so things that point at it keep working.
Org unit
A branch of the customer's organisation chart, such as a region or an office. Units form a tree: "my region" means my unit and everything under it.
Directory sync
The job that copies users, groups and org units from the login system into the platform every few minutes.
Explainer
The admin screen that answers "can this user see this ticket, and why".
Spike
A short, time-boxed experiment that measures something before we commit to building it.

3. Options considered

OptionResultWhy
Named conditions and allow-only policies in one versioned document per ticket typechosenNo new table or cache. A condition change is one atomic version, and everything reuses today's proven engine.
One condition library shared across all ticket typesrejectedOne edit would spread across many documents and versions, and need another table and publish path. We revisit if admins copy the same condition across more than 3 types.
"Deny" rules that override "allow" rulesrejectedRanking rules is a new way for the database filter and the program check to disagree. "Allow, AND NOT x" covers every case in the brief.
A text rule language typed by adminsrejectedIt would put a parser in the security path and need its own "safe subset" checker. A friendly text form can be added later on top of this format.
Region checks by joining an org-tree table inside each queryfallbackKept as plan B if the spike shows the chosen approach is too slow.

4. The decisions that close the review findings

FindingRiskFix
B1: a broken building block under NOT"NOT broken" could have read as "NOT false", which is true, and that would grant every ticket.A broken block voids the whole policy, which then grants nothing. "Broken" is never treated as true or false.
B2: deleting an org unitWith a ticket still pointing at the deleted unit, the directory sync would fail every time, and removed users would keep their access.Org units are marked deleted (tombstoned), never removed. Tickets under a deleted unit lose region access.
B3: speed of existing rulesConverted rules would lose today's fast list plan: 38 to 166 ms per page instead of 2 to 4 ms.Converted rules are split exactly as today. A test checks the database filter text is unchanged, up to a limit the spike measures.

Who sets a ticket's org unit: it is set when the ticket is created, from the requester's main org unit. After that it is an ordinary stored field, protected and audited like any other. Tickets do not move when a person changes unit; moving them is a workflow step.

5. Migration of today's rules

Nothing stored is rewritten. When an old rule is read, it is translated in memory into a policy with the same name and the same meaning. The next save stores the new format. A test runs every old rule shape through both engines and requires identical answers and an identical database filter.
