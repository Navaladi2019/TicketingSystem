ADR-004 erratum E1, explained

The whole decision in three sentences. (1) Two earlier decisions require the platform to write an audit row when a workflow loop is stopped, but the audit log's fixed list of allowed actions had no name for either row. Written the obvious way, one of them would also have clashed with the record's own audit row. (2) We add two action names and one new kind of subject, a fingerprint of the loop, so that every row fits the log's rules and the record still needs its own row. (3) Separately, the flag that says "this change description was cut because it was too large" becomes part of each row's tamper seal, so nobody can flip it unnoticed.
How serious is this? A gap in the specification, found while planning. No code is wrong and nothing has shipped. The audit log is still empty. Without this erratum, the engineers building the write pipeline (P5-12b, P5-13b) and the export format (PR #365) would each have had to guess.

Terms used here

Audit log
The one append-only table (ADR-004) that records every change to records and configuration. Each row says who did what to which subject.
Subject
The thing a row is about, as a pair: a type (for example record) and an id.
Cascade
A record change starts a workflow, the workflow changes a record, and that may start another workflow. ADR-001 limits how far this can go.
Cycle (suppressed start)
Workflow D would start a second time on the same record from the same original user action. The platform skips that start, lets the change through, and writes a cascade_cycle row (ADR-001-A5).
Too deep
A chain of changes goes past the depth limit of 8. The change is refused, and a cascade_too_deep row records the refusal.
Origin O
The id of the original user action that a cascade started from.
Unique key
A database rule that allows at most one row per (transaction, subject, version). Two rows with the same values make the whole transaction fail.
Commit check
At the end of every transaction, the database confirms that each changed record has its own audit row. A change without one is refused.
Envelope / hash chain
The fields of a row that are fingerprinted and linked to the previous row's fingerprint. Editing any envelope field breaks the chain, and the offline verifier reports the row as tampered.
UUIDv5
An id computed from its inputs: the same inputs always give the same id, and different inputs give different ids.

1. The problem

ADR-004 closed the list of allowed audit actions so that every row can be filtered by a fixed spelling. Two later rules each require a row whose action is not on that list:

  • ADR-001-A5: when a workflow loop is stopped, write one row naming the origin, the record and the workflow definition. The row goes in the same transaction as the record change.
  • PLAN-003 D-3-7a: when a change is refused for being too deep, write one row that survives even though the change itself is rolled back.

The fingerprint uses a namespace id fixed for this purpose only. It is computed in Go in one place, and the verifier recomputes it the same way. Postgres did not have to change.

The one blocking review finding. If the same workflow matched one change twice, two identical loop rows would clash and roll back the user's change. The rule now says the pipeline records each (origin, record, workflow) at most once per change. Test CI-A17 (f) proves it.

Item 2: the "diff was cut" flag is sealed

Decision text (R1)
The envelope gains diff_truncated (boolean, always emitted): 22 members. Past 64 KB, diff keeps whole RFC 6902 ops only: the longest prefix of ops whose single Go serialization fits in 65,536 bytes, stored verbatim and never re-serialized. diff_sha256 = SHA-256(diff_salt ‖ stored diff bytes). Erasure leaves the flag unchanged.

A change description over 64 KB is shortened and flagged. If the flag sat outside the seal, someone could switch it off, and a cut description would pass as complete. Switching it on would falsely suggest that something was removed. Only the description and its salt stay outside the seal, because erasure for privacy must be able to remove them without breaking the chain. The flag is never erased, so it goes inside.

4. What changes, and for whom

  • No data migration. The audit log is empty until P5-13b.
  • PR #365 (export format and golden vectors): it freezes the 22-field envelope, plus test vectors for a cut diff and for the fingerprint.
  • P5-03 (verifier): a flipped flag reports as tampered.
  • P5-13 (pipeline switch): one rename (cascade_rejected becomes cascade_too_deep) and two extra columns in a read that already happens.
