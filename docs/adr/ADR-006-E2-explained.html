ACCEPTED · rev 1 · 2026-11-22 ADR-006-E2 · issue TICK-1094 · amends ADR-006-A2 (A2-2, A2-3, A2-8) · source: spike S-A2-cancel runs 5 and 6 (TICK-1083, PR #851)

The count's time limit drops to 170 ms, and the count stops using parallel workers

In three sentences. (1) A list page shows "how many records match". Since amendment A2, that count has a fixed time limit. If the limit runs out, the page still loads and shows "50+" instead of a number. (2) A2 promised that a cancelled count stops within 15 ms. Two new tests found it can take up to 46 ms when the count had written temporary files, and up to 71 ms when it ran on parallel worker processes. (3) We lower the limit from 200 to 170 ms to pay for the first case. We remove the second case by running the count without workers, provided that a measurement before merge shows this doesn't make more counts miss the limit.

1. The problem in plain words

A list request does two things. It fetches one page of records, and it counts the matching records the user may read, up to 1,000. The count can be slow when the user may see only a few of many matches. So A2 gave it a time limit, CountBudget, of 200 ms. The limit is enforced by the database's own statement timeout, which cancels a query that runs too long. The whole request must stay under 350 ms at the 95th percentile (p95: 95 of 100 requests are faster).

The 200 ms came from a sum: 350 ms, minus 94 ms for the page, minus 6 ms for two extra network round trips, minus a 35 ms safety margin. It assumed that a cancelled count stops almost at once, within 15 ms. A2 set a test, spike S-A2-cancel, to check that. Its rule: if a count overshoots by more, subtract the measured overshoot from the budget.

The first runs passed on a simple plan. The Technical Architect then asked for two harder cases:

Spill
A sort or hash table too big for its memory (work_mem) writes temporary files to disk. When the database cancels such a count, it must first close and delete those files.
Parallel
The database can split one query across parallel workers: extra processes whose results a plan step called Gather collects. When it cancels such a count, it must wait for every worker to stop.

3. The decision

  1. Budget 170 ms. 350 − 94 − 6 − 35 − 40 = 175, rounded down to 170. The 40 ms is run 5's spill overshoot (45.9 ms), less the 6 ms of round trips already counted. That is a deliberately cautious figure: run 5's machine failed its quiet-host check, and the only clean run measured 27.8 ms (which would allow 190 ms). Erring this way can only make the page faster; the cost is a few more "N+" totals. If those rise, one clean 10-minute rerun can give back up to about 20 ms.
  2. No parallel workers for the count. The command that opens the count already sets its time limit. It now also says "use no workers" (SET LOCAL max_parallel_workers_per_gather = 0). It is the same single message to the database, so it costs nothing extra. The count ends by rolling back to a savepoint (a bookmark inside the transaction), and that undoes both settings. The page query keeps the normal settings.
  3. A real leak check. The old test read a counter of temporary files created, which can't show one left behind. The new test lists the files that exist (pg_ls_tmpdir()), after the run and 60 s later. Runs 5 and 6 found none.

4. The check before it ships

One fact cuts against choice 2. Under the database's own settings, a count shaped like a band (ii) list (a broad filter, a narrowing access rule) already uses workers: it finished in 94.5 ms with two of them. Without workers it may take longer. We have not measured how much longer. The only serial figure we have (192 ms) came from forced low-memory settings, so it overstates.

So the change is gated on a measurement, A2-8 (3e). On a fresh, quiet stack with 8 users at once, it compares (A) no workers with 170 ms against (B) workers with 140 ms. The two arms run in alternating 15-second blocks (A, B, B, A), each checked for a quiet host, so that machine drift does not land on one arm only. That gives about 800 requests per arm. Choice 2 stands if (A) leaves the count without a number no more often than (B), allowing for chance: the margin is twice the statistical error of the difference, and at least 1 percentage point. The whole band (ii) request must also stay within 350 ms. A plan check confirms that (A) really runs without workers and (B) with them. If (B) gets no workers at all on the test machine, the result is reported as inconclusive and choice 2 stands, because it removes a slow cancel that no clean run has ever bounded. If (A) is clearly worse, we fall back to 140 ms with workers on, after one clean 10-minute rerun to pin down the parallel figure.

5. The fix and migration

A two-line code change on the S21 story branch (internal/records/store/list.go): the constant becomes 170 ms, and the savepoint command gains the worker setting. Tests check that the setting is 0 inside the count and back to normal after it, including on the next request that reuses the connection. Nothing is stored, so there is no data migration. The S21 acceptance kit is rerun once to record the new "N+" share.

Until then: the S21 code change (PR #827) ships with 140 ms, or waits. 170 ms ships only together with the no-workers change, after the check in section 4 passes.

6. What we are accepting

  • A few more "N+" totals. A count that would have finished in time only with workers now shows "N+". The page itself is always complete. The check in section 4 gives the first number. In production, the existing alert fires if more than 5% of filtered lists show "N+" for an hour (risk register row AR-TICK-1094-01).
  • Nothing about tenant isolation changes. It is the same query under the same row security. Only the time threshold moves.
