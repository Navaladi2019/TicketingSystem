PROPOSED · 2026-11-04 ADR-004-A1 · issue TICK-549 · RFC-012 rev 1 · amends ADR-004 (R7, R12, R14, CI-A3) · source: TICK-541 / PR #443 Security review

Only the masking reader may read the raw audit diff, and the database enforces it

In one sentence. Today the database lets the main application account read the full, unmasked change history of a record, secret fields included, and only a coding convention keeps other code from doing so. From now on, a separate database account is the only one allowed to read those columns. It is used only by the one piece of code that hides secrets, and PostgreSQL itself refuses every other attempt.

Words used here

Audit log and diff
ADR-004 keeps one tamper-evident log of every change. Each entry has a diff, the exact before-and-after change (in JSON Patch format), and a random diff_salt used to hash it. A diff can contain the values of fields marked secret.
Masking (rule R7)
When someone reads the log, values they are not allowed to see are replaced with {"redacted":"mask"}. The code that does this, the "masker", lives only in internal/audit/read.
Database role
An account the application uses to log in to PostgreSQL. nava_app is the main API's account. Each role gets only the table and column permissions listed in one file, db/grants.yaml (invariant I3, least privilege).
RLS (row-level security)
PostgreSQL rules that limit which rows a role sees: only the current tenant's. RLS does not limit columns, which is why it does not help here.
Pool and PgBouncer
A pool is a set of reusable database connections for one role. PgBouncer sits in front of PostgreSQL and shares connections between requests, one transaction at a time.
SQLSTATE 42501
PostgreSQL's error code for "permission denied". Tests check this code, not the wording of the message.

The problem

nava_app had permission to read diff and diff_salt. The masker runs in one package, but any other code running as nava_app could query those columns and get secrets in the clear. That includes a query for a user in the same tenant who is not allowed to see them. TICK-541 added a check that scans the source code for such queries, but Security showed three ways past it: a query assembled piece by piece, a column list kept in a variable, and SQL that is not Go code. No code does this today. This is a risk that grows with the codebase, not a live leak.

Options we considered

OptionWhat it meansVerdict
(a) Database function with owner rightsRemove the permission and add a SECURITY DEFINER function, which runs with its owner's rights, to return the diff.Rejected. Invariant I3 forbids such functions for runtime roles, and every package could still call it.
(b) Switch role inside the transactionnava_app runs SET LOCAL ROLE nava_audit_reader.Rejected. nava_app would have to be a member of the reader role, which I3 forbids, and any package could switch.
(c) Mask inside the databaseA view or SQL function applies the masks.Rejected. CI bans views that run with their owner's rights, and a view that runs with the caller's rights needs the very permission we are removing. It would also duplicate the masker in SQL.
(d) Keep only the source-code checkAccept the risk.Rejected as the end state. CI cannot prove that a read is denied, and the known bypasses stay open.
(e) A separate account with its own connectionsA new login role, nava_audit_reader, with its own PgBouncer login and its own pool, held only by the masking package.Chosen. The database enforces the wall, there is no role switch and no I3 exception, and masking stays in one place.

The decision

  • A new role, nava_audit_reader. It may read the audit columns, diff and diff_salt included, and the entity schemas the masker needs. It cannot write anything, and it cannot read tickets (records).
  • nava_app loses the two columns. Writers are unaffected, because inserting a diff does not need read permission (spiked).
  • Row rules (RLS policies) on audit_log and entity_definition_versions name the new role. The audit_log_select list becomes exactly nava_worker, nava_erasure, nava_audit_reader, and CI checks that exact list. nava_app keeps row access only through the generated writer policy.
  • The masker fails closed. Review found that without the policy change, the new role would see no schemas, conclude that nothing is secret, and return everything. Now "no schema found" is an error, never an empty mask.
  • Connections are capped at 5, by PgBouncer pool_size=5 and the client pool's MaxConns = 5.
  • The TICK-541 source check stays, as a second layer. It now watches the one thing the database cannot: only the masking package may open the reader pool, and only the config loader may read its connection string.

How it is rolled out

  1. Step 1: the new role, with its password in every environment (a missing password stops the role-setup job for every role); the pooler cap; the policy change; removing nava_app's permission; and the new tests, which fail at first.
  2. Step 2: the reader's own pool, the fail-closed masker, and the audit endpoints moved onto that pool.

Steps 1 and 2 ship in one pull request, and neither merges alone, because between them the audit pages would return errors. Preferably this lands inside the open audit-log story (TICK-419) before that story reaches main, so main never has the gap. The source-check update can follow later.
