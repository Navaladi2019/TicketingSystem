# RFC-017 critique, round 1 (Technical Architect)

Archived verbatim from TICK-792 comment 01a1d39d-67f8-77f8-b2a9-36b853a8b470, 2026-11-13T06:34:30Z.

**RFC-017 rev 0, Technical Architect critique round 1: no blocking findings. The identity core (D1, D2, D4) is sound. Six non-blocking defects need a fix in the revision; two of them would break the widget in every browser as written. Three spikes need sharper pass criteria.**

I checked against `main` @ `36b6153` and Keycloak **26.8.1** source (tag `26.8.1`, the version our image pins in `deploy/compose/README.md:17`).

## Findings

| # | Mechanism | Verdict | Evidence | Known / Inferred |
|---|---|---|---|---|
| F1 | D1/D2: tenant from `(iss, org id)` only; `azp` and `Origin` only refuse | **confirmed sound** | `internal/identity/keycloak/keycloak.go:197-256`: `Resolve` picks the tenant from `Binding(iss, orgID)` and never reads `azp`. `azp` is only required to be non-empty (`:348`). Adding a refuse-only `azp` gate after `Resolve` cannot change which tenant is chosen. | Known |
| F2 | D1: which org ends up in the token when one host serves many tenants | **confirmed sound, with a note** | Keycloak `OrganizationScope.java` @26.8.1: plain `organization` (ANY) returns the user's single enabled org. If the user belongs to several orgs, Keycloak prompts them to pick one. `organization:<alias>` (SPECIFIC) keeps only orgs where `org.isMember(user)`. So a host can pass `organization:<alias>` as a hint, and Keycloak still enforces membership. I2 holds. **Revision:** say that a multi-tenant host should send `organization:<alias>`, and that this is a hint, not a trust input. | Known |
| F3 | D1 "silent SSO" | **non-blocking** | The RFC rejects the iframe (option E) because third-party cookies are blocked. keycloak-js `check-sso` uses a hidden iframe to the Keycloak origin, so it runs into the same block. When the tenant's IdP session exists, the sign-in that works is a **top-level redirect** to Keycloak and back with no prompt, not a silent iframe. **Revision:** replace "silently" with "without a prompt, via top-level redirect", and make S1 test that path in WebKit and in Chrome with third-party cookies off. | Inferred (adapter behaviour; S1 settles it) |
| F4 | D2 "resolver unchanged" vs "the resolver checks `azp`" | **non-blocking** | `identity.Principal` has no `azp` field (`keycloak.go:255`). D2 needs either a new field or a check inside `Resolve`. **Proposed:** keep `Resolve` byte-identical, add `ClientID string` to `Principal` (filled from the verified token), and run the `embedding_client` check as separate middleware inside `InTenantTx`. **No cache:** CI-E1 expects a disable to take effect on the very next request. A cache needs a stated TTL, and CI-E1 would then change to match it. | Known |
| F5 | D3 CORS header set | **non-blocking (the widget breaks as written)** | (a) D11's `Nava-SDK` request header is not in `Access-Control-Allow-Headers`. Under the Fetch standard, every non-safelisted request header must be listed, so **every browser request from the SDK fails preflight**. (b) `Access-Control-Allow-Methods` is not set, so only GET/HEAD/POST pass. Any SDK `PATCH`/`PUT`/`DELETE` with `If-Match` fails from a browser. (c) The actual responses, including **401/403/429 from the auth and rate-limit middleware**, must carry `Access-Control-Allow-Origin`. Otherwise `fetch` rejects with an opaque `TypeError`, and the widget can neither see the 401 that triggers its retry (D7) nor read the 9457 body or `Retry-After`. CORS therefore has to be the **outermost** middleware. (d) Add `Vary: Origin` and `Access-Control-Max-Age` (Chromium caps it at 7200 s). (e) Exposed headers should include `Location`. | Known (Fetch standard CORS protocol). Middleware order is Inferred until S4. |
| F6 | D6: two buckets, "a request spends from both" | **non-blocking** | `ratelimit.go:98-117` reserves a token and calls `CancelAt` when the request is refused. With two buckets in sequence, a host refused by its sub-bucket has **already spent a tenant token**. A host at its cap keeps draining the tenant bucket, which defeats "cannot starve the tenant's own users". **Proposed:** reserve from both buckets under one lock and cancel both if either one delays. Set the sub-bucket's **burst** as well as its rate, and change the `Limiter` interface from `Allow(ctx, tenant)` to take a key. CI-E7 should assert that the first-party bucket keeps its full burst while host X is refused. | Known (code) |
| F7 | D5/RR5: `via_client_id` in the hashed envelope | **non-blocking** | `internal/audit/chain/doc.go`: NULL is "emitted and never omitted", and changing the canonical form "is a breaking change to the export format and needs Technical Lead review (PLAN-005 D-5-7)". Adding the member changes the bytes for every entry unless the verifier knows which form each entry uses, and the envelope has no version member today. **Proposed for ADR-004-A2:** add `envelope_version` (1 = current, absent from v1 bytes; 2 = adds `version` and `via_client_id`, both inside the JCS bytes). New golden vectors for v2. The offline verifier accepts both forms. Also note the field is named `envelope_sha256` in code, not `content_sha256`. | Known (code). The design is my proposal. |
| F8 | D7: SRI on the platform-served ES module | **non-blocking** | `integrity=` covers only the top-level script. Chunks loaded later with `import()` are not checked unless the import map carries integrity metadata, which browsers do not support uniformly. **Proposed:** the CDN bundle is a single file with no dynamic imports, and CI fails if the build emits a second chunk. | Inferred (browser support varies) |
| F9 | D8: JSONForms with no `eval` under a strict CSP inside a shadow root | **verify-by-spike (S3, criteria widened)** | Three likely failures beyond "validation off": (1) **rules** (`SHOW/HIDE` with a schema-based condition) and **oneOf/anyOf** subschema selection call Ajv, which compiles with `new Function`. `validationMode: 'NoValidation'` may not cover those paths. (2) MUI/emotion injects `<style>` elements into `document.head`. CSP `style-src 'self'` blocks them unless a nonce is passed, and styles in `head` do not reach into the shadow root anyway. (3) MUI `Select`/`Popover` portal into `document.body`, outside the shadow root, so they render unstyled. | Inferred (S3 settles it) |
| F10 | D4: service account as an org member | **verify-by-spike (S2), now more likely to pass** | In Keycloak 26.8.1, `OrganizationMemberResource.addMember` and `JpaOrganizationProvider.addMember` (lines 107-128 and 233+) have **no service-account guard**. ANY scope maps a "user" with one enabled org, and a service account is a `UserModel`. Our side is still unproven. `Resolve` requires a synced `principals` row with `LinksKnown = true` and every federated link bound (`keycloak.go:229-247`). The directory sync must create that row for a service-account member, with known-empty links. | Known (Keycloak source). Inferred for our sync. |
| F11 | B (token exchange) rejected | **confirmed sound** | Rejecting it removes a second token-minting path. My review does not depend on its preview status, so S1 does not need to check that. | — |

## Spikes before the ADR (pass/fail fixed now)

- **S1 (widened):** Keycloak 26.8.1 public client with PKCE, scopes `organization:<alias>` and `organization`, and an audience mapper for `nava-api`. **Pass:** the token passes the unchanged `keycloak.Adapter.Resolve`; a user in two orgs who requests `organization` gets the picker, and the picked org resolves; a top-level redirect with an existing brokered IdP session shows no prompt in WebKit and in Chromium with third-party cookies blocked. **Fail:** any 401 from `Resolve` or any prompt.
- **S2 (widened):** client_credentials service account added as a member of one org. **Pass:** the token carries exactly one `organization` entry; directory sync creates a `principals` row with `LinksKnown = true` and no links; `Resolve` returns that tenant. The same account in two orgs → 401. **Fail:** no org claim, or `Resolve` refuses. If it fails, the revision chooses the fallback. My preference is a "hardcoded claim" mapper on the confidential client, which is operator-only so R3 still holds, *but* it needs a resolver branch for principals with no links, so it is no longer "unchanged".
- **S3 (widened):** the published `loan_application` schema from TICK-789, plus one SHOW/HIDE rule and one `oneOf` field, rendered inside the `<nava-records>` shadow root under `script-src 'self'; style-src 'self'`. **Pass:** zero CSP violations in Playwright (Chromium, Firefox, WebKit); the rule toggles; the select menu is styled. **Fail:** any violation. **Q4 answer if it fails:** first, pass JSONForms a custom `ajv` that evaluates rules with a small interpreter for the rule subset we allow (`const`/`enum`, no compile), and use a renderer set that styles itself through constructable stylesheets (`adoptedStyleSheets`, not governed by `style-src`) with portals targeting the shadow root. If that does not work, use a hand-written renderer for the v1 field kinds. I will run S3 once the revision fixes the field kinds.
- **S4 (widened):** preflight plus the actual request carrying `Authorization`, `Content-Type`, `Idempotency-Key`, `If-Match` and `Nava-SDK`, for GET/POST/PATCH. **Pass:** the browser exposes 200, 401, 403 and 429 status codes and bodies to the SDK in all three engines, and a non-listed `Origin` gets a readable 403 `origin_not_allowed`. **Fail:** any opaque `TypeError`.

## Paste-ready text for D3

> CORS is the outermost middleware and applies to every response, errors included. Preflight: echo `Origin`; `Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE`; `Access-Control-Allow-Headers: Authorization, Content-Type, Idempotency-Key, If-Match, Nava-SDK`; `Access-Control-Max-Age: 7200`; no `Allow-Credentials`. All responses: `Access-Control-Allow-Origin: <echoed Origin>`, `Vary: Origin`, `Access-Control-Expose-Headers: ETag, Location, Retry-After`. The D3 allow-list check runs after authentication and only refuses, with a 403 that still carries the CORS headers.

**Budgets:** none proposed yet. The D2 lookup adds one indexed read per embedded request. I will measure its p95 cost with S4 rather than guess it now.

One revision round, per the triad. Anything still disputed after it gets settled by S1–S4, not by a third round.
