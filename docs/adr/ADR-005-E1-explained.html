ACCEPTED · 2026-11-12 ADR-005-E1 · issue TICK-665 · amends ADR-005 §4.2 and §8 · source: PR #581 integration test failure

During the counter migration, the first ticket of a brand-new type can fail to save

In three sentences. (1) ADR-005 changes the key of the table that hands out ticket numbers, in steps, and promised that old and new server versions can run side by side during the change. (2) That holds for every record type that already has a number counter, but not for a type's very first ticket: if two people create the first ticket of a type at the same instant, one of them gets an error. (3) The fix is that the new server version simply tries once more, which always succeeds; the old version cannot be fixed, so for the length of one rollout that rare failure is an accepted risk.

1. The problem in plain words

Each tenant and record type has one row in a counter table that says which number comes next. The first ticket of a type creates that row; every later ticket adds one to it. The database statement that does this says "insert the row, or, if it already exists, add one". To know whether the row "already exists" the database uses a unique index (a lookup list that refuses two rows with the same key), and the statement names which one to use.

To support custom number formats, the migration adds a second, wider unique index next to the old one, and only later swaps it in as the main key. For a while the table therefore has two unique indexes. When two first tickets of the same type race, the slower statement checks the index it named, then trips over the other one, and the database reports "duplicate key" (error code 23505) instead of quietly adding one.

This is a worst case: every one of the 160,000 tries was a first create racing others. In real use a type gets its first ticket once. The earlier spike missed it because it ran the statements one after another, not at the same time. An integration test on PR #581 caught it.

4. The decision

  • The new server version (R1) retries the numbering step exactly once on this error, and only when it names one of the two counter indexes. A second failure is reported, never retried again. Built in TICK-666.
  • A test that races first creates is added now, switched off until TICK-666 switches it on.
  • The migration (PR #581) and the retry (TICK-666) are merged together, so no build ever has the migration without the retry.
  • The runbook says: run M3 soon after the new version is fully rolled out.
  • The retry relies on the database's default isolation level (how strictly concurrent transactions are kept apart), "read committed". Nobody may raise it for the application, in code or in database settings; at a stricter level this race shows up as a different error and the retry would not fire.
  • The retry is temporary: it is deleted together with the last migration step (M3), after which the race cannot happen.
  • ADR-005 §4.2 is corrected: "old and new versions run side by side" holds for existing counters only.

6. Evidence

  • Race reproduction, numbers above: docs/adr/ADR-005/spikes/postgres/e1-first-create-race/.
  • Pinned test: TestConcurrentFirstCreatesOfATypeAllSucceed on PR #581, switched off until TICK-666 adds the retry; with it switched on today, it fails in both modes.
  • Retry check (Technical Architect): 13,136 retries, none failed; every attempt produced exactly one number. Under a stricter database isolation setting the retry does not help, which is why that setting is forbidden (section 4). docs/adr/ADR-005/spikes/technical-architect/e1-retry-once/.
  • PostgreSQL's own documentation: an "insert or update" statement only handles duplicates on the index it names.
