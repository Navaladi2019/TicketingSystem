ACCEPTED · 2026-11-03 ADR-004-E4 · issue TICK-517 · amends ADR-004-E3 (Budget) · source: TICK-509 / PR #420 review, finding 1

The audit speed check should fail on a slower audit check, not on a slower machine

In one sentence. Our CI speed test for the audit check failed because GitHub gave us a slower machine, not because our code got slower. From now on the test fails only on comparisons made inside one run on one machine, which cancel out the machine's speed. The raw timings are still recorded and still produce a visible warning.

Words used here

Commit check
A database trigger that confirms, when a transaction saves, that every changed record has a matching audit entry (ADR-004). ADR-004-E3 made it plan its lookup afresh on every call, which costs a little time per write.
Budget row
A line in docs/budgets.md that limits how slow something may be. There are two here: per call (one small write, at most 300 µs) and import (a 10,000-record import, at most 175 µs per record). µs means microseconds, millionths of a second.
Clause arm / reference arm
In each test run we time our real function (the clause arm) and an unchanged copy without the E3 change (the reference arm). They run on the same data, on the same machine, a few seconds apart.
Ratio
Clause time divided by reference time in the same run. A slow machine slows both arms, so the ratio barely moves. If our code gets slower, only the clause arm moves, and the ratio rises. The limits are 5 (per call) and 15 (import).
Flatness
The per-call time measured after 200, 1,000 and 5,000 writes. The highest divided by the lowest must stay below 1.5. A rising value means the check gets slower the longer a connection is used, which is the failure E3 fixed.
Runner
The rented GitHub machine a CI job runs on. We ask for a 4-CPU ubuntu-latest machine, but the hardware behind that label varies.
main-red
The CI step that opens a top-priority (P0) "main is broken" issue whenever a required job fails on main.

The problem

On the same code, the speed job ran twice on two different GitHub machines, with nothing else running on either. On the second machine everything ran about 1.4× slower, both arms alike. The import number went from 129.5 µs to 190.9 µs, over the 175 µs limit, and the job went red. The ratios hardly changed: 9.76 to 9.98 for the import and 1.45 to 1.54 per call. So the code had not changed, only the machine had. The import limit leaves 1.35× of headroom, and machines vary by about 1.45×. A required job set up like that fails roughly one run in three, and each failure on main opens a false P0.

The decision

What the run foundVerdictCI job
A result line is missing, or a timing is zero or invalid (the test measured nothing)fail_no_rowsfails
A ratio is over its limit (per call over 5, import over 15)fail_ratiofails
Per call is not flat (highest / lowest ≥ 1.5)fail_flatfails
An absolute number is over its threshold, everything else fine. Per call: any of the three measurements (after 200, 1,000 or 5,000 writes) over 300 µs. Import: over 175 µswarnpasses, with a yellow warning on the job
Everything within limitspasspasses

Every run also records the machine's CPU model next to its timings, so a later reader can tell "slower machine" from "slower code". The limits keep their values (300 µs and 175 µs), and they are now called review thresholds. The measurement method, the 38 partitions and the ratio and flatness limits do not change.

Why a slow machine no longer fails the job. The ratio compares two arms in the same run, and flatness compares one arm at three points in the same run. A machine that is slow all the way through trips neither. A machine whose speed changes in the middle of a run can trip flatness. That has not happened in CI (1.03–1.04 against a 1.5 limit), but a laptop once reached 1.30.

The emergency plan from E3 (called S3: a faster but more invasive way to run the check) still starts the same way. A run must have a ratio over its limit and either row over its threshold. The threshold half depends on the machine, so the same real slowdown can start S3 on a slow machine and not on a fast one. Every failed ratio run is red and gets looked at anyway, and the numbers are compared with the recorded baseline for the same CPU model. "S3 did not start" is not evidence that nothing is wrong.

The fix

  1. The verdict code in PR #420 (commit_check_verdict_test.go) gets the five verdicts above, with a unit test for each. One of them covers "only the 5,000-write measurement over 300 µs", which gives warn. Today, "over the threshold with in-range ratios" means rerun. After the change it means warn, and an uneven per-call row with in-range ratios means fail_flat.
  2. The CI script fails if either result line is missing, logs the CPU model, and prints the warning annotation and a summary table.
  3. docs/budgets.md relabels the two limits as review thresholds and records the CPU model with each baseline.
  4. Once TICK-509 merges, commit-check-budget becomes a required check on main. On 2026-11-03 it is not one yet.

Nothing in the database, the audit function or production changes.

What we are accepting

  • A slowdown that hits both arms equally passes. If shared code (for example the audit insert path, or a Postgres upgrade) slows the real function and the reference copy by the same factor, the ratio stays the same and CI stays green. It still shows as a warning and in the logged numbers. Nobody is alerted automatically. The Postgres specialist re-takes the baselines on every Postgres upgrade. Two warnings in a row on main, on a CPU model we already have a baseline for, are the cue to investigate. That cue only works if one CPU model gives steady timings. A follow-up measurement checks this once runs log the CPU (target: under 1.2× spread per model). If they don't, the cue is replaced. (AR-TICK-517-01, low.)
  • The ratio and flatness gates are now a little stricter. Before, an out-of-range ratio or an uneven per-call row failed only together with an over-limit time. Now each fails on its own. If the reference copy gets faster, for example after a Postgres upgrade, the ratio can rise without our code getting worse, and CI goes red. That is still a real change worth looking at. The import ratio has 1.5× of headroom, and between machines it moved by 2 %. A Postgres upgrade changes the pinned-versions file, and that runs this job on the upgrade PR. So a faster reference copy turns the PR red before it merges, not main, once the job is a required check. (AR-TICK-517-02, info.)
