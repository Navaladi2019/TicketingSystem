The audit export can read the chain columns it has to print

In one sentence. The database account that serves audit reads was given a fixed list of columns. Three columns that the audit export must print were missing from that list, so the export could not work. This erratum adds them. None of them is new or sensitive information.

The problem in plain words

Every change in the platform writes an entry to the audit log. The entries are linked in a hash chain: each entry stores a fingerprint of itself (entry_hash) and of the entry before it (prev_hash). If anyone edits or deletes an entry, the links break. The export gives a tenant a file it can check on its own, so it has to include those links for every entry in the range.

Amendment A1 created a separate, read-only database account, nava_audit_reader (the "reader"), and listed exactly which columns it may read. That list was written for the two on-screen audit endpoints. It left out the two hashes, and erasure_ref, the id of the erasure request that wiped an entry's personal data. The export file prints all three. A1 also says the export runs on the reader. Because the export needs columns the list leaves out, A1 could not be followed as written: each export page failed with a permission error (42501).

Options considered

OptionVerdictWhy
A. Add the three columns to the reader. Take the chain's latest position from the statement that already locks the export.ChosenOne grant line. No schema change, no row-access change.
B. Read the hashes through the main app accountRejectedGoes against A1's "export runs on the reader". The main account is kept away from the hashes on purpose.
C. Let the reader read the chain-head table tooRejectedGives the reader access to a second table, for a value the lock statement already returns.
D. Fix the grant, leave the ADR aloneRejectedThe ADR's list is the reference that reviews and CI checks are held to. A grant that differs from it looks like drift.

The decision

  • A1-1: the reader's audit_log list gains prev_hash, entry_hash and erasure_ref. It still never includes txid and still has no write rights.
  • A1-7: the chain's latest position ("head") is read by the same statement that takes the one-export-per-tenant lock, on nava_app. If that statement finds no free lock, the caller gets 409 export_in_progress.

What is being accepted

ColumnDoes the reader learn anything new?
prev_hash, entry_hashNo. They are fingerprints of data the reader already sees, and the export publishes them by design.
erasure_refNo. It is the same value as subject_id of the matching erasure entry, which the reader already reads. erased_at already shows that an entry was erased.

Tenant isolation is untouched. The reader still sees only the current tenant's rows. With no tenant set, it sees nothing. Only the reader can read the diff columns, and the policy's role list is unchanged. No new accepted risk.

Evidence

  • Catalogue check on PostgreSQL 16.10: the reader had no read right on the two hashes, which causes the export failure. See docs/adr/ADR-004/spikes/postgres/e8/.
  • Red to green: TestP540aReaderReadsChainHashes fails before the grant and passes after it, including the other-tenant and no-tenant zero-row checks. TestP540aExportLeaseAndHeadRead pins the lock-and-head statement.
  • Open at DRAFT: PR #508 does not yet grant erasure_ref. It must add it before this erratum is accepted.
