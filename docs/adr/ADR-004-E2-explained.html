An honest audit export was being called "tampered"

In one sentence. When a customer exports their audit log with a filter that happens to match everything, our offline checker said the file had been tampered with. The rule was wrong, not the file. We fix the rule: the checker judges the file by what is actually in it, and only the closing line of the file has to agree.

Words used here

Audit export
A file a tenant downloads that contains their audit entries, each linked to the one before it by a hash (a fingerprint), so that a removed or edited entry is detectable.
Range
The run of entries from the start of the requested time window up to the newest sealed entry. Every entry in it is numbered (seq).
Stub
A placeholder line for an entry the filter did not ask for. It keeps the fingerprint chain unbroken without showing the content.
stubs=false
The caller asked to leave the excluded entries out entirely, instead of writing stubs. The file is smaller, but if anything was left out the chain has holes ("gaps") and cannot be checked end to end.
Header / trailer
The first and the last line of the file. The header is written before any entry is read; the trailer is written after the last one.
Verifiable
The chain has no holes from start to end, so a checker can prove nothing in the range was removed.

The problem

The specification said two flags must both match the truth: the header's stubs and the trailer's verifiable. But the exporter writes the header first, straight from the request, before it knows whether the filter will exclude anything. If the filter happens to match every entry, a stubs=false file has no holes. It is fully verifiable, yet its header says stubs:false. The checker (PR #370) followed the spec and reported tampered, exit code 1. An auditor would see an alarm on a file nobody touched.

Revision 2. The Technical Architect's review found a third honest file that was still flagged: the time window has entries, but the filter matched none of them. The file then has only its starting point and its closing line. Rev 2 treats that as "unverifiable" too, and tightens one check so a forged closing fingerprint is caught even when the file has holes.

While proving the first case, we found a second case of the same kind: if the filter left out only the last entries of the range, the checker saw no hole between lines and failed the file at the "does it end at the newest entry?" check, again as tampered. That file is honest; it is simply not verifiable.

Options considered

OptionVerdictWhy
A. Only the trailer must agree; the header records the requestChosenThe trailer is written after the range, so the exporter knows the answer without extra work. No memory cost, no extra query.
B. Exporter holds the whole range in memory, then writes the headerRejectedAn export can run to 15 minutes in pages of 5,000 rows. Holding it all before sending the first byte costs memory or disk and delays the download, and buys nothing: neither flag is fingerprinted, so the checker has to compute the answer anyway.
C. Exporter counts first, then writes the headerRejectedAn extra database query per export, a second place that must agree with the stream, and the header would no longer record what the caller asked for.
D. Ignore the header completelyRejectedWhen someone asked for stubs, a missing line can only mean deletion. Keeping that as "tampered" (seq_missing) is free and more useful to an auditor.

The specification also gets a complete list of the reasons the checker can give, including seq_missing and anchor_mismatch (the starting point of the chain is not where the request puts it). Until now the spec claimed the reasons were only those in the test files.

The fix

  • Checker (internal/audit/verify/verify.go, about 15 lines): treat entries left out at the end as a hole; compare only the trailer's flag.
  • Test vectors (the shared example files every component is tested against): ten new examples: one per row above, two for the chain's starting point, plus a file with every line deleted and a forged closing fingerprint. No existing example changes its expected result.
  • Exporter (TICK-444, not shipped yet): header copies the request; trailer says verifiable when every numbered entry in the range has a line.

Not a format change: files that passed before still pass, and no exporter has shipped, so no customer file changes its verdict.

What we are accepting

Nothing new. The header flag was never protected by a fingerprint, so relaxing the rule on it removes no protection. Someone who deletes lines in the middle and edits both flags gets "unverifiable", before and after this change. One verdict does move: cutting lines off the end of a file and editing both flags now also gives "unverifiable" instead of "tampered". That is no weaker than the middle-deletion case. The known limit stays as it was: nothing proves the file as a whole came from us (accepted risk AR-TICK-409-01, no external anchor).
