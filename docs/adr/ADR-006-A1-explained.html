PROPOSED · 2026-11-20 ADR-006-A1 · issue TICK-1001 · amends ADR-006 D13 and residual R-a · source: TICK-992 measurements (PR #775)

Two kinds of filtered list get 350 ms instead of 150 ms, because of how much they read

In plain words. (1) When a user filters a big ticket list on a custom field, we promised an answer in 150 ms for 95% of requests, with one exception at 350 ms: a filter matching a few percent of tickets, for a user who can only see some of them. (2) Measured on a 400,000-ticket tenant, the same filter is just as slow for users who can see everything, and a broad filter (40% of tickets) is slow for users who can see only some. In both cases the cause is how many matching rows the database must read, not the user's permissions. (3) This amendment moves the 350 ms exception to those two cases, keeps 150 ms everywhere else, and names the signal that tells us when to build the faster query.

1. The problem in plain words

Admins can mark a custom field of a ticket type as filterable. Its values are then copied into a side table, a small extra table with an index (a sorted lookup structure, like a book index), so filters on it are fast (ADR-006).

A list page shows the 51 newest matching tickets and a count of matches (the count stops at 1,001). Some users have a row ACL: an access rule that hides the tickets of groups they are not in. ADR-006 decision D13 set the speed target: p95 (the time 95% of requests beat) ≤ 150 ms, except a filter matching 0.5–5% of tickets for a user with a row ACL, which was allowed 350 ms (accepted risk R-a).

The new measurement (TICK-992) shows the exception was drawn around the wrong thing:

  • A 2% filter, no ACL: 237–268 ms. About 8,000 tickets match. To show "the newest 51", the database fetches all 8,000, sorts them and keeps 51. The ACL plays no part in that.
  • A 40% filter, with an ACL: 176–328 ms. The page itself takes 4–14 ms. The count is the slow part: the database loads all 160,258 matching side rows into memory to compare against the 4,910 tickets the user can see, and that memory overflows to disk.

The test machine was not fully idle (another stack was running at idle, approved by the Technical Lead), so every number may be up to about 1.3× too high. Even with that removed, the 2% band without an ACL reads 182–206 ms: a real miss of 150 ms, and comfortably inside 350 ms.

3. The decision

A1-1: the new target
p95 ≤ 150 ms for every filtered list, except two bands at ≤ 350 ms: a filter matching 0.5–5% of a ticket type (any user), and a filter matching 40% or more for a user with a row ACL.
A1-2: why these two
Both do work proportional to the number of matches, which the current query shape cannot avoid. A future exception needs the same proof from the query plan, not just a slow number.
A1-3: the accepted risk, rewritten
R-a now names both bands. The old note that "the 40% count is a count-only miss at 538–1,255 ms" is gone: after recent fixes, the whole 40% request, count included, fits in 350 ms.
A1-4: a signal we can actually watch
Today nothing tells us which band a slow list belongs to. One new metric, nava_records_list_data_filter_seconds, recorded only for lists filtered on a custom field, with two labels: whether a row ACL applied, and whether the count hit its 1,001 cap. Both 350 ms bands are "count hit the cap" lists. Alert when their p95 passes 350 ms for an hour. No tenant, field or value goes into the metric.
A1-5: two near-misses are not excused
A 0.25% filter with two values missed by 2–7% (160.9 / 152.8 ms), with only 29–35 ms of database time and no fan-out. It keeps 150 ms. The Technical Lead decides whether to re-run it on an idle machine; a confirmed miss would need its own decision.
A1-6: what the follow-up spike must prove
When the trigger fires, a spike tries the adaptive query for both the page and the count. It must get both bands to ≤ 150 ms on an idle machine without touching tenant isolation or permission checks.

4. The fix and migration

None in code. This changes a budget: the D13 row of docs/budgets.md (on the S21 story branch) and the accepted-risk index. The metric in A1-4 is a follow-up task for the Technical Lead.
