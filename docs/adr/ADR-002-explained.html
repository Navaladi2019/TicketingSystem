ADR-002, explained

The whole decision in three sentences. (1) A user currently has no way to see which groups they belong to without someone running SQL, because /me returns only random-looking ids. (2) We add a field that lists each of the caller's groups with a readable path such as /service-desk, and only the caller's own groups in the caller's own tenant. (3) We drop the internal /t/<tenant-id> part of the path, and we lock the field down so it can never become an input to security decisions.
How big is this? It is a small change that only adds things. One new response field and one database read, on one endpoint. No invariant changes, the database schema does not change, and no existing field changes. It needs a decision record because it adds a permanent field to the public v1 API, and it sits on the identity path, where getting tenant isolation wrong would be serious.

Terms used here

Tenant
One customer of the platform. Tenants share the database, but must never see each other's data.
/me
The API endpoint that answers "who does the platform think I am?" It returns the user id, the tenant and the user's groups.
Group path
A group's name in the identity provider (Keycloak), written like a folder path. We store it as /t/<tenant-id>/service-desk.
Row-level security (RLS)
A PostgreSQL feature that makes the database itself hide every row that does not belong to the current tenant, even if the query forgets to filter.
Port
A small interface in our code through which the API reaches the database or an outside service. Keeping it narrow limits who can call it.
Lint rule
An automatic check that runs on every pull request and refuses certain code patterns.
v1 additive-only
Our rule that the public v1 API may gain fields but never lose or narrow them. Anything we publish there is permanent.

1. The problem in plain words

Story S5, step 1 says: "As Alice, GET /api/v1/me shows group service-desk." During acceptance (TICK-264) this step could not pass. /me returns Alice's groups only as internal ids, for example 0a000000-…-4a1. These ids are generated at random when groups are synced, and no endpoint turns them into names. Alice is in the right group, but nobody can tell without querying the database.

2. Options considered

OptionVerdictWhy
Change the story text so it no longer says "shows group service-desk"rejectedThat makes the story pass on paper, but users still cannot see their memberships.
A plain list of path strings next to the idsrejectedTwo lists that line up only by position break silently if one changes.
Group names only (the last part of the path)rejected/emea/leads and /apac/leads would both show as leads.
Keep the full path, /t/<tenant-id>/service-deskrejectedThat prefix is how our Keycloak setup happens to be laid out. Because v1 fields are permanent, publishing it would tie us to Keycloak's layout for good.
A new "look up group by id" endpointlaterIt needs its own rules on who may look up which group. That is more than this story needs.
A list of {id, path} pairs, with the prefix removed, showing only the caller's own groupschosenIt is the smallest change that makes the story true, and it cannot leak across tenants.

3. The decision

Decision text (ADR-002 §1, items 1–3)
  1. GET /api/v1/me gains group_paths.
    • The field is an array of GroupPath {id, path}. It is always present and may be empty.
    • path is the group's path relative to the tenant root. Alice sees /service-desk, and a nested group reads /service-desk/tier-2.
    • groups (the uuid array) does not change.
  2. The field is tenant-scoped and membership-scoped.
    • It lists only the groups the calling principal belongs to, in the caller's own tenant.
    • Membership is checked in SQL, under row-level security on both groups and group_members (I1).
  3. The tenant prefix /t/<tenant_id> is stripped. It describes how the Keycloak adapter lays out groups (D26). It is not a product promise, and v1 is additive-only, so it stays out of the contract.

What Alice's /me response gains:

"groups":      ["0a000000-0000-4000-8000-0000000004a1"],          // unchanged
"group_paths": [{"id": "0a000000-0000-4000-8000-0000000004a1",
                 "path": "/service-desk"}]                         // new

4. What gets built

This is one implementation task for Delivery:

  • The API contract. A new group_paths field and a GroupPath type in api/openapi.yaml. Existing clients ignore the extra field.
  • A narrow read port, GroupPathReader. Its one query joins "my memberships" to "groups" inside the tenant-scoped transaction. Because the query starts from the caller's memberships, a caller can only ever see their own groups. They cannot see other groups in their tenant, and they cannot see another tenant's groups.
  • The handler. GetMe removes the /t/<tenant>/ prefix. The database already guarantees every stored path has that prefix. If a row ever breaks that rule, the entry is left out and an error is logged with only the ids, never the path, so /me keeps working.
  • No migration. The schema does not change.

Guards that keep paths "display only"

Paths are written by tenant admins. They are not unique across tenants (both tenants can have /agents), and they change when a group is renamed. Any security rule that keyed on a path would mix tenants up or break on a rename. So:

GuardWhat it stops
A test that pins the fields of the Principal type (the identity every request runs as)Someone adding names or paths to the security context. The test fails until Security reviews the change.
A lint rule: only api.go may call GroupPathsOther code starting to read paths
Tracker item TODO-013: the future access-control compiler must use group ids only, with a testAccess rules keyed on paths. The compiler does not exist yet.

6. Evidence

  • The contract check passes. The Technical Architect ran the repo's API-compatibility tool on the exact edit, and it exits 0, so the change counts as additive. The run also showed a test fixture that would go red, and the fix is now an acceptance criterion. Raw output: ADR-002/spikes/technical-architect/apidiff-openapi-compat.md.
  • The lint rule works. The rule first proposed (rev 1) caught 0 of 3 forbidden calls in a test fixture: red. The adopted type-qualified rule catches 3 of 3, and does not flag the harmless response field: green. Raw output: ADR-002/spikes/technical-architect/forbidigo-scope.md.
  • Isolation tests a leak would fail.
    • The isolation suite gets a group that exists only in tenant B, and a test that fails if it ever shows up in tenant A's /me.
    • Tenant A gets a second group that Alice is not in, and the test requires Alice's list to match her memberships exactly.
    • A database test runs the query with the wrong tenant on purpose and must get no rows back.
    • The CTO signed off on changing these protected test files (TICK-266 comments 01a17cc5 and 01a17cd9).
