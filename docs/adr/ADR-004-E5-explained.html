Removing a group in Keycloak must never rewrite tickets behind the audit log

In one sentence. When a group disappeared from Keycloak, the database blanked that group on every ticket by itself, with no audit entry, no version change and no event, and the new audit check correctly refused it, which stopped group sync. From now on, removed groups are only marked as removed, so tickets are never touched, and a CI check forbids this kind of hidden write on any audited table. Separately: secrets may never be stored inside a ticket.

Words used here

Record
A ticket (or any other tenant-defined item) stored in the records table. Every change to it must go through one write pipeline, which checks permissions, validates the change, bumps the version and writes an audit entry, all in one transaction (invariant I4).
Audit entry and commit check
ADR-004 keeps one tamper-evident audit log. The commit check is a database trigger: when a transaction saves, it refuses the save unless every changed record has a matching audit entry.
Group sync
A background job (database role nava_groupsync) that copies users and groups from Keycloak, the identity provider, into our tables. It also handles deprovisioning, so it must never get stuck.
Foreign key (FK) and referential action
A foreign key says "this column must point at an existing row elsewhere". A referential action such as ON DELETE SET NULL tells the database to change the pointing rows itself when the target is deleted. That change runs as the table's owner and skips our permissions and the write pipeline.
Tombstone (soft delete)
Instead of deleting a row, set deleted_at to mark it as removed. The row stays, so nothing that points at it breaks.
Audited table
A table listed in db/audited-tables.yaml. Every write to it needs an audit entry (ADR-004).

The problem

A record's assignment_group_id pointed at groups with ON DELETE SET NULL. When Keycloak dropped a group, group sync deleted it, and PostgreSQL silently blanked the group on every record that named it. That is a second, hidden writer of records: no version bump, no audit entry, no event. When the commit check was attached to records (TICK-452), it refused that save, so group sync failed for the whole tenant, deprovisioning included. Our CI check did not notice, because it looks at permissions, and a referential action needs none.

Options we considered

OptionWhat it doesWhy it lost or won
(a) Sync clears the group through the pipeline firstEvery affected record gets a proper, audited writeLost. One record that fails validation stalls sync again. A busy tenant turns one sync into thousands of record writes, and sync would need rights on records and the audit log.
(b) Sync writes the audit entries itselfKeeps the hidden write, adds entriesLost. It is still a second write path, with no version bump and no event.
(c) Let the check ignore writes made by the database itselfExempts writes made from inside triggersLost. The history silently stops matching the record, and the hash chain still says "verified". A spike showed that any write issued from any trigger would also escape.
(d) Never attach the check to recordsRelies on a code-level architecture testLost. That test cannot see this write either, so it has the same gap as (c) and no database guard at all.
(e) Block deletion; sync reassigns or waitsGroup cannot be deleted while usedLost. Reassigning is (a) again, and waiting leaves an unmarked ghost group.
(e) Soft delete: chosenMark the group removed and never delete itWon. Records are never touched, sync never stalls, and the check stays strict.

The decision

  1. Groups are tombstoned, never deleted (D1, D2). Group sync removes the group's memberships, then sets deleted_at, then removes the tenant's admin or auditor pointer if it named that group. The record FK becomes RESTRICT, and sync loses the right to delete groups.
  2. New rule R29: no foreign key on an audited table may change rows by itself. CI checks every audited table, so the next hidden writer fails in CI, not in production.
  3. A removed group grants nothing, and the database enforces it (D11). A removed group cannot have members: a generated live flag and a foreign key make the database reject it, for every role.
  4. The admin and auditor pointers are deleted when their group is removed (D5). That way a group restored in Keycloak does not silently make people admins or auditors again. Sync can delete only pointers whose group is already removed. The policy reads USING (<tenant predicate> AND EXISTS (SELECT 1 FROM groups g WHERE g.tenant_id = tenant_admin_group.tenant_id AND g.id = tenant_admin_group.group_id AND g.deleted_at IS NOT NULL)), and the same with tenant_auditor_group. The outer column is always written with its table name, so a future group_id column on groups cannot silently turn the check into a column compared with itself. It also needs read access to the auditor pointer (condition I1: SELECT (tenant_id, group_id) and the SELECT policy). Without it, the delete either errors (and sync stalls) or silently does nothing.
  5. Records keep the removed group and show it as removed (D7). A ticket cannot be newly assigned to a removed group (D6). For another tenant's group, the error is the same as for an unknown id, so nothing leaks.

How it is rolled out: expand, then contract

Q2: can a ticket hold a secret?

No. A value at a field marked writeOnly or x-nava-secret is refused with 422 audit_secret_in_diff. The error names the field, never the value. Storing the value and hiding it only in the audit diff was rejected, because ticket data also flows to scripts, workflow payloads, search and backups, and the audit mask covers none of them. Note that JSON Schema's writeOnly normally means "accepted, not returned". Here, for a record, it means never accepted. Publishing a ticket type that requires such a field anywhere in its schema is refused, because nobody could ever create that ticket.
