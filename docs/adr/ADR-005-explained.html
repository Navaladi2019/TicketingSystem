ADR-005, explained

The whole decision in four sentences. (1) A record's number is handed out in its own tiny database step, just before the record is saved, instead of during the save, so people creating records at the same moment stop queuing behind each other. (2) Tenants describe a number format as a short pattern, for example {prefix}-{yyyy}{MM}{seq:4} for "the type's letters, year, month, then a 4-digit counter that restarts every month", giving VISA-2026110001. (3) A format is created at runtime, by an admin first and later also by a plugin through our API, and linked to as many record types as need it, with no software release. (4) Every existing record type keeps exactly today's numbers (INC0000042 continues as INC0000043).

1. The problem in plain words

Speed. Every record gets a human-facing number such as INC0000042. Today, the counter that produces it is locked from the moment a record is numbered until the record is fully saved. When 8 people create the same kind of record at once, they stand in a queue for that one counter. The target is that creating a record takes at most 50 ms for 95 % of requests (the "p95"). We measured 264–408 ms.

Formats. Today every number is a 2–6 letter prefix plus 7 digits. Each record type already has its own prefix (INC for incidents, VISA, PF and so on), chosen by the tenant admin, and its own counter. Tenants building applications such as visa or PF applications want numbers like 202611 0001 (restart each month), 20261110 01 (restart each day) or BLR_26_01_11 (per branch and month). You also asked whether a format could be a plugin "created dynamically and linked".

2. Words used on this page

Counter
One row in the database per tenant and record type (and now per "scope") holding the next number.
Lock
While one request updates the counter, others wanting the same counter wait. The time it is held decides how long the queue gets.
p95
95 % of requests are at least this fast.
Gap
A number that was handed out but never ended up on a record, so the sequence skips it (41, 43).
fsync
The database waiting for the disk to confirm a change is safely stored. It takes a few milliseconds and is usually the slowest part of saving.
Scope
What a counter restarts for: a month, a day, a branch, or a mix. Each scope has its own counter row.
Epoch
A version number for a type's format. A new format starts a new counter, so it never continues an old one by mistake.
Numbering mode
A per-type setting: gaps (a failed create may skip a number; fast) or gapless (never skips; creates of that type queue for the counter).
Prefix
The 2–6 capital letters that start every number of a type, unique within a tenant.
Plugin
Tenant-supplied add-on code. Our rule I8 says plugins reach data only through our API, never the database directly.

4. The decision

  • Allocator, per type. For a gaps type (the default) the number is handed out in a tiny step after permission and validation checks, on its own small pool of database connections (L2s). For a gapless type it is taken at the very end of the save, so a failed save gives the number back (L1). If someone retries a request we already completed, they get the same record and the same number back.
  • Switching a type's mode is safe. Both modes use the same counter, so a switch can never hand out one number twice. The switch applies to creates that start after it. A test switches the mode back and forth while creates are running and checks for duplicates.
  • Every format starts with the type's prefix. Right after the prefix comes a digit, a date part, the counter or a separator such as - or /, never another letter. Because prefixes are unique letters, the letters at the start of any number always identify exactly one type, so searching by number finds exactly one record. A format without the prefix is refused when published (number_format_prefix_required). Your examples become VISA-202611____, VISA-20261110__ and VISA/BLR/26/__/11. If you ever want numbers without any prefix, that would make numbers unique only within a type; tell us and it becomes a product decision.
  • Patterns. Pieces available: the type's prefix, year, month, day, a counter of chosen width, and a value from a fixed list on the record (for example the branch). Patterns are checked when published; anything ambiguous is refused with a clear message.
  • Restarts. A counter restarts for whatever the pattern shows: a pattern with a month restarts monthly; one with a branch keeps a counter per branch.
  • Changing a format never rewrites existing numbers. A changed pattern starts a new counter (a new epoch), and we refuse a new pattern that could ever produce a number an older pattern of the same type already produced. Different types cannot clash, thanks to the prefix rule above.
  • Running out. A format either grows the counter past its width, or refuses the create with a clear "number space exhausted" error. You are alerted at 90 % use.

4a. Security conditions on formats and plugins

Security approved the new format tables and the plugin route with six conditions, C8 to C13. They are rules of the ADR (§3.7). Two of them would be High if missed, meaning one tenant could reach into another's data or a plugin could act with more rights than it should.

ConditionIn plain wordsIf missed
C8Every link between tables (a type to its format, an epoch to its type) includes the tenant, so a tenant can never point at another tenant's format, and cannot even learn whether one exists. The database checks links without applying tenant filtering, which is why the tenant must be part of the link itself.High
C9The format tables are built exactly like our existing record-type tables: tenant-filtered by the database, format names unique per tenant only, published versions can never be edited or deleted.at scale
C10A new epoch is taken inside the same save as the type's publish, with the type locked, so two admins publishing at once get a clear answer instead of an error.at scale
C11Plugins cannot write formats yet. The admin screen ships first. We have no plugin identity today. Before plugin writes are switched on, five things must exist: one login per plugin per tenant; the tenant taken from the installation, never from what the plugin sends; the plugin recorded as a real user in the audit trail; a plugin's rights can only narrow its tenant permissions, never widen them; and permission to edit formats does not include permission to change a record type.High
C12The audit trail records "this change came from plugin X" from the server's own knowledge of who called, never from a field in the request, so nobody can disguise who made a change.at scale
C13"Re-publish linked types" checks, type by type, that the person asking may change that type, and the report shows nothing they could not already see.at scale

The implementation must also add tenant-isolation tests for each of these (for example: tenant A asking for tenant B's format gets exactly the same "not found" as for a format that does not exist).

6. Moving from today, safely

The counter table gets a new column and a new key. To avoid breaking record creation during a rollout, the change happens in four steps: add the column, build the new index in the background, deploy code that uses it, then switch the key. Custom formats stay switched off until the last step is done. Existing types keep the empty scope, so INC0000042 is followed by INC0000043; a test pins exactly that.

7. Evidence

  • Spike S1 (Technical Architect): every option measured with 8 simultaneous creators, on a quiet and a busy machine, plus 3 forced database crashes with no duplicate numbers. Code and raw output: docs/adr/ADR-005/spikes/technical-architect/s1/.
  • Counter bench (Postgres specialist): every migration step timed, the rollout failure reproduced (which is why the four-step order exists), and lookups shown to stay just as fast at 1.43 million counter rows. docs/adr/ADR-005/spikes/postgres/counter-scope/.
  • Reviews: Security approved twice: the design, and then the format tables and plugin route added in the revision (conditions C1–C13, all written into the ADR), the Technical Architect approved, and the Postgres specialist's two required fixes were made and re-checked.

8. Still owed, not blocking

  • A clean re-measurement of a single user creating a record over the network (the database part is 15–32 ms; the rest of the 174 ms miss is elsewhere and is tracked on TICK-621).
  • Code-running plugins come back only when we have a safe plugin runtime, a tenant needs a format patterns cannot express, and there is at least 20 ms of speed headroom to spend.
