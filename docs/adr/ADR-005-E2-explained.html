ACCEPTED · 2026-11-13 ADR-005-E2 · issue TICK-775 · amends ADR-005 §3.5 · source: TICK-667 (PR #615), number-format compiler

A counter that "grows" may not sit directly next to a digit

In three sentences. (1) When a ticket-number counter outgrows its digits, a format can either grow (print more digits) or refuse (stop creating tickets of that type until the format is widened). (2) The decision record allowed "grow" in some formats where the counter comes right after a date, which makes numbers like INC261000 hard to read; the code that was built refuses those formats, which is what its task asked for. (3) We keep the code's stricter rule and correct the document, because loosening a rule later is harmless, while tightening it after customers have formats would break them.

1. The problem in plain words

An admin can design a ticket-number format such as VISA-2026110001: a fixed type prefix, a year and month, and a counter of four digits (written {seq:4} in the format). The format also says what happens on the 10,000th ticket of a month, when four digits are no longer enough. That setting is called overflow:

grow
the counter just gets a fifth digit: VISA-20261110000.
refuse
creating tickets of that type fails with a clear "number space exhausted" error, and the admin publishes a wider format. An alert fires at 90 % use.

"Grow" is only sensible if a person can still see where the counter starts. If a digit sits directly before the counter, they cannot:

The decision record (ADR-005 §3.5) only constrained what comes after the counter. Read literally, it allowed "grow" for {prefix}{yy}{seq:3} and for VISA-2026110001. The format compiler built in TICK-667 refuses both, as that task's acceptance criterion required. Document and code disagreed, and the difference is something an admin sees: an error when publishing a format.

2. Options considered

OptionWhat it meansVerdict
A. Adopt the code's ruleNo digit directly before or after the counter when growing. Fix the document.Chosen
B. Loosen the code to match the old textOnly check what comes after the counter.Rejected: allows unreadable numbers and contradicts the task's acceptance criterion
C. Drop the ruleIt is not needed for uniqueness today, so allow grow everywhere.Rejected: readability, and the "after" half is needed for uniqueness once branch-code tokens arrive (S19)

Why the strict side wins. No tenant has published a custom format yet: they stay switched off until the counter migration and the admin API (S18) are done. Loosening a publish rule later never breaks anything that exists. Tightening it later would leave already-published formats invalid. So now is the cheapest moment to be strict.

3. The decision

grow is allowed only when the number reads unambiguously without the template: no token or literal that renders a digit is directly before or directly after {seq:N}, and every other variable-width token is followed by a literal outside its character set or ends the number. {field:br}{seq:3} and {prefix}{yy}{seq:3} are refused with number_format_invalid; use refuse.
Formatgrowrefuse
{prefix}{seq:7} (today's default, INC0000042)allowedallowed
{prefix}-{yyyy}-{seq:4} (VISA-2026-0001)allowedallowed
{prefix}/{yy}/{seq:2}/{MM}allowedallowed
{prefix}-{yyyy}{MM}{seq:4} (VISA-2026110001)refused (new)allowed
{prefix}{yy}{seq:3}refused (new)allowed
{prefix}-{seq:2}{yy} (digit after)refused (as before)allowed

The admin sees error number_format_invalid (HTTP 422) pointing at the counter, with the text "grow needs a non-digit before {seq:N}; use refuse". The admin API task (TICK-672) adds it to the error catalogue.

4. The fix

No code changes: the compiler in PR #615 already implements the chosen rule. This erratum corrects ADR-005 §3.5 (a note in the section and at the top of the ADR), and the ADR-005 summary page points here.

5. What you are accepting

ConsequenceSizeWhat would make us revisit

If a type creates more than 10,000 tickets in one month, further creates of that type fail until an admin publishes a wider format. The 90 % alert warns ahead of time. No risk to tenant isolation or to uniqueness: the rule only refuses more formats at publish time, and adds nothing to ticket creation.

6. Evidence

  • Stricter, never looser. Every format the old text refuses, the code also refuses (Technical Architect review of PR #615).
  • Uniqueness does not depend on it today. A spike rendered 1,259,690 numbers for each of five "digit next to the counter" formats, every counter past its width: 0 clashes. Rerun on this issue with the same result. docs/adr/ADR-005/spikes/technical-architect/e2-grow-injectivity/.
  • Different formats of the same type cannot collide, checked separately: a property test over about 45,000 format pairs and a fuzz run of 2.87 million cases, both passing; four deliberately broken versions of the check were all caught.
  • The code: internal/records/numbering/template.go, function unambiguous(), on PR #615.
