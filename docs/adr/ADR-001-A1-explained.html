ADR-001 amendment A1 explained

The decision in three lines. (1) Upgrade our workflow engine, Temporal, from version 1.28.4 to 1.29.7. That's a routine move, not an emergency. (2) Add a new safety rule, D9, which closes a real gap: today a platform component could ask Temporal's own internal machinery to destroy another tenant's work. (3) Add a startup check, D6-K, so the engine refuses to start if anyone switches off a safety setting.

Words used throughout:

  • Temporal is the engine that runs our long-running background jobs, called workflows (for example, "wait for approval, then send the email"). We run our own copy of its server.
  • A tenant is one customer organisation. Many tenants share the platform, and the top rule (ADR-001 I2) is that no tenant can see or change another tenant's data.
  • Namespace: Temporal's own top-level partition. We use one, called nava, for all tenants. Inside it, each tenant's workflows are labelled t:<tenant>:…, and our access checks keep them apart.
  • The Authorizer is our gatekeeper code inside Temporal. Every request passes through it, and it decides allow or deny based on who is calling.
  • A task queue is a named inbox inside Temporal. A workflow is placed on a queue, and whichever program is listening on that queue (a worker) runs it.

1. The problem, in plain words

What the alert said

A public security advisory, GO-2026-5766, says every Temporal version below 1.29.5 lets one namespace terminate or tamper with workflows in another namespace. Our security scan in CI (the vulncheck gate) flags our version, 1.28.4, so the build is red.

What is actually true

1.28.4 is not affected. The broken code was added in 1.29.0 and fixed in 1.29.5. Two reviewers read the source and ran tests: the bug is absent on 1.28.4, present on 1.29.4 and fixed on 1.29.5. The advisory's version range is simply too wide.

Why we move anyway

The gate checks versions, not code paths, so it stays red until we move. We won't add an exception to silence it. Urgency is normal: there's no live risk from this advisory.

Why 1.29.7 and not 1.29.5? A different advisory, GO-2026-5578, is broken again in 1.29.0 to 1.29.5 and fixed in 1.29.6. Version 1.29.7 is the newest release in that line and clears both advisories. Never land on 1.29.0–1.29.4: on those versions our setup would be exploitable.

2. The real gap review found (S1)

While checking the advisory, the Security reviewer found a separate problem. It exists on every version, old and new, so the upgrade alone doesn't fix it.

Temporal ships its own internal workflows, for example a batch workflow that can terminate many workflows at once. They run on an internal queue and act as Temporal's own all-powerful system identity, temporal-system. Our Authorizer lets temporal-system do anything, because Temporal needs that to run itself.

The gap: our relay, the platform component allowed to start workflows, could start Temporal's internal batch workflow instead of one of ours. Nothing checked which workflow or which queue it named.

How exposed are we today? No tenant can trigger this yet, because the relay code that turns customer actions into workflow starts doesn't exist yet. It would go live the moment it does. That is why the fix ships in the same change as the upgrade (the T27d pull request) and not later. A stolen worker certificate could abuse two related routes, through what a worker listens to and what it asks Temporal to do, so D9 closes those too.

3. How D9 blocks it

D9 is an allow-list for work, not just for actions. Before D9, the Authorizer only asked whether this caller is allowed to start a workflow. With D9 it also asks which workflow, on which queue, for which tenant. Only names written in our code are allowed. Everything else, including every internal Temporal name present or future, is refused because it isn't on the list. We deliberately did not write a block-list of "bad" names: a block-list misses the next name Temporal adds.

PartWhat it covers, in plain words
D9a: startsThe relay may only start or signal our own workflow types, on our own queue, labelled with a tenant.
D9b: listeningA worker may only listen on our queues. Each worker also gets a private, temporary queue (a sticky queue) for speed. Its name must look exactly like the random name the Temporal library generates (host:uuid), so it can't be named after an internal queue to eavesdrop on it.
D9c: what workers ask forWhen a worker asks Temporal to do the next step (run an activity, start a child workflow, restart itself as a new run), the same list applies. A missing workflow type is refused, not filled in.
D6-K: defence in depthWe switch off Temporal's batch and schedule features, which the first milestone doesn't use, and the server refuses to start if any of them, or any authorization-bypass setting, is switched back on.

4. What changes in the upgrade

Temporal keeps its data in our PostgreSQL database. Version 1.29.7 needs a slightly newer table layout, the schema: main store 1.17 → 1.18. The search store stays at 1.9. The order matters, and the software enforces it.

Still open, and owned by the Technical Lead: whether any data on today's 1.28.4 servers must be kept (E4). The development and CI servers can simply be recreated. It doesn't block your decision.
