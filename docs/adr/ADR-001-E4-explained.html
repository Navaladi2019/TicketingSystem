PROPOSED · REV 1 · 2026-11-26 ADR-001-E4 · issue TICK-1140 · corrects ADR-001-A1, Decision 3 · round 1 taken; re-check approved (Technical Architect, Security)

The decision says a failed security-flaw check blocks every merge. It does not. We correct the text, and make it block the changes that matter

In plain words

Goal
Make the written decision about our check for known security flaws true. The check compares the third-party code we use (code written by others, built into our programs) with a public list of known flaws.
Today
The decision says the check runs on every proposed code change and must pass before it is merged (added to the main code). On 10 November it was moved, and the owner asked for it to run every second day. It also runs when a proposed change touches our lists of third-party code. A failed check then blocks nothing for our own program. For the workflow engine we run beside it (the program that carries out long-running steps such as approvals), the check shared its name with another check that must pass, so it was unclear which of the two the hosting service (GitHub) counted. That shared name was removed on 25 November (PR #900). A later test showed that a newer result on the same change does replace an older failed one (PR #902), so the check still blocks nothing until the new rule below is built.
What's new
The text says what really happens. The two checks get different names. And one new result, shown on every proposed change, must be green (passed) before a merge. It is green without checking anything when neither the lists of third-party code nor the check itself changed, and it is the result of the check when they did. That result is given its name only on changes aimed at the main code, so a run of the same change for another target cannot stand in for it. We expect this to work because GitHub refuses a merge while a result it was told to require is missing or red (failed). The last step tests that on a real change.
Who is affected
Customers see no difference. Engineers see one more result on each proposed change. A change that updates third-party code can no longer be merged while the check fails.
Risks
A flaw made public after a merge can stay unseen for about 50 hours, because the check runs every second day; the owner chose that. If a flaw has no fix yet, updates to that list of third-party code wait until our architects and technical lead decide what to do. Until the new rule is built, no machine stops a bad merge: the AI agents who merge code must follow the written rule that every result is green. Someone who changes both the check and its reference copy can still make it pass without checking; only a security review of such changes stops that. The scan only means something if it checks the same Go version the product is built with, so the build now compares the two.
How we'll know it worked
Half-way: the new result appears, green, on a change that touches only documents. At the end: a test change that adds third-party code with a known flaw shows red, and GitHub refuses the merge.

1. The problem we faced

The scanner is govulncheck. It reads the two modules we ship (a module is a Go program with its own list of libraries, go.mod and go.sum): the root module, our platform, and temporal-server, our build of the Temporal workflow engine. A required check is a named result GitHub insists on before a merge into main.

The decision saidWhat is built
A required step of the main test workflow, ci.ymlA workflow of its own, govulncheck.yml: every second day, by hand, and on pull requests (proposed changes) that change one of the four list files
A red result blocks the mergeRoot module: it does not. Temporal module: not known

What we found on the way (fixed since by PR #900, 25 November). Two different jobs were called temporal-server: the unit tests in ci.yml and the scan in govulncheck.yml. Branch protection requires a check by name, so GitHub marked both as required. GitHub's documentation says only that this "can cause ambiguous status check results". It could go wrong the other way too: a green scan might count in place of red tests. The tests protect the part of the server that keeps customers apart. We found no case of it: in the three merged changes where both ran, both were green.

3. The decision

E4-1. Text
Decision 3 says where and when the scan runs. Zero findings and no exception stay.
E4-2. Clearing a finding
An ordinary bug fix after a full test run in which the Authorizer, unit, integration, isolation and stack tests all passed. The architects decide if it moves a Temporal version we pin, changes an Authorizer reference file, or uses replace, exclude or a fork. Security reviews it if it moves a library on the trust path (grpc, protobuf, jwx, pgx) or changes a test's expectation. A flaw in Go itself is cleared only when the Go we scan with equals the Go in every image we build.
E4-3. Until it is built
The agents' rule stops the merge. On a library change each of the scan jobs and the Authorizer tests must say success; skipped or missing counts as red. Until TICK-1146's fix is merged, the reviewer reads every check run on the head commit, across all runs, not the merge box or the latest run. Any result other than success is red.
E4-4. Required
The new job vulncheck always reports. It has that name only on changes aimed at main: a check belongs to a commit, so the same commit aimed at another branch could otherwise lend its green result. A change to the check itself, to an image's Go version or to a go.work file scans both modules. The full rules and tests are in docs/adr/ADR-001/E4/vulncheck-contract.md.
E4-5. Unique names
No two workflows report the same check name. A test enforces it over every job; there is no list to keep in step.
E4-6. Schedule
Every two days, as the owner decided.
