ACCEPTED · 2026-11-22 ADR-010-E3 · issue TICK-1085 · amends ADR-010-E1 (CI-6 rewrites) and the ADR-010 test bullet "format-1 equivalence" · source: TICK-1049 (T-A2-5), TICK-1084 (S21 fix)

A service desk agent in one group gets their ticket list in 1 ms, not 61 ms, by asking "equal to my group" instead of "in my list of groups"

In three sentences. (1) The standard access rule "agents see tickets assigned to their group" is turned into a database query that asks "is the ticket's group in this list?", even when the list has one group, and on PostgreSQL 16 that makes one page of the list read and sort about 20,000 tickets. (2) Asking "is the ticket's group equal to this group?" returns exactly the same tickets in about 1 ms, but a test that guards older access rules (CI-6) forbids any change to the query text except two named ones. (3) We name a third, narrow allowed change, (c), and keep the test strict about everything else.

1. The problem in plain words

Each ticket type has access rules: who may see which tickets. Every new tenant gets a default rule for incidents: members of the service desk group see tickets whose assignment group is one of their own groups. In the rule this is written caller: my_groups ("the groups of whoever is asking").

The platform turns each rule into a piece of SQL (the database's query language). For my_groups it always writes assignment_group_id = ANY(list), "the group is any of these", and passes the caller's groups as a list. Most agents are in exactly one group, so the list has one element.

The ticket list shows 50 tickets per page, newest first. The database has an index (a pre-sorted lookup table) called records_list_group, sorted by tenant, ticket type, group, then last-updated time. If the query says "group = G", the database can walk that index from the newest ticket of group G and stop after one page. If the query says "group is any of [G]", PostgreSQL 16 does not use the index's order for the sort: its planner treats any "any of" test on a column that is not the first in the index as unordered, whatever the list's length. So it reads all of G's tickets (about 20,000 in the test data), checks the filter on each, then sorts them to find the newest 50.

Why it matters. The performance target for this list (the "≥ 40% ACL cell": a filter that matches 40% or more of the tickets, under access rules) is 350 ms at the 95th percentile (p95: 95 of 100 requests are at least this fast). On fresh test stacks it measured 361, 429 and 277 ms. The earlier design (ADR-006-A2) assumed one page costs at most 20.6 ms; it cost 49 to 62 ms.

Why the fix is blocked. When the access-rule format changed (ADR-010), a test called CI-6 was written to prove that old-format rules still produce the same SQL as before, character for character. Erratum E1 allowed exactly two named exceptions, (a) and (b), and said explicitly that the test must not accept every one-item list turned into "=". The one-line fix fails CI-6 on exactly one case: the default incident rule for a service desk agent.

3. The decision

E3-1. Rewrite (c) is allowed
A caller: my_groups condition, for a caller in exactly one group, is written as assignment_group_id = $n::uuid with that group's id, instead of = ANY($n::uuid[]) with a one-item list. It applies wherever that condition appears: old and new rule format, the page and the count query, and the "not already matched" parts of later branches.
E3-2. Narrow scope
Only my_groups. Only one group. A caller in no group still sees nothing through this rule (fail-closed, unchanged). Two or more groups keep "any of". Lists typed into a rule by an admin keep "any of", even with one item. Shares are untouched.
E3-3. The test stays strict
The test's normalizer learns (c) only for that column, that caller and that argument. It records which rewrite applied to which case, and fails if a rewrite shows up anywhere not listed. The reference file is still the old code's output and is not regenerated.
E3-4. Same tickets, proven
"group is not empty and equals G" and "group is not empty and is any of [G]" select exactly the same rows, and so do their negations. Tests: one-group, two-group and zero-group rendering; a real-database comparison that both forms return the same tickets and page cursors; the random Go-versus-SQL checker must show it actually compared a my_groups rule against a one-group caller, and against a multi-group caller, in the same check.
E3-5. The plan test checks the right node
The fast plan still sorts the final 51 rows at the very top (0.85 ms). TICK-1084's "no Sort node" test must check that there is no sort between the group index and the page limit, not that the plan has no sort at all, and that the index read fewer than 10% of the group's matching tickets (QA's fast plan read 115 of 20,137). It runs on the exact query the code produces.
Why PostgreSQL 16 does this
Confirmed in the PostgreSQL 16.10 source by the Technical Architect (indxpath.c, found_lower_saop_clause). PostgreSQL 17 lifted the restriction for one-item lists, but not for several groups, because the index is sorted by group first.

Glossary

CI-6
The test that old-format access rules still produce the same SQL after conversion to the new format.
Golden
A reference file holding the old code's exact output, which the test compares against.
Rewrites (a), (b), (c)
The only text differences CI-6 accepts: (a) dropping a "true AND", (b) "= me" for caller: self, (c) "= my group" for caller: my_groups with one group.
Fail-closed
When information is missing (here: the caller has no group), the rule grants nothing.
I5
Platform invariant: the SQL filter and the Go access check always agree.
