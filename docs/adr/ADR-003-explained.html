ADR-003, explained

The whole decision in three sentences. (1) Our CI keeps recordings of past workflow runs and replays them against new code, to prove that runs still in flight won't break. Those recordings may never be edited or deleted, so there was no legal way to retire one when old code is finally removed. (2) We now allow a recording to be deleted only together with a precise, machine-checked "tombstone" note, and only when the old code is removed in the one safe way: the version check stays in the code, and only its oldest allowed version is raised. (3) CI checks every step mechanically. The one thing CI can't see, "no old run is still open in production", is checked by the Operator, and only you merge such a change.
How big is this? It is small, and design only. It touches test code, test data and docs, with no production code change. Nothing needs it today. It matters the first time someone removes old workflow code. It is a standalone ADR, not an ADR-001 amendment, because it changes no platform invariant. It does set a deploy rule that only a human may approve, which is why it needs a durable record.

Terms used here

Workflow run
One execution of our ticket automation (nava.interpreter) on Temporal, the engine that runs long-lived workflows. A run can last days.
History
Temporal's log of everything a run did. If a worker restarts, Temporal replays the history through the current code to rebuild the run's state. The code must make the same decisions again, or the run breaks.
Recorded history
A history saved as a file in internal/workflow/testdata/histories/. CI replays every one against each change. This is the "replay gate".
Append-only test
TestHistoriesAppendOnly. It fails if a recorded history that is on main was edited or deleted, so nobody can make the gate green by rewriting the evidence.
GetVersion
Temporal's way to change workflow code safely. Old runs take the old path ("DefaultVersion", version −1), and new runs take the new one. It is called with an oldest and a newest allowed version (minSupported, maxSupported).
Retiring the old arm
Removing the old path once no run needs it.
TMPRL1100
The error Temporal raises when a run needs a version the code no longer supports. The run then blocks: it waits, unharmed, until the code is fixed.
Tombstone
One line in retired-histories.json saying which recording was deleted, its exact content id, which code change retired it, and which ticket holds the evidence.
Blob id
Git's fingerprint of a file's exact content.

1. The problem in plain words

Two of our own rules collided:

  • Deploy rule (c) lets us remove old workflow code once no run in production still needs it.
  • Once that code is gone, the recordings made before it no longer replay, so the gate goes red. But the append-only test forbids deleting them.

So old code could never be removed. And a careless escape hatch ("just delete the red recording") would let anyone hide a real breakage, which makes the gate worthless.

Review then found a second, worse problem. The obvious way to remove old code is to delete the GetVersion check. That turned out to be unsafe: Temporal then silently replays old runs down the new path. The gate goes green, and in production a missed old run quietly does the wrong thing.

3. The decision

Decision text (ADR-003 §1)
  1. A GetVersion change's old arm is retired only by raising minSupported. This means workflow.GetVersion(ctx, "<change_id>", workflow.DefaultVersion, N) becomes GetVersion(ctx, "<change_id>", 1, N) (or the first non-default version), and the DefaultVersion code is deleted. The call is never deleted.
  2. In the same PR, each recorded history that now fails replay with TMPRL1100 … removed support of version -1 … "<change_id>" is deleted from internal/workflow/testdata/histories/ and from wantHistories. One tombstone per deleted file is appended to the append-only manifest internal/workflow/testdata/retired-histories.json.
  3. TestHistoriesAppendOnly enforces this mechanically (§3), using git objects, Go AST literals and a local replay. There is no clock, no network and no judgment.
  4. Approval is human, outside CI. The Operator posts the rule (c) production query evidence after the Technical Architect approves the PR. Only the human owner merges a PR that touches the manifest ("MergePr" label). Agents never do.
  5. Scope: only the DefaultVersion arm. Retiring a later recorded version (≥ 0) is out of scope and needs its own decision (§7, RS-3).

What CI checks, in plain words

RuleCI fails the change when…
R-1a recording on main was edited (retiring is deletion only)
R-2a recording was deleted without a tombstone that matches its exact content
R-3an existing tombstone was changed or removed (the tombstone list is append-only too)
R-4a retired file name is reused
R-5′the GetVersion check was deleted, or it still accepts the old version
R-6′the tombstone names a change that never had an old arm on main (an invented excuse)
R-7′the version check's arguments aren't plain literals, so CI couldn't compare them
R-8the deleted recording does not fail replay with exactly "removed support of version −1" for that change (it was deleted for some other reason)

6. Evidence

  • Temporal SDK source at our pinned version (v1.49.0), read by both reviewers:
    • the SDK's own docs recommend keeping the GetVersion call "so that if there is older version execution still running, it will fail here and not proceed";
    • replay with no version marker resolves to version −1, which raises TMPRL1100 once it is unsupported.
  • Spike (Technical Architect, on our four recorded histories that use timers):
    • with the call deleted, all four replay green, so the danger is invisible;
    • with the call kept, all four fail with [TMPRL1100] Workflow code removed support of version -1. for "spike-rfc007-timer" changeID.
    It is archived under docs/adr/ADR-003/spikes/.
