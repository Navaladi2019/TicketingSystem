QuestionHow can tenant-defined fields on tickets be filtered and searched fast (under 150 ms) at 100k+ records, including a field an admin marks filterable after the data already exists?

1. The problem in plain words

Each tenant designs its own ticket fields, such as site, priority or customer tier. We store them in one flexible JSON column, records.data. Filtering on them is slow: filter[site]=s7 takes 1.3 s at the 95th percentile, against a 150 ms target.

The usual fix, an index on the JSON column, does not work for us. The reason is our tenant wall.

RLS (row-level security)
A database rule that makes every query see only the current tenant's rows. It is our main protection against one customer seeing another's data.
Leakproof
A property of a database comparison: it cannot reveal anything about a row through an error message. Under RLS, the database only uses an index for a comparison that is leakproof. Otherwise it first applies the tenant rule row by row, which means reading everything.
Index
A sorted lookup structure, like a book index, that lets the database jump to matching rows instead of reading all of them.

The JSON comparisons are not leakproof. So for our application user the database ignores any JSON index and reads the tenant's whole table: 9 ms with the index, 292 ms without it, in our earlier benchmark.

A new finding in this RFC: plain comparisons on text, whole numbers, floating-point numbers, dates and true/false are leakproof. Exact decimal numbers (numeric) and the database's own full-text search operator (@@) are not. That shapes every choice below.

2. The decision

  1. Keep JSON as the truth; copy filterable fields into a typed side table. An admin marks a field "filterable" in the type designer. From then on, a database trigger copies that field's value into record_field_values whenever a ticket is saved, in the same transaction.
  2. Store numbers as floating-point, not as exact decimals, because only floating-point comparisons are leakproof. Whole numbers stay exact up to 9 quadrillion.
  3. Range filters on numbers and dates (for example "due before Friday") come back. Sorting by a custom field stays out until the benchmark shows its cost.
  4. Search ("tickets mentioning printer") uses a second side table that stores each word of a "searchable" field. Word lookups are leakproof, so they work inside the tenant wall.
  5. No per-tenant database changes. Flagging a field never changes the database structure, which keeps the rule "configuration, not code".

4. Marking a field filterable when 100k tickets already exist

  • The background job is a resumable workflow. If it stops, it continues from its last batch. Running a batch twice changes nothing.
  • It pauses between batches so it does not slow down people saving tickets.
  • Before it starts, it waits for every save that was already in flight when the admin flagged the field. Without this wait, a ticket saved at exactly that moment could be skipped forever; the Technical Architect reproduced this in rev 0, and the wait (the same trick PostgreSQL uses when it builds an index online) removes it. The same wait runs when a flag is cleared, so no leftover copies remain.
  • It locks each batch briefly, so a ticket edited at the same moment is never overwritten with an older value.
  • Dates and numbers are read the same way whatever the server’s time-zone or date settings are, so the live copy and the background copy always agree.
  • Rough duration: one to two minutes per field for 400k tickets. Unverified; spike S3 measures it.
  • While the field is not ready, a filter on it returns a clear "not ready yet" answer with progress, not a slow or failing query.

5. What is being accepted

ResidualIn plain words
StorageAbout 320 bytes per ticket per filterable field (about 2.6 GB at 800k tickets with 10 fields each). Search words cost more; S2 measures it. Quotas cap it: 10 filterable and 5 searchable fields per ticket type.
Save speedEvery filterable field adds work to each save. Estimated 25–40% fewer saves per second with 5 fields. Unverified: S1 measures it, and the quota is lowered if it is worse than 30%.
Search qualityFinds tickets containing the words (and word beginnings). No "best match first", no typo tolerance, no stemming. That needs a search engine: a decision for you (below).
Middle-range filtersA filter that matches 0.5–5% of a very large tenant may be the slow case. S1 measures it.
Decimal precisionNumbers with more than 15 significant digits may compare as equal when they are not.

5b. Security rules added in rev 1

  • Hidden fields stay hidden in search. If every searchable field is hidden from a user, search returns nothing, without running a query. It never falls back to searching all fields.
  • One query decides everything. The copied values are only ever used inside the same query that applies the user’s access rules. There is no separate count or summary that could reveal tickets the user cannot open.
  • Progress is a percentage only (“indexing, 43%”), so it cannot reveal how many tickets exist.
  • Every copied value is tied to its tenant’s field by a database rule, so a bug cannot file it under another tenant.
  • The background job never carries ticket content through the workflow engine’s history.

6. Decisions for the human (business tradeoffs)

H1. Accept database-only search (word and prefix match, no ranking, no typo tolerance) for now? Recommended: yes.

H2. When ranked search is needed: OpenSearch (Apache 2.0 licence) or Elasticsearch (licence to check with legal)? Recommended: OpenSearch, for search only. It is a new system to run (at least 3 servers for high availability, backups, upgrades). We do not have cost data yet.

H3. Accept the storage cost above? Recommended: yes, bounded by quotas.

H4. Keep filtering inside the database's tenant wall (no external store for filters)? Recommended: yes.
