QuestionHow can tenant-defined ticket fields be filtered fast at 100k+ records, including a field an admin marks filterable after the data already exists?
DecisionCopy each filterable field into a small typed table that the database can index safely inside the tenant wall. A database trigger keeps the copy in step on every save. A field flagged late is filled by a background job that cannot miss or duplicate a ticket.
Not decided hereFree-text search. The measured design was too slow and too large, so it moves to its own RFC (RFC-016).

1. The problem in plain words

Each tenant designs its own ticket fields, such as site, priority or customer tier. We keep them in one flexible JSON column. A filter on them today takes 0.8 to 1.3 seconds for a large tenant, against a 150 ms target, and is only kept from hanging by a 2-second timeout.

RLS (row-level security)
A database rule that makes every query see only the current tenant's rows. It is our main wall between customers.
Leakproof
A comparison that cannot reveal anything about a row through an error. Under RLS, the database only uses an index for leakproof comparisons. Comparisons on JSON are not leakproof, so a JSON index is ignored and the tenant's whole table is read.
Side table
A separate table that holds a copy of one field's values, with an index, next to the main ticket table.
Backfill
Copying the values of tickets that already existed before a field was flagged.

2. The decision

  1. Admins flag a field "filterable" in the type designer. This is configuration: it needs no database change per tenant or per field.
  2. A trigger copies the field on every save, in the same transaction, into one of four typed tables. Four tables instead of one made the database's row estimates accurate. With one shared table some filters took 1.3 to 1.8 s; with four tables the same filter takes 4.7 ms.
  3. Filters support equals, "one of", and before/after or less/more for numbers and dates. Sorting by a custom field is not included.
  4. A filter is always one query that also applies the user's access rules and field masks, so a filter can never reveal a ticket or a hidden field the user cannot see.
  5. Quota: 5 filterable fields per ticket type, up to 10 with operator approval after a cost check.

3. Flagging a field when 400k tickets already exist

  • Why the wait matters. In the first draft, a ticket saved at the exact moment of flagging could be skipped forever, and a ticket saved while a flag was being cleared could leave a stray copy behind. The Technical Architect reproduced both. With the wait, both came out at zero in two independent re-runs. It is the same technique PostgreSQL uses to build an index without stopping writes.
  • The job copies in batches of 1,000 and pauses between batches (starting at half a second) so people saving tickets are not slowed by more than a quarter.
  • Measured: about 3 minutes for 400k tickets on a quiet system, about 5 minutes under load, with zero differences against a full recount.
  • Until the field is ready, a filter on it answers "not ready yet" with a percentage, never with a slow query.

4. Options considered

OptionOutcomeWhy
A Typed side tables kept by a trigger (the proposal from vknavaladi)ChosenWorks inside the tenant wall, needs no per-field database change, no new system. Measured.
B Spare columns on the ticket tableRejectedAbout 20 extra indexes would slow every save for every tenant, and filling a column late rewrites audited tickets.
C Promote common fields to real columnsFallbackOnly helps fields we name. Tenants' fields differ.
D External store (OpenSearch, Elasticsearch, MongoDB, Cassandra)Rejected for filtersThe tenant wall and access rules would live in our code instead of the database, and saved tickets would appear seconds late. Cassandra cannot do ad-hoc filters; MongoDB adds nothing and has a restrictive licence.
Word table for free-text searchMoved to RFC-016Multi-word and prefix searches took 0.5 to 1.4 s, the table was 3.5 GB (twice the tickets themselves), and saves dropped to 90 per second.

5. What is being accepted
