The slowdown alarm should compare each machine type with its own past, not with a fixed limit

In one sentence. The cue we chose for "the audit check got slower everywhere" went off constantly on one kind of CI machine and could not go off on another. We replace it with a per-machine comparison: if one machine type reads more than 1.2× its own recorded baseline in two main runs in a row, someone looks. Nothing in CI or in the product changes.

Words used here

Commit check, clause arm, reference arm, ratio
As in ADR-004-E4. The CI job commit-check-budget times the real audit check (the clause arm) and an unchanged copy (the reference arm) on the same machine. It fails if the clause/reference ratio is out of range.
Review threshold, warn
Fixed limits: 300 µs per call and 175 µs per import record (µs means millionths of a second). Since E4, going over one only produces a yellow warning (warn), and the job still passes.
CPU model
The processor of the rented GitHub machine (the runner). We ask for the same machine size every time, but GitHub hands out several processor models, and the fastest is about 2.4× faster than the slowest. Every run now logs its model.
Baseline
A timing recorded for one CPU model in docs/budgets.md: that model's normal speed.
Uniform regression
A change that slows both arms equally, for example a slower shared insert path or a Postgres upgrade. The ratio does not move, so the CI gate cannot see it. ADR-004-E4 accepted this risk (E4-R1) and named a cue that tells a person to look.

The problem

E4's cue was "two warn runs in a row on main, on a CPU model we have a baseline for". A spike (a small, timeboxed measurement experiment) ran the job 16 times on one version of the code. The good news is that one CPU model gives steady timings: at most 1.13× apart, and usually under 1.07×. The bad news is that warn applies one fixed limit to every machine, and the machines differ far more than that:

  • Always on. The AMD EPYC 7763 machine is simply slow. Its import timing is normally 189–195 µs, over the 175 µs limit, so all 7 of its runs were warn. It got 7 of the 16 runs, so the cue would go off week after week with nothing wrong, and people would learn to ignore it.
  • Never on. The AMD EPYC 9V45 machine is fast, at about 80 µs per import record. The code would have to get about 2.2× slower before it crossed the limit, so a 1.5× slowdown would go unnoticed.

Options considered

OptionWhat it meansOutcome
Keep the E4 cueTwo warnings in a rowRejected. It is always on for 7763 and blind below about 2.2× on 9V45
Per-model bandCompare each run with its own model's baseline, and look when two runs in a row are more than 1.2× offChosen. It fits the measured noise (≤ 1.13×), catches a 1.2× slowdown on every recorded model, and needs no code
Warning rate over a time windowCount warnings per weekRejected. It is still tied to the fixed limit, so it has the same two faults
Make the band an automatic CI check nowThe script compares and flagsDeferred. It needs baselines the script can read, and a hard gate this tight would go red on noise. It may come later as a summary line, never as a failure
Re-check every baseline that is over the limitThe second half of the old cueChanged. Every 7763 re-take is over the limit, so this clause would also be always on. Now it reads: a re-take more than 1.2× that model's previous baseline

The decision

  1. Off-baseline row: on a CPU model with a recorded baseline, any of the four timings is more than 1.2× that model's baseline. The four timings are per call after 200, 1,000 and 5,000 writes, and per import record.
  2. Trigger to look again at the risk: two main runs in a row on recorded models, each with an off-baseline row. Or a baseline re-take that is more than 1.2× the same model's previous baseline. Runs on machines with no baseline are skipped.
  3. A slow machine is not a regression. A baseline over the fixed limit with a normal ratio is recorded as "slow host" and needs no escalation. The 7763 import baseline is annotated that way: 194.9 µs, with a ratio of 8.58, in line with 8.13–9.75 on the other models.
  4. Still manual. As in E4, the Postgres specialist reads the logged numbers, and nothing alerts anyone automatically. The warnings themselves do not change.
  5. A baseline is the median of at least 3 runs. The band is close to the worst noise we measured, so a baseline taken from one unlucky run would shift it. The spike's rerun recipe takes about 6 minutes.

The change

  • docs/security/accepted-risks.md: the AR-TICK-517-01 trigger is reworded.
  • docs/budgets.md: the 7763 import baseline gets a "slow host, not a regression" note.
  • docs/budgets.md: the method now says a baseline is the median of at least 3 runs on that CPU model.
  • The spike note is archived under docs/adr/ADR-004/spikes/technical-architect/.

No code, CI job, threshold, database or production behaviour changes, so no plan issue is needed.

What we are accepting

  • A slowdown under 1.2× still passes unseen, and so does one that shows only on machine types we have no baseline for. A slowdown of 1.2× or more is seen only when someone reads the logs. Severity stays low (AR-TICK-517-01).
  • The evidence covers one hour on one code version. Older baselines from other days, on other code versions, fall inside the same ranges or within 1% of them. Day-to-day drift is still not fully measured. If it is larger, the band gives false alarms. A false alarm costs a look, not a red build. If two happen within 30 days, we re-run the spike across days and then widen the band or switch to a rolling median.
