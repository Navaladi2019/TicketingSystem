PROPOSED · 2026-11-20 ADR-010-E2 · issue TICK-1012 · amends the ADR-010 test table and RFC-022 §5 · source: TICK-945 (S30 handbook)

Saving access rules over someone else's newer version is refused with 412, and the ADR said 409

In three sentences. (1) ADR-010's test table says that saving access rules based on an out-of-date version returns the status code 409. (2) The system returns 412, the code every "save only if nothing changed since I read it" request in our API uses, and the tests already check 412. (3) We correct the document, not the code: nothing in the running system changes.

1. The problem in plain words

An admin edits a ticket type's access rules (who may see or change which tickets). To stop two admins overwriting each other, the save request carries the version the admin started from, in a header called If-Match. If someone published a newer version in the meantime, the save is refused and the response names the current version (in the ETag header) so the admin can reload.

An HTTP status code is the three-digit number a server answers with. 412 Precondition Failed means "the condition you attached (the version) no longer holds". 409 Conflict is a more general "clashes with the stored state". Our API uses 412 version_conflict for every If-Match refusal, and reserves 409 for other clashes, such as reusing a request's idempotency key (a unique id the client sends so a retried request is not applied twice) with a different body.

The RFC behind ADR-010 wrote "409 ConflictError": it read the Go error's name, ConflictError, as a status code. The ADR copied the 409. The S30 handbook writer noticed the mismatch.

2. Options considered

OptionVerdict
Correct the ADR's test table by erratumChosen: the documents match what ships and what is tested.
Change the code to return 409Rejected: it would make this one route differ from every other versioned save, break clients and the S10 acceptance kit, and go against the HTTP standard's meaning of 412.
Edit the archived RFC in placeRejected: archived RFCs stay as written; errata record corrections.
Leave it to a handbook noteRejected: the ADR is the normative text engineers write tests from.

3. The decision

A save whose If-Match names a version that is not the newest gets 412 version_conflict with the current version in ETag, and writes nothing. Two saves from the same version write once: the second gets 412, whether it arrives later or at the same moment; if it repeats the first one's idempotency key and body, it gets the first one's 200 replayed instead.
E2-1: the code is 412 version_conflict
As the route, its tests and the S10 kit already do.
E2-2: the double-save line names both outcomes
412 with a new key, the replayed 200 with the same key. One version either way.
E2-3: the RFC stays as written
This erratum is the correction; the ADR-010 row points to it.

4. The fix and migration

None. No code, data, API contract or test changes. The API description already lists 412 for this request.

5. What we are accepting

No residual risk: the document now matches shipped and tested behaviour.

6. Evidence

  • internal/server/access.go, PutEntityTypeAccess: a stale If-Match becomes ConflictError, answered as 412 version_conflict with the current ETag.
  • internal/authz/publish.go, publishLocked: two simultaneous saves are serialized by a lock on the ticket type; the second re-checks the version and gets the same 412.
  • internal/server/access_integration_test.go: tests marked covers: putEntityTypeAccess 200 412 428 assert 412 and the current ETag; TestPutAccessReplayWithTheSameKeyWritesOneVersion asserts one version after a replay and 409 idempotency_key_reuse for a reused key with another body.
