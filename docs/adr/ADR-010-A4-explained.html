PROPOSED · 2026-11-26 ADR-010-A4 · issue TICK-1143 · RFC-023 rev 0 and rev 1 · amends ADR-010-A3 A3-1, A3-5, A3-R2 and A2-R4 · CTO tie-break comment 01a2154d

"Tickets in my region": make the count read one index instead of the whole ticket table

In three sentences. (1) When one customer holds about half of all tickets or more, the number shown above a region ticket list could make the database read every ticket of every customer, which pushed the list past its 150 ms budget. (2) We add one column to an index the list already uses, so the database can count from the index alone: 17 to 28 ms, warm or cold. (3) Nothing changes in the code or in the results; the price is a slightly larger index and about 1 to 1.5 % more write log.

1. In plain words

Goal
A list of tickets "in my region" shows a page of tickets and a total (counted up to 1,000). Both must come back within 150 ms for 95 of every 100 requests. We want the total to stay fast however big the shared ticket table grows.
Today
For a small ticket type under a large part of the organisation, the database counts by reading the type's tickets and checking each one's org unit. It sometimes guesses that it will find 1,000 matches quickly and reads the table from start to end (a sequential scan). When there are few or no matches, that means reading every row in the table, including rows that belong to other customers, whose data it then discards. In one test the page plus the count took 162 to 178 ms of database time.
What's new
An index is a sorted copy of a few columns that lets the database find rows without reading the table. The list already has one sorted by "last updated" per ticket type. We also store each ticket's org unit in it (an INCLUDE column), so the count can be answered from the index alone (an Index Only Scan). That read starts at the customer's own part of the index and never touches another customer's rows.
Who is affected
Agents whose access rule says "tickets in my region", on installations where one customer is large. They see the same tickets and the same total, faster. Operators see one index rebuilt online during the upgrade. Every ticket write also writes about 31 bytes more.
Risks
The index does not help when the agent also filters on something the index does not hold (a state list, a custom field). That case stays as it is today. The very first region list after a database restart can still take seconds. That is the page, not the count, and it is recorded, not fixed here.
How we'll know it worked
A test on a deliberately unfavourable table, one large customer plus others, fails today and must pass with the index. The test also checks that the plan is not a near tie that could flip. Then the region benchmark (TICK-1105) is re-run with a count at 500 matches.

3. Options considered

OptionVerdictWhy
Add the org unit to the existing "last updated" indexChosenThe only option no worse than today in any measured cell, warm or cold. No code change. Costs: that index +23 % in size (+2.3 % across all ticket indexes) and +1.0 to 1.5 % write log.
Make the count read in "last updated" order (the first proposal, RFC-023 rev 0)RejectedFast with a warm cache, but 9 to 10 s after a restart, against 1.1 to 1.7 s today. It also needs a code change and is 16 to 37 ms slower on some combined rules.
Both: the index and the orderKept as fallbackWith the index, both texts already plan as an index-only read, so the order adds nothing that was measured. It is applied only if a test shows the index-only read is not picked.
Change nothingRejectedThe count's worst case grows with the whole shared table, breaks the bound A3 promised, and its time reflects other customers' data.
Add every column a rule can name to the indexRejectedOne more column for each kind of rule, and it still cannot cover custom-field filters.

4. The decision

  1. The index. Build the new index online beside the old one, drop the old one, and give the new one the old name: records_list_updated (tenant_id, entity_definition_id, updated_at DESC, id DESC) INCLUDE (org_unit_id). The list page keeps using it as before.
  2. No code change. The count's SQL text and the page's SQL text stay exactly as A3 specified.
  3. A fallback, decided now. If a test ever shows the count is not answered from the index, the count gets the "last updated" order, but only when it has at most one region branch.
  4. Tests that pin the plan. On the test tables, the count must be an index-only read starting at the customer's own range. It must read no more rows than the customer's own tickets of that type. Its nearest rival plan must cost at least 1.3 times more, so the test cannot pass on a coin-flip. A deliberately broken build without the new column must fall back to the full-table read.

5. Migration

One database migration that runs outside a transaction: CREATE INDEX CONCURRENTLY for the new index, DROP INDEX CONCURRENTLY for the old one, then a rename. Tickets can be read and written throughout. A failed build leaves an unfinished index, which the migration drops when it is run again. At 800,000 tickets the build took 1.3 s; at production size it has not been measured, which is a recorded risk.

7. Evidence

  • Technical Architect's spike on PostgreSQL 16.10, using the real statements through the list code. W1 is 250,000 tickets of 1 KB for one customer. W2 is 800,000 empty tickets. Warm count: today 86–110 and 145–170 ms; order 61–80 and 64 ms; index 17.3–27.6 and 16.9–18.0 ms. Cold: today 1,122–1,654 ms; order 8,958–10,231 ms; index 18–25 ms. With 5 % of the type updated and no vacuum since, the index read still took 23.0–28.1 ms.
  • Postgres & Data Modeling Specialist: query plans in many table shapes, without timings. The test table (200,000 rows, one customer at 75 %) uses a full-table read today, 53 % cheaper than the next plan, so it fails before the change. With the index it is an index-only read in 4 of 4 loads. Comparing only the ticket-reading step, the full-table read costs 5.2 times the index-only read. Size and write-log costs as above.
  • Security & Multi-Tenancy Reviewer: plans with other customers' rows present. The index removes the cross-customer read for the plain count and leaves it under a default-valued custom-field filter. Rated Low; no isolation gap. Approved.
  • Not measured: the index-only read in combined rules beyond the two shapes above, the generic-plan case, and the build time at production size.
