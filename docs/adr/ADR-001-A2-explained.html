ADR-001 amendment A2 explained

The decision in three lines. (1) Tighten our gatekeeper, the Authorizer, so that a platform component can name only tenant workflows and our task queues, never Temporal's internal ones. Seven small rules do this. (2) Add one startup check, so Temporal refuses to start if a token-safety setting is switched off. (3) Write down a hard rule for our core API, R-CORE: it works out which tenant a workflow belongs to only from the user's login token, and it never passes a client's opaque token on to Temporal.

Words used throughout:

  • Temporal is the engine that runs our long-running background jobs, called workflows. We run our own copy of it, in one partition (a namespace) called nava, which all tenants share.
  • A tenant is one customer organisation. Each tenant's workflows are labelled t:<tenant>:…. The top rule (ADR-001 I2) is that no tenant can see or change another tenant's data.
  • Temporal also runs its own internal workflows inside nava, such as schedulers and deployment bookkeeping. Their names start with temporal-sys-.
  • A task queue is a named inbox. Our workers listen on one platform queue, nava-tq. A sticky queue is a worker's private cache inbox, named <host>:<random id>.
  • A service certificate is how our own components (nava-relay, nava-core and nava-worker) prove who they are to Temporal. The Authorizer is our gatekeeper code inside Temporal. It checks every request against the caller's allow-list.
  • A task token or a page token is an opaque blob that Temporal hands out ("here is your job", "here is page 2") and that the caller sends back later.
  • An erratum means our earlier decision (A1) already required the check and the code missed a case. An amendment is a new rule.

1. The problem, in plain words

Amendment A1 (20 October) added a rule: a request that names a workflow, a workflow type or a task queue is allowed only if every such name is on our list. A follow-up security audit (TICK-122) and this review found places where that promise still had holes. Every one of them needs an attacker who has already stolen one of our service certificates. None of them lets one tenant reach another tenant directly. This is clean-up of the wall, not a breach.

Reading or steering Temporal's internals

With a stolen worker or core certificate, someone could read the history of Temporal's internal workflows and could cancel or update them. In one case they could change how work is routed to our queue (F2-2, F2-4, F2-5).

Making Temporal start internal workflows

A worker that says "I use versioning" makes Temporal start its own deployment-tracking workflows inside nava (F2-1).

Forged tokens

Several "I finished this job" calls don't check whose job the token names. If one setting is switched off, the token can even point at a different namespace (F2-3, F2-3b).

Unplugging the shared inbox

A worker's "I'm shutting down, drop my private inbox" call accepts any queue name. Naming nava-tq makes Temporal briefly drop the main inbox that every tenant uses (F2-6). This affects availability only.

2. What we decided

One principle runs all the way through, so the rule is a list of what is allowed, not a list of what is banned:

Every workflow name a platform component sends must carry a tenant label, t:<tenant>:. Every queue name must be our queue, or a private-inbox name of the right shape. That includes names hidden inside tokens and heartbeats. If a Temporal upgrade adds a new field, our build fails until someone decides how to check it.

Why R-CORE has to be a written rule

The core API serves every tenant with one certificate. So the gatekeeper can check that a request names some tenant's workflow, but not which tenant. The only thing between tenant A's login and tenant B's workflow is how the core API builds the name.

The review also found a subtler path. When Temporal is asked for "page 2" of a workflow's history, it follows the page token, not the workflow name in the request. If the core API ever passed a client's page token straight through, someone holding a leaked tenant-B token could read B's history through tenant A's own record. No code does this today, because the core API doesn't call Temporal yet. R-CORE makes sure the first code that does is built correctly.

4. The fix

  • Gatekeeper code (temporal-server/authz): the seven rules above, each one denying with an alert. This is one core-dev task, which the Technical Lead plans.
  • Startup check (temporal-server/cmd/server): a new "must be true" mode, used for the token-namespace setting.
  • Build-time field check: CI keeps a list of every field in every request our components are allowed to send. If a Temporal upgrade adds a field, the build fails until someone decides how to check it. That is exactly how F2-6 slipped in: the shutdown request gained new fields over recent releases.
  • No configuration change and no data migration. Our current workers send nothing that the new rules deny. We checked this against the SDK source, and acceptance includes a smoke test of a normal worker shutdown.

5. What we are accepting (residual risks)

RS6: R-CORE is a code rule, not a gatekeeper rule

The gatekeeper can't tell tenants apart for the core API, and it can't see inside a page token. Correctness depends on one id-building helper and two tests: R-CORE-1 (someone else's record looks "not found") and R-CORE-2 (a client's page token is never forwarded). Security reviews the first core-API change that calls Temporal. Owner: Security & Multi-Tenancy Reviewer.

RS7: one worker can drop a sibling's private inbox

The new shutdown rule checks the shape of a private-inbox name, not who owns it, so one worker pod could drop another pod's private inbox. This is harmless: Temporal falls back to the main queue, so the job still runs, just without the cache. Owner: Security & Multi-Tenancy Reviewer. Revisit if worker certificates become per-pod or per-tenant.

RS2 (widened): startup-only check

Like the other setting checks, the new one runs only when Temporal starts. Revisit if we ever add a way to change settings while Temporal is running.
