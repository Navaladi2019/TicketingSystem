ADR-001 amendment A2, explained from the ground up

The whole decision in three sentences. (1) Our gatekeeper inside Temporal, the Authorizer, gets seven small rules. With them, a platform component can name only tenant workflows and our task queues, never Temporal's internal ones. That includes names hidden inside tokens and heartbeats. (2) Temporal refuses to start if one token-safety setting is switched off. (3) Our core API follows a written rule, R-CORE: it takes the tenant only from the user's login token, and it never forwards an opaque Temporal token it got from a client.
How serious is this? Every one of these findings needs an attacker who has already stolen one of our own service certificates. None lets one customer reach another customer's data. They are gaps in the second wall, not a breach of the first. The work is normal priority.

How to read this page. Parts 1 and 2 teach the background: what Temporal is and how we use it. If you already know it, skip to Part 3. Part 4 takes the six findings one at a time, always in the same order: the attack step by step, a diagram, what goes wrong, the rule that stops it, and the test that proves it. Parts 5 to 11 cover the rest of the decision. A glossary is at the end. Each term is also explained the first time it appears.

Part 1. Temporal from zero

Workflows and activities

Temporal is an open-source engine for long-running jobs that must not get lost, such as "approve this ticket, wait three days, escalate if nobody answered". We run our own copy (server version 1.29.7).

  • A workflow is one such job. Each one has a workflow id, a name we choose, for example t:acme:order-42. It also has a workflow type, which says what kind of job it is.
  • Temporal records everything that happens to a workflow as a list of events, called its history. If a machine crashes, the workflow is rebuilt by replaying its history. That is why workflows survive crashes.
  • An activity is one step of a workflow that touches the outside world, such as sending an email or writing to the database.

Namespaces

A namespace is a walled-off partition inside one Temporal server, a bit like a separate database schema. We use one namespace, nava, for every tenant. Temporal also keeps a namespace of its own, temporal-system. Because all tenants share nava, Temporal itself does not keep tenants apart. We have to.

Task queues, polling, partitions and sticky queues

  • A task queue is a named inbox of jobs. Temporal never pushes work to a worker. A worker (our code that runs workflows) polls: it asks "anything for me on queue X?" and waits. Our platform queue is nava-tq. We call it a platform queue because it is on our list.
  • Temporal splits a busy queue into partitions. Partition 0 is the root, and the others forward to it. Temporal's queue service is called matching.
  • A sticky queue is a worker's private inbox, named <host>:<random uuid>. Temporal sends the next step of a workflow there, so the worker that has it cached can skip a replay. If the sticky queue disappears, Temporal falls back to the normal queue. It's a speed-up, never a requirement.

Tokens: task tokens, query tokens, page tokens

  • When a worker receives a job, Temporal hands it a task token. The worker sends the token back with the result ("activity done", "activity failed", "still working"). The token is how Temporal knows which workflow and which step the answer belongs to. In our setup it's a plain serialized structure, token.v1.Task, and it is not signed. Whoever sends it chooses what it says.
  • A query asks a running workflow a read-only question. The worker answers with a query token, token.v1.QueryTask, which names a task queue.
  • A page token (NextPageToken) means "give me page 2 of this history". Temporal follows the token to find the data, and the workflow id in the request only picks which server shard to ask.

Temporal's own workflows: temporal-sys-*

Temporal implements some of its own features as workflows that run inside our namespace. Their ids start with temporal-sys-. For example:

IdWhat it does
temporal-sys-scheduler:<schedule>Runs a cron-like schedule.
temporal-sys-worker-deployment:<name>Records which build of workers is current for a queue ("worker versioning").
temporal-sys-worker-deployment-version:<version>Records one worker build.

Temporal also has an internal queue, temporal-sys-per-ns-tq. None of these are tenant data, but they steer how nava behaves. A platform component has no business touching them, and that is the theme of this whole ADR.

Part 2. How we use Temporal

Our four components and their certificates

Each of our components proves who it is to Temporal with a service certificate (mutual TLS). The certificate says which component it is, but not which tenant it's acting for.

ComponentJobWhat it may do in Temporal
nava-relayReads the outbox (rows our database writes together with each change) and starts or signals the matching workflow.Start and signal workflows (rule D9a).
nava-coreOur main API that users and apps call, with a login token (JWT).Cancel, update, query, describe and read the history of workflows. Until A2, no name rules applied.
nava-workerRuns every tenant's workflows and activities.Poll queues (D9b), send commands (D9c), report results with task tokens, read history, heartbeat, shut down.
nava-operatorAdmin tooling, only reachable from the operator network.Inspect anything, including system workflows. A2 leaves it outside D9.

The Authorizer and its allow-lists (D9)

The Authorizer is our code running inside Temporal's front door. For every call, it reads the certificate, finds that component's allow-list (the APIs it may call), and then runs the D9 rules on the request's contents. D9 is a set of name rules from amendment A1: D9a for relay starts and signals, D9b for worker polls, D9c for worker commands. Erratum E1 added a check of the task token on RespondWorkflowTaskCompleted. A1 states its governing promise like this:

A1's governing sentence, as quoted in the ADR

“A request that names a workflow type, a task queue or a workflow id is allowed only if every such field is allow-listed.”

F2 is the list of places where that promise wasn't fully kept.

How the t:<tenant>: label keeps tenants apart

Every tenant workflow id starts with t:, then the tenant id, then a colon: t:acme:order-42. The label is built by our code from a trusted source: the tenant on the outbox row (for the relay) or the tenant in the user's validated login (for core). It never comes from what a client typed. That is invariant I2: the tenant comes only from a platform-verified source. Temporal's own workflows never have the label, so "must start with t:<tenant>:" is an easy allow-list test: tenant workflows pass and everything else fails.

What a label can't prove

The Authorizer can check that an id has a tenant label. It can't check that it's the right tenant, because the certificate carries no tenant. For the relay, the right tenant is guaranteed by reading it from the outbox row. For nava-core, it has to be guaranteed by how core builds the id. That is R-CORE (Part 5).

Part 3. The threat: someone holding a stolen certificate

All the findings assume one starting point: an attacker has a copy of one of our service certificates. They might have got it from a compromised pod, a leaked secret or a bad backup. With it, they can talk to Temporal directly and pretend to be that component.

Already stopped before A2

Starting Temporal's workflows from the relay; spawning them as child workflows from a worker; signalling them; polling Temporal's internal queue; forging a token on RespondWorkflowTaskCompleted (D9a to D9c, E1).

Still open (F2)

Six ways in. A request field names a workflow id, a task queue, or a feature switch, and no rule reads it. Part 4 goes through them.

Why it is not tenant-to-tenant

A worker already runs every tenant's workflows, so a worker cert reaching tenant B is not new power. What's new is reach into Temporal's machinery. Each such reach is a stepping stone, and we close it now while it's cheap.

Part 4. The six findings, one at a time

Findings F2-1 to F2-4 come from the security audit (TICK-122). F2-5 was found while framing the RFC, and F2-6 in review round 1. F2-3b is the namespace half of F2-3. In the diagrams, red arrows are the attack today, the amber box is where the Authorizer fails to look, and the green band shows what happens after A2.

F2-1 A versioned poll makes Temporal start its own workflows in nava amendment A2

stolen certnava-worker
severityLow; exploitable with a worker cert
partAmendment A2

What the attacker does, step by step

  1. The attacker uses the stolen worker cert to poll our real queue, nava-tq. That is exactly what a worker is supposed to do, so rule D9b (which checks the queue name) is happy.
  2. They add two extra fields that say "I am a versioned worker": DeploymentOptions with mode VERSIONED, or the older WorkerVersionCapabilities.UseVersioning = true.
  3. Temporal's queue service (matching) sees a versioned worker and registers its deployment. Doing that starts temporal-sys-worker-deployment* workflows inside nava. The server setting system.enableDeploymentVersions allows this, and it defaults to on.

What goes wrong

Temporal now runs internal bookkeeping workflows in our shared namespace that we never asked for, and the attacker chose their names. Those workflows control how nava-tq is routed between worker builds. F2-4 shows how they can then be steered. Our own workers never send these fields: the SDK sends UseVersioning: false, and it sends DeploymentOptions only if a deployment is configured, which ours isn't.

The rule that stops it

Worker polls must be unversioned. We chose this rule over the alternative of switching the feature off in config. Part 9 explains why.
Decision text, word for word from the ADR

D9b+ (A2) · nava-worker: PollWorkflowTaskQueue, PollActivityTaskQueue

In addition to D9b: DeploymentOptions.WorkerVersioningMode must be UNSPECIFIED or UNVERSIONED (absent counts as unspecified), and WorkerVersionCapabilities.UseVersioning must be false. Anything else is denied with an alert.

The test that proves it

TestAdversarialF2SystemWorkflowsOnPerNSQueue in temporal-server/authz/adversarial_f2_test.go (merged with PR #36, skipped with the finding id). Subtest worker versioned poll starts deployment workflows: it sends both versioning shapes on both poll APIs and expects a denial.

Control that must stay green: the plain poll our SDK sends is allowed. The core-dev task also adds an allow-path test for the exact poll sdk-go v1.49.0 sends.

red today when the skip is removed → green once the core-dev fix lands.

F2-2 nava-core can act on any temporal-sys-* workflow amendment A2

stolen certnava-core
severityLow; bites at scale
partAmendment A2

What the attacker does, step by step

  1. The attacker has the stolen nava-core cert. Our core API is allowed to call RequestCancelWorkflowExecution, UpdateWorkflowExecution, QueryWorkflow, DescribeWorkflowExecution and GetWorkflowExecutionHistory.
  2. They call one of them with the id of a Temporal workflow, for example temporal-sys-scheduler:nightly.
  3. The Authorizer checks only that the API is on core's list. A1 said, on purpose, that the D9 name rules don't apply to nava-core. So the call is allowed.

What goes wrong

The attacker can cancel a schedule, poke an update into an internal workflow, or read its configuration and history. No tenant's data is exposed directly, but Temporal's own machinery can be broken or inspected, and F2-4 shows a case that affects every tenant.

The rule that stops it

Every workflow id that nava-core names must carry a tenant label. Temporal's own ids never do, so they're out of reach.
Decision text, word for word from the ADR

D9f (A2) · nava-core: RequestCancelWorkflowExecution, UpdateWorkflowExecution, QueryWorkflow, DescribeWorkflowExecution, GetWorkflowExecutionHistory

The request's workflow id (WorkflowExecution.WorkflowId / Execution.WorkflowId) must carry the t:<tenant>: prefix. Missing or empty is denied.

Decision text, word for word from the ADR

A1's sentence "D9 doesn't change … nava-core / nava-operator" now reads "D9 doesn't change … nava-operator". nava-operator stays outside D9: inspecting system workflows is its job, and the operator network restricts it (T28).

The test that proves it

TestAdversarialF2CoreWorkflowIDTenantPrefix in temporal-server/authz/adversarial_f2_test.go (merged with PR #36, skipped with the finding id). It sends each of the five nava-core APIs with each system workflow id and expects a denial.

red today when the skip is removed → green once the core-dev fix lands.

F2-3 Forged "job finished" tokens erratum E2

stolen certnava-worker
severityLow; exploitable with a worker cert
partErratum E2

What the attacker does, step by step

  1. A task token is just bytes. In our setup it is not signed, so anyone can build one. It contains the namespace, the workflow id and which step it belongs to.
  2. The attacker builds a token whose WorkflowId is a Temporal workflow, for example temporal-sys-scheduler:nightly.
  3. They send it on RespondActivityTaskCompleted, RespondActivityTaskFailed, RespondActivityTaskCanceled, RecordActivityTaskHeartbeat or RespondWorkflowTaskFailed.
  4. Erratum E1 already makes the Authorizer read the token, but only on RespondWorkflowTaskCompleted. On these five calls nobody reads it, so they are allowed.

What goes wrong

Temporal looks up the workflow the token names. If the step numbers line up with a pending job, it records the attacker's result, failure or heartbeat against a Temporal workflow. The worker was never given that job.

The rule that stops it

Every task token a worker sends must name a tenant-labelled workflow. This is E1's check, applied to all five remaining token APIs.
Decision text, word for word from the ADR

D9d (E2) · nava-worker: RespondWorkflowTaskFailed, RespondActivityTaskCompleted, RespondActivityTaskFailed, RespondActivityTaskCanceled, RecordActivityTaskHeartbeat

Decode TaskToken as token.v1.Task. Deny, with an alert, if it does not decode or if WorkflowId lacks the t:<tenant>: prefix. This extends E1's first bullet from RespondWorkflowTaskCompleted to every task-token API.

The test that proves it

TestAdversarialF2ActivityTaskTokenTenantPrefix in temporal-server/authz/adversarial_f2_test.go (merged with PR #36, skipped with the finding id). It sends a forged token naming each system workflow on each of the five APIs, and expects a denial.

Control that must stay green: a token for a tenant workflow is allowed on each API. The fix task adds that allow path for every API.

red today when the skip is removed → green once the core-dev fix lands.

F2-3b The frontend trusts the namespace inside the token amendment A2

stolen certnava-worker
severityMedium; bites at scale
partAmendment A2

What the attacker does, step by step

  1. The token also carries a namespace id. The attacker builds a token that names a different namespace, such as Temporal's own temporal-system or any namespace we add later.
  2. The request itself still says Namespace: nava. The Authorizer's namespace rule checks the request field, so the call is allowed.
  3. Inside Temporal, the frontend's namespace check runs after our Authorizer, and it lets the token's namespace win over the request's (common/rpc/interceptor/namespace_validator.go:226-249).
  4. Only one server setting, frontend.enableTokenNamespaceEnforcement, makes the frontend reject the mismatch. It defaults to true, but nothing makes sure it stays true.

What goes wrong

If that setting is ever turned off, by a config mistake or an upstream default change, a stolen worker cert reaches outside nava entirely. That is why this one is rated Medium.

The rule that stops it

Temporal refuses to start unless that setting is explicitly true. Our startup guard, D6-K, could only check "must be false" until now, so it gains a "must be true" mode.
Decision text, word for word from the ADR

checkSecurityConfig (temporal-server/cmd/server/check.go) implements only must-be-false today. guardedKey gains a want bool field. This can't live in the Authorizer: namespace validation runs after the auth interceptor (frontend/fx.go chain), and the token's namespace wins over the request's (common/rpc/interceptor/namespace_validator.go:226-249).

The test that proves it

TestAdversarialF2TokenNamespaceEnforcementGuarded in temporal-server/cmd/server/adversarial_f2_test.go (merged with PR #36, skipped with the finding id). F2-4 nava-core changes how nava-tq is routed amendment A2

stolen certnava-core
severityLow; bites at scale

What the attacker does, step by step

F2-5 A worker reads the history of Temporal's own workflows erratum E2

stolen certnava-worker
severityLow
partErratum E2

What the attacker does, step by step

  1. Workers are allowed to call GetWorkflowExecutionHistory. The SDK uses it to replay the tenant workflows it is running.
  2. The attacker calls it with a Temporal workflow id instead.
  3. No D9 rule checks the id on this API (authz/authorizer.go:149 has no entry for it), so the call is allowed.

F2-6 Unplugging the shared queue with a shutdown call erratum E2

stolen certnava-worker
severityLow; availability only
partErratum E2

What the attacker does, step by step

  1. When a worker shuts down cleanly, it calls ShutdownWorker with the name of its private sticky inbox, so that Temporal can drop it. The name normally looks like worker-host:<uuid>.
  2. The attacker sends ShutdownWorker with StickyTaskQueue: "nava-tq", our shared queue.
  3. Nobody checks that name, so the call is allowed. The frontend then force-unloads partition 0 of a queue with that name (frontend/workflow_handler.go:2733). For nava-tq, partition 0 is the root partition that every tenant's dispatch goes through.
  4. Two neighbours have the same gap. The queue named in a WorkerHeartbeat (on ShutdownWorker and RecordWorkerHeartbeat) is not checked, and neither is the queue inside a query token on RespondQueryTaskCompleted.

What goes wrong

Each call makes Temporal throw away the in-memory state of the shared queue and rebuild it. Workers' polls are cut off, and dispatch has to reload. Sent in a loop, it keeps work for every tenant stalling. No data is read or changed. The Technical Architect found this in review round 1, and the spike showed that the unload key is exactly the nava-tq root partition.

The rule that stops it

A shutdown or heartbeat may name only our platform queue, or a private-inbox name of the right shape. A query token may point only at those queues too. Both rules reuse the sticky-name check that D9b already has (stickyQueueName).
Decision text, word for word from the ADR

D9g (E2) · nava-worker: ShutdownWorker, RecordWorkerHeartbeat

StickyTaskQueue must be empty or pass the name half of the D9b sticky rule (stickyQueueName, and not a platform queue). Every WorkerHeartbeat.TaskQueue must be a platform queue. Anything else is denied with an alert. An absent heartbeat is allowed; a present one with an empty TaskQueue is denied.

Decision text, word for word from the ADR

D9d query clause (E2) · nava-worker: RespondQueryTaskCompleted

Decode TaskToken as token.v1.QueryTask. Deny, with an alert, if it does not decode, or if TaskQueue is neither a platform queue nor sticky-shaped (stickyQueueName).

Decision text, word for word from the ADR

Known at api v1.53.0. sdk-go v1.49.0 (api v1.63.5) also sends ShutdownWorkerRequest.TaskQueue, TaskQueueTypes and WorkerInstanceKey. The server's api v1.53.0 has only fields 1–5, so the Authorizer can't see them today. The api bump that adds them fails the golden, and that policy PR must classify TaskQueue as "platform queue".

The test that proves it

TestAdversarialF2WorkerShutdownTaskQueue in temporal-server/authz/adversarial_f2_worker_reach_test.go (merged with PR #36, skipped with the finding id). It expects denials for StickyTaskQueue set to the platform queue, temporal-sys-per-ns-tq, temporal-sys-x or nava-tq:not-a-uuid, and for a heartbeat queue of temporal-sys-per-ns-tq on both APIs.

Control that must stay green: the SDK-shaped ShutdownWorker is allowed: sticky worker-host:<uuid> and "", with the heartbeat on the platform queue.

red today when the skip is removed → green once the core-dev fix lands.

Part 5. R-CORE: the rule the Authorizer can't enforce

D9f (from F2-2) makes sure nava-core only ever names some tenant's workflow. But core serves every tenant with one certificate, so nothing at the Temporal door can tell tenant A's request from tenant B's. The only thing between tenant A's login and tenant B's workflow is how core builds the id. Page tokens add a second path. Temporal reads history by the page token, not by the workflow id in the request. So if core ever passed a client's page token straight through, a leaked tenant-B token would read B's history through A's own record. No code does this today, because core doesn't call Temporal yet. R-CORE makes sure the first code that does is built correctly.

Decision text, word for word from the ADR

R-CORE. nava-core builds every workflow id it sends to Temporal as t:<tenant>:<target_key>. <tenant> is the tenant D26 resolves from the request's validated access token, through tenant_identity_binding. <target_key> is read from workflow_ref under RLS in that tenant's context. nava-core never takes a full workflow id, or the tenant segment of one, from the request path, query string, body, headers other than the bearer token, or any stored column. A record that is not visible under RLS yields the same "not found" as a missing one (I5), and no Temporal call is made.

R-CORE, opaque tokens. nava-core never sends Temporal a page token (NextPageToken), or any other opaque Temporal token, that came from the client. It keeps the cursor server-side, or seals it with AEAD bound to the tenant and the workflow id. A token that fails to open, or that opens to a different tenant or workflow id, is treated as "not found" (I5), with no Temporal call.

Decision text, word for word from the ADR

Why it is a rule. D9f proves that a nava-core call names a tenant's workflow, never which tenant, because the nava-core certificate carries no tenant. History also reads a page by the token's branch token. The request's workflow id only picks the shard (server@v1.29.7 service/history/api/getworkflowexecutionhistory/api.go:140-165). So D9e and D9f bind the id in the request, not the history that comes back. R-CORE is I2 on the nava-core → Temporal path, and it mirrors the relay's rule in Annex A.2.

  • R-CORE-1: tenant A's JWT on a path naming tenant B's record returns the same 404 as a missing record, with no Temporal call.
  • R-CORE-2: tenant A's JWT on A's own record, with a client-supplied page token minted for B's workflow or with any raw NextPageToken, returns the same 404, with no Temporal call made with that token.

In plain words: one helper function is the only code allowed to build a Temporal workflow id. It takes the tenant from the validated login and the key from a database row that tenant can see. Anything else gets the same "not found" as a record that doesn't exist, so an attacker can't even learn that it exists. That matches invariant I5.

Part 6. The one principle behind all seven rules

Consolidated Annex A.2 statement, word for word from the ADR

Every workflow id that an allow-listed nava-relay, nava-core or nava-worker API names, including the one inside a token.v1.Task task token, must carry the t:<tenant>: prefix. Every task queue that such an API names, including the one inside a token.v1.QueryTask query token and inside a WorkerHeartbeat, must be a platform queue or, where D9b permits a sticky queue, sticky-shaped. A request field that names a workflow id or a task queue and that no rule classifies is a CI failure (drift golden), not an allow.

In plain words, the rules list what is allowed (tenant labels, our queues, private-inbox shapes) rather than what is banned. A ban list such as "no temporal-sys-" would quietly let through anything Temporal invents next year.

Part 7. Why some fixes are an erratum and others an amendment

An erratum corrects a record whose words were right but whose rule table and code fell short. An amendment changes what the record says. The difference matters for trust. An erratum says "we already promised this, here is the missing piece". An amendment says "this is a new promise, or a reversal of an old one", and it needs its own justification. Both are in this one record, and both go to you for sign-off.

Decision text, word for word from the ADR

The test for erratum vs amendment: A1's governing sentence is "A request that names a workflow type, a task queue or a workflow id is allowed only if every such field is allow-listed." If a finding is a field that names one of those, it is an erratum. If A1 is silent, or explicitly excludes the case, it is an amendment.

  • F2-3, F2-5, F2-6 are errata. A task token names a workflow id. A history request names a workflow id. A shutdown, heartbeat or query token names a task queue. The caller, nava-worker, is inside D9. So A1's "every such field" already covered them.
  • F2-2 and F2-4 are amendments, even though they also name workflow ids. A1 said in so many words that D9 does not change nava-core. Reversing an explicit sentence is a new decision. The ADR rewrites that sentence (see F2-2).
  • F2-1 is an amendment. Versioning fields are not a workflow id, a type or a queue, so A1 was silent about them.
  • F2-3b and R-CORE are amendments. One adds a new row to a closed config table plus a new guard mode. The other is a new written rule for code the Authorizer can't see.

Part 8. The CI drift golden

A golden is a file checked into the repo that holds the expected output of a test. If the real output differs, the test fails, and a person must look at the difference and either fix the code or knowingly update the file.

F2-6 shows why we need one. Between Temporal API releases, ShutdownWorkerRequest grew new fields, and nobody's rule read them. The drift golden lists every field of every request our three platform components are allowed to send. A Temporal upgrade that adds a field then fails CI until someone decides how that field is checked. This makes the rules complete by construction: "we forgot about a new field" becomes impossible to merge.

Decision text, word for word from the ADR

Drift golden (CI-C). A test in temporal-server/authz/policy_test.go, next to TestAllowListGolden, holds a golden of the full field paths of the request message of every API allow-listed for nava-relay, nava-core and nava-worker. It reads them from the proto descriptors, recursing into nested messages, and generates them from the allow-list itself. Any go.temporal.io/api bump that adds, removes or renames a field fails CI until a policy PR classifies that field. This is what makes D9b+ and D9g allow-list shaped, not deny-lists on named fields.

Implementation note (Technical Architect, round 2; it doesn't change the decision). The drift-golden walk must stop at any message type it has already visited on the current path. temporal.api.failure.v1.Failure contains itself through cause (api@v1.53.0 failure/v1/message.pb.go:669), and it sits under RespondActivityTaskFailed and RespondWorkflowTaskFailed, so a naive walk never ends. Print a cycle as failure.cause → (Failure) so the golden stays stable.

Part 10. What we are accepting (residual risks)

A residual risk is a weakness we knowingly keep. Each one has an owner and a trigger that tells us when to look at it again. The cards below are copied from the ADR.

RS6

R-CORE is enforced by code and tests, not by the Authorizer. That covers both clauses: R-CORE-1 (ids built from the JWT tenant) and R-CORE-2 (no client-supplied opaque token is forwarded). The Authorizer can't see inside a history page token.

Owner: Security & Multi-Tenancy Reviewer

Revisit when: The first nava-core Temporal call; any nava-core API that paginates Temporal results; any nava-core path that runs tenant-supplied code

RS7

Under D9g, one nava-worker pod can still unload a sibling pod's SDK-shaped sticky queue, because stickyQueueName checks the shape, not the owner. This is harmless: sticky dispatch falls back to the normal queue.

Owner: Security & Multi-Tenancy Reviewer

Revisit when: Worker certificates become per-pod or per-tenant; sticky queues gain a tenant meaning

RS2 (widened)

The new D6-K row is checked only at startup, like the rest.

Owner: Security & Multi-Tenancy Reviewer

Revisit when: Any runtime write path to dynamic config

  • RS6 in plain words: R-CORE is a promise about our own code, and no gatekeeper enforces it. What enforces it is one helper, two acceptance tests (R-CORE-1 and R-CORE-2), and a security review of the first core change that calls Temporal.
  • RS7 in plain words: the shutdown rule checks that a private-inbox name has the right shape, not that it belongs to the caller. So one worker pod could drop a sibling pod's private inbox. That only costs a cache miss: Temporal falls back to nava-tq, and the job still runs.
  • RS2 in plain words: like every startup check, the new "must be true" row only runs when Temporal starts. That's fine while nothing can change settings at runtime.

Glossary

Activity
One step of a workflow that touches the outside world.
Allow-list
A list of what is permitted. Anything not on it is denied. The opposite of a ban list (deny-list).
Amendment
A change to what a decision record says: a new rule, or the reversal of an old sentence.
Authorizer
Our gatekeeper code inside Temporal's front door. It checks every call against the caller's allow-list and the D9 rules.
AEAD
Authenticated encryption. Data sealed with it can't be read or altered without the key, so a cursor sealed this way can be handed to a client safely.
CI-C, CI-E, CI-I, CI-D/CI-G
Named CI gates from A1: C is the allow-list and drift goldens, E is the startup-guard keys checked by Go symbol, I is the adversarial tests, and D/G are the test suite and the full-stack smoke test.
D6-K
Our startup guard (checkSecurityConfig). Temporal refuses to start if a listed setting has the wrong value. A2 adds a "must be true" mode.
D9, D9a to D9g, D9b+
The Authorizer's name rules. D9a covers relay starts and signals, D9b worker polls, D9c worker commands (from A1). D9b+, D9d, D9e, D9f and D9g are new in A2.
D26
The earlier decision on how a login token is resolved to a tenant, through the tenant_identity_binding table.
Drift golden
A checked-in list of every request field our components may send. CI fails if a Temporal upgrade changes it, until a person classifies the change.
E1, E2
Errata to ADR-001. E1 added the token check on RespondWorkflowTaskCompleted, and E2 is part of this record.
Erratum
A correction where the record's words already required something and the rule table or code missed it.
Frontend / history / matching
Temporal's internal services: the front door, the store of workflow histories, and the task-queue dispatcher.
I2, I5
Platform invariants from ADR-001. I2: the tenant comes only from a platform-verified source. I5: an unreadable, other-tenant or missing record all give the same response.
JWT
The signed login token a user's request carries. Its tenant claim is the only trusted source of "which tenant" for nava-core.
mTLS / service certificate
How our components prove their identity to Temporal. It names the component, not a tenant.
Namespace
A walled-off partition inside a Temporal server. We use one, nava, shared by all tenants.
nava-core, -relay, -worker, -operator
Our API, our outbox dispatcher, our workflow runner, and our admin tooling.
Outbox
Rows our database writes in the same transaction as a change. The relay turns each row into a workflow start or signal, so the tenant comes from the database, not from a client.
Page token
An opaque "next page" cursor from Temporal. History follows the token itself, not the workflow id in the request.
Partition 0
The root partition of a task queue, which every other partition forwards to.
Platform queue
A task queue on our list. Today that is nava-tq.
Polling
A worker asking Temporal "any work for me on this queue?"
Query / query token
A read-only question to a running workflow, and the token the worker answers it with. The token names a task queue.
R-CORE, R-CORE-1, R-CORE-2
The written rule for how nava-core builds workflow ids and handles opaque tokens, and its two acceptance tests.
Residual risk (RS)
A weakness we knowingly keep, with an owner and a trigger for when to look at it again.
RLS
Row-level security in PostgreSQL. A tenant's queries see only that tenant's rows.
SDK (sdk-go v1.49.0)
Temporal's Go library, which our workers use to talk to Temporal.
Spike
A small, timeboxed experiment that settles a factual question.
Sticky queue
A worker's private inbox, <host>:<uuid>, used to skip a replay. Losing it only costs speed.
stickyQueueName
The existing check (authz/policy.go) that a name has the sticky-queue shape.
Task queue
A named inbox of jobs that workers poll.
Task token
The unsigned blob (token.v1.Task) that ties a worker's answer to a workflow and a step.
t:<tenant>:
The label at the start of every tenant workflow id. Temporal's own workflows never have it.
temporal-sys-*
Ids and queues of Temporal's own internal workflows, which run inside our namespace.
Worker versioning / deployment
A Temporal feature that routes tasks to specific worker builds. We don't use it.
Workflow, workflow id, workflow type, history
A durable job; its name; its kind; and its recorded list of events.
